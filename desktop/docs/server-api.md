## mold-server HTTP API surface

Router assembled in `crates/mold-server/src/routes.rs::create_router` (state routes) merged with `web_ui::router()` (SPA fallback) plus a feature-gated `/metrics`. Middleware stack (outer→inner) from `lib.rs`: **CORS → Trace → RequestID → (Metrics) → Auth → RateLimit → routes**. All request/response types unless noted are in **`mold-core`** (package `mold-ai-core`, `src/types.rs`, `src/chain.rs`, `src/chain_job.rs`, `src/catalog_wire.rs`).

### Endpoint table

Auto-chained one-shots can resume only from `Paused` or `Interrupted`; authored
sequences additionally permit resume from `Failed` or `Cancelled`.

### Creation-time filing and request advisories

`GenerateRequest` and the `POST /api/chain-jobs` body carry three additive
optional fields — `title`, `tags` (`Vec<String>`), and `collection`
(`mold_core::CollectionRef`, either `{ "id": … }` or `{ "name": … }`) — so a
print arrives already organized. Rules live in `mold_core::organization` and
are enforced at admission: at most 20 distinct tags after normalization, each
1..=64 Unicode scalars, whitespace controls collapsed to a single space and
any other control character a `422`; a leading `#` is a literal character on
the wire, never a sigil the server strips. A `{ "name": … }` collection
resolves by slug on the serving host and is created when absent, so one name
means one collection across a fleet; a `{ "id": … }` reference resolves at
admission. Filing is applied ONCE, when the print is published, and only on
the row's INSERT — a reconcile or re-publication never resurrects a tag the
user removed. A sequence files the stitched print only; intermediate clips
never reach the gallery. Batch and prepared siblings inherit their parent's
filing.

Filing can never fail a render. A host with `MOLD_DB_DISABLE=1`, a collection
deleted between listing and Generate, or an otherwise unusable value drops the
filing, publishes the print anyway, and reports it as an advisory.

Advisories about an ACCEPTED request ride the `x-mold-request-warning`
response header (the same header that already carries e.g. a lip-dub retime)
and are mirrored into additive `request_warnings: Vec<String>` on
`GenerateResponse` and `ChainResponse` for JSON consumers. **Never split that
header's value on `;` or `; `** — the server joins several advisories with
`"; "`, but its own advisory prose contains that sequence ("…were not applied;
the print was generated and saved normally"), so a splitting parser shreds one
advisory into dangling half-sentences. Take each value whole. Read it with
`get_all` (as `mold_core`'s client does) so a server that one day emits one
header per advisory is handled without a client change.

## Durable queue and the retention contract

A queued generation survives a server restart on hosts that report
`capabilities.queue.durable_queue`. The row is written before the job is
queued and returns after restart as `paused` **under the same job id**. It does
not run until an operator calls `POST /api/queue/resume`.

Four client rules follow, and the first is not optional:

1. **Never `DELETE` a queued job because its stream died.** Accepted work is
   detached from the client stream and still runs in the current server
   process. `durable` only controls restart replay; even a `durable: false`
   reference-upload job must remain queued. Keep polling `/api/queue` instead.
2. **`SseErrorEvent` gains additive `retained: bool` and `code: Option<String>`.**
   A terminal frame with `retained: true` (`code: "server_restarting"`) means
   the job did **not** fail — the host is restarting and retained it. Treat it
   as interrupted: suppress the failure notification and reconcile it as
   `paused`. Old clients that ignore the flag see
   an ordinary error message, which is why a frame is sent rather than a quiet
   close (a quiet close leaves a client stuck in `loading`, or hard-fails).
3. **`durable_queue` is false when the host has no server gallery output.**
   Such a host cannot promise durability for any job — the only delivery is
   the HTTP response — so the capability is false there even though the
   journal itself is available. A client gating on the capability alone is
   therefore correct for that whole class, and does not need to model it.
4. **Durability is per job, not just per host.** `JobEntry` gains additive
   `durable`, `replayed`, `dispatch_attempts`, and `held_reason`.
   `capabilities.queue.durable_queue` says the host _can_ promise durability;
   `JobEntry.durable` says whether _this_ job got it. A job with no gallery
   target, one carrying reference-upload media, or one whose request exceeded
   the payload ceiling reports `durable: false`; it still runs normally but
   cannot be replayed after a server restart.

**Recovery finishes before the router serves.** A restarted host does not answer
`/api/queue` until every retained queued or running job has been parked as
`paused` under its original id. A successful listing after restart therefore
reflects work waiting for explicit resume, never work silently restarted.
Absence from a `200` response is therefore a sound signal that a job is gone;
absence because the host was unreachable is not.

`JobLifecycle` includes `paused` for restart-recovered work and `held` for a
job retained across restarts that exceeded its
attempt budget or could not be reconciled. Held rows are listed with a
`held_reason` and are **never** started automatically — surface them, do not
hide them, and clear one with `DELETE /api/queue/:id`.

`OutputMetadata` gains additive `job_id`, the queue job that produced a print.
It is the server's replay idempotence key; clients may use it to correlate a
resumed job with the print it eventually produced.

`queue.cooperative_cancellation` is `true` on current servers. A
`DELETE /api/queue/:id` for running singleton work revokes its inference token
and returns immediately; the worker stops at the next model safe point. Older
servers omit/false this capability, so clients keep their running rows read-only.

During shutdown, `POST /api/generate` and `/api/generate/stream` answer
`503` with code `SERVER_RESTARTING` and a `Retry-After` header.

`PATCH /api/queue/:id` accepts additive `hard_pinned_device_id`; legacy
`target_gpu` remains supported, and supplying both is valid only when they
resolve to the same device. `/api/events` adds `queue_plan_changed` and
`device_state_changed` deltas. Device events cover administrative lifecycle,
worker health, and activity transitions; raw utilization and memory stay on
`/api/resources/stream`. Clients bootstrap/refetch the snapshot endpoints after
subscribing or reconnecting and apply only newer plan versions.

### Streaming / progress mechanism

**SSE only — there are no WebSockets anywhere.** All progress is `axum::response::sse::Sse` with a 15 s keepalive `ping` comment. Two channel patterns:

- **Single-shot generation** (`/api/generate/stream`, `/api/upscale/stream`, `/api/models/pull`): an `mpsc::unbounded_channel<SseMessage>` (enum in `state.rs`: `Progress|Complete|UpscaleComplete|Error`) is drained into named SSE events. Progress payload is **`mold_core::SseProgressEvent`** (tagged enum: `DependencyWait, StageStart, StageDone, StageProgress, Info, CacheHit, DenoiseStep, Preview, DownloadProgress, DownloadDone, PullComplete, Queued{position,id}, WeightLoad`). Completion is **`mold_core::SseCompleteEvent`** (base64 image _or_ video bytes + `video_*` metadata fields; additive `filename`/`original_filename` carry the server-gallery names the payload was saved under and `metadata` the recorded `OutputMetadata`, so mirroring clients keep one cross-host identity — absent on older servers). Prepared native-app siblings optionally send `original_prompt`, `batch_id`, one-based `batch_index`, and `batch_count`; the server copies them unchanged into complete-event and saved Gallery metadata. Errors are `mold_core::SseErrorEvent{message, retained?, code?}` — see the durable-queue section for `retained`. Event names on the wire: `progress`, `complete`, `error`.
- A generation request with `upscale_model` auto-pulls that upscaler on the serving host before multi-GPU dispatch (the single-worker path also auto-pulls before its post-generation upscale), so remote desktop routing never depends on the model already being installed locally or remotely.
- A post-generation upscale saves both `-original` and `-upscaled` gallery artifacts. Image completion events keep `image` as the upscaled payload and add optional `original_image`, `original_width`, and `original_height` fields for remote mirroring; output metadata keeps physical `width` / `height` separate from reusable `generation_width` / `generation_height`.
- **Broadcast/telemetry** (`/api/resources/stream`, `/api/downloads/stream`, `/api/chain-jobs/:id/events`): `tokio::sync::broadcast` → `BroadcastStream`, each stream yields an initial **snapshot** frame then live deltas. `/api/events` is the same mechanism but **deltas only** (no snapshot frame): `mold_core::ServerEvent` job lifecycle, gallery adds/removes, queue replans, and semantic device transitions. Clients refetch `/api/queue` and `/api/devices` on relevant events and on every reconnect; raw device telemetry stays on `/api/resources/stream`. Older servers without the endpoint (probe `capabilities.events`) fall back to polling. Chain job events use `mold_core::chain_job::ChainJobEvent` (`Snapshot, StageStart, DenoiseStep, StageDone, Finalizing, Yielded, Finalized, StateChanged`), event name `chain_job`.

The **non-streaming `/api/generate`** returns raw bytes with headers, not SSE. Clients that want progress must use `/stream`. The SPA also **polls `GET /api/queue`** to dead-letter cards whose SSE stream silently dropped (the `Queued{id}` event lets it correlate).

**Chain generation** has exactly one execution tier. `routes_chain.rs` is read-only planning — it holds `POST /api/generate/chain/validate` and nothing else; the synchronous `POST /api/generate/chain` and SSE `POST /api/generate/chain/stream` shims are **deleted**, because they ran a chain as a hidden ephemeral job and destroyed its artifacts when they answered, so a dropped connection lost work that could not be resumed, retaken, or reattached. Every sequence — authored or auto-chained — is a durable job on `/api/chain-jobs*` (`routes_chain_jobs.rs`), persisted in SQLite (`mold-db`) with resume/retake/amend/cancel/gc and per-stage JPEG previews, and requiring the metadata DB (else 503 `CHAIN_JOBS_UNAVAILABLE`). `ChainRequest.ephemeral: true` marks an auto-chained one-shot: it stays out of authored `GET /api/chain-jobs` listings and emits no `chain_job_queued`, but remains visible in `/api/activity`; graceful shutdown parks it as `paused`, preserves its manifest and stage media, and permits explicit resume. Cleanup sweeps it only after settlement, and its print has no `chain_job_id`. `ChainRequest` accepts the same optional `original_prompt`, `batch_id`, `batch_index`, and `batch_count` provenance as `GenerateRequest`; auto-expansion, normalization, durable resume, synthetic stitched metadata, Gallery rows, and complete events preserve them unchanged.

**Preview frames**: live denoise previews arrive on `/api/generate/stream` as `progress` events of variant `SseProgressEvent::Preview`, and the latest snapshot for a job already accepted is `GET /api/queue/:id/preview` (`QueueJobProgress`, `null` before the first progress event) — that is how web, desktop, iPhone, and the TUI paint a running print. Two other things are also called "previews" and are unrelated: (a) chain-job per-stage JPEG stills (`/api/chain-jobs/:id/stages/:idx/preview`) and (b) gallery animated-GIF sidecars (`/api/gallery/preview/:filename`). Video output (MP4/WebP/GIF/APNG) is served as whole files via `/api/gallery/image/:filename` with Range support for `<video>` scrubbing.

### Auth (MOLD_API_KEY)

`auth.rs`: `load_api_keys()` reads `MOLD_API_KEY` — single value, comma-separated list, or `@/path/to/file` (one key/line, `#` comments). Unset/empty ⇒ auth disabled. Enforced by `require_api_key` middleware checking the **`X-Api-Key`** header with constant-time compare (`subtle`). Exempt paths (`auth.rs::EXEMPT_PATHS`): `/health`, `/api/docs`, `/api/openapi.json`, and `/api/pairing/claim` — the last because the one-use pairing ticket _is_ the credential being redeemed, so it is deliberately the only unauthenticated credential handoff (`/metrics` is mounted outside the auth layer entirely). When auth is **disabled**, `POST /api/shutdown` is restricted to loopback IPs. Rate limiting (`rate_limit.rs`) is opt-in via `MOLD_RATE_LIMIT=N/period` (sec|min|hour) + `MOLD_RATE_LIMIT_BURST`, and `classify_route` sorts every path into two tiers: **read** is every `GET`, `POST /api/generation-batches/status`, and anything unclassified, at ten times the configured rate capped at 1000/period; **generation** is `POST` to `/api/generate`, `/api/generate/stream`, `/api/generate/placement-preview`, `/api/generation-batches`, `/api/chain-jobs/placement-preview`, `/api/expand`, `/api/upscale[/stream]`, `/api/models/load`, `/api/models/pull`, `/api/queue/:id/retry` and `/api/queue/held/sweep`, plus `PATCH /api/devices/*`, `DELETE /api/models/unload`, and every `DELETE` under `/api/gallery/`. `/health`, `/api/docs`, and `/api/openapi.json` are not rate limited at all.

Pairing never copies an operator key. `POST /api/pairing/sessions` creates a
two-minute, one-use handoff; `POST /api/pairing/claim` exchanges it for a
random per-client credential whose SHA-256 digest is persisted in
`paired_clients`. Operator credentials list grants with
`GET /api/pairing/clients` and revoke one immediately with
`DELETE /api/pairing/clients/:id`. Paired credentials are accepted by normal
API routes but cannot mint or manage pairing grants.

Browser and native media elements cannot attach `X-Api-Key` to their own Range
requests. An authenticated client can POST `{ "path":
"/api/gallery/image/:filename" }` to `/api/gallery/media-token` and receive a
15-minute `media_token` plus Unix `expires` value. That query credential is
signed by a per-process secret, scoped to the exact path, accepted only for
GET/HEAD gallery-image reads, and deliberately omitted from trace paths. It is
not an API-key verifier and cannot authorize gallery deletion or any other API.
When auth is disabled the endpoint explicitly returns `auth_required: false`
and no token is needed.

### CORS / binding

`build_cors_layer()` in `lib.rs`: if `MOLD_CORS_ORIGIN` is set → restricted `CorsLayer` allowing GET/HEAD/POST/PATCH/PUT/DELETE (PATCH and PUT are load-bearing — `/api/gallery/image/:filename`, `/api/gallery/collections/:id[/items]`, `/api/queue/:id`, `/api/devices/:id`, and `/api/config/:key` all need them) and exposing the `x-mold-*`/`x-request-id`/`retry-after` headers; otherwise **`CorsLayer::permissive()`** (default). Body limit 64 MiB. Default bind is `0.0.0.0:7680` (CLI `serve`/`server start`, `--port`/`MOLD_PORT` env, `--bind`). The SPA can be overridden at runtime with `MOLD_WEB_DIR`; embedded bundle resolution order is documented in `web_ui.rs`.

### Library embedding (mold-cli → mold-server)

Single entry point (`crates/mold-server/src/lib.rs`):

```rust
pub async fn run_server(
    bind: &str, port: u16, models_dir: PathBuf,
    gpu_selection: mold_core::types::GpuSelection, queue_size: usize,
) -> anyhow::Result<()>
```

Called from `crates/mold-cli/src/commands/serve.rs::run`. It re-arms SIGPIPE ignore, discovers GPUs (`mold_inference::device`), builds a per-GPU worker pool + tokio generation queue, opens the metadata DB (`mold_db::open_default`), spawns the chain-job runner, resource aggregator, download driver and idle-evictor, then `axum::serve` with graceful shutdown (SIGTERM or `POST /api/shutdown`). `queue_size` defaults to 200 and bounds only the hydrated runtime window; it does not cap the durable backlog. `logging::init_tracing` is also a public library helper the CLI uses. A Tauri backend could call `run_server` directly to host the same API in-process, or import the router builder.

### mold-core types reusable directly by a Tauri Rust backend

All of these derive `Serialize`/`Deserialize` (and utoipa `ToSchema`) and are the exact HTTP wire types — a Tauri backend depending on `mold-ai-core` reuses them verbatim:

- **Generation**: `GenerateRequest`, `GenerateResponse`, `ImageData`, `VideoData`, `OutputFormat`, `LoraWeight`, `LoraInfo`, `KeyframeCondition`, `TimeRange`, `Ltx2PipelineMode/SpatialUpscale/TemporalUpscale`, `Scheduler`, `DevicePlacement`, `GpuSelection`.
- **SSE**: `SseProgressEvent`, `SseCompleteEvent`, `SseErrorEvent`, `SseUpscaleCompleteEvent`.
- **Chain**: `ChainRequest`, `ChainStage`, `ChainResponse`, `ChainScript`, `ChainProgressEvent`, `SseChainCompleteEvent`, `ChainFailure`; `chain_job::{ChainJobSummary, ChainJobDetail, ChainJobStageDetail, ChainJobListing, CreateChainJobResponse, RetakeRequest, RetakeMode, ChainJobEvent, ChainJobState, StageState, GcOutcome, FinalizeRecord}`.
- **Status/telemetry/gallery**: `ServerStatus`, `DiskUsage`, `ActiveGenerationStatus`, `GpuInfo`, `ResourceSnapshot`, `GpuSnapshot`, `RamSnapshot`, `CpuSnapshot`, `GpuBackend`, `GalleryImage`, `OutputMetadata`, `ServerCapabilities`/`GalleryCapabilities`/`CatalogCapabilities`, `GenerationMemoryEstimate`, `ModelInfo`, `ModelInfoExtended`, `ModelComponentsResponse`.
- **Expand/upscale/downloads/catalog**: `ExpandRequest`, `ExpandResponse`, `UpscaleRequest`, `UpscaleResponse`, `types::DownloadEvent`, `catalog_wire::{InstalledCatalogResponse, InstalledCatalogEntry, DownloadRecipeWire}`.
- Also `mold_core::client` is a ready-made HTTP client (already used by mold-discord/mold-tui) that a Tauri backend could reuse instead of hand-rolling requests.

A few wire structs live in **mold-server** (not reusable without depending on the server crate): `routes::{LoadModelBody, UnloadRequest, CreateDownloadBody, CreateDownloadResponse}`, `job_registry::{JobEntry, QueueListing, JobLifecycle}`, `chain_limits::ChainLimits`, and `catalog_api::CompanionJob`. These are simple enough to mirror if the Tauri backend only depends on `mold-core`.

## Metal host memory

The shared device panel displays a connected Metal host's effective capacity,
allocation headroom and kernel mode when its server advertises that telemetry.
Older hosts omit this section. Shared RAM remains separate from the Metal
budget. Kernel changes are local-only `mold system metal-memory` commands on
that Mac; the app has no remote privileged control. See the
[Metal memory guide](../../website/guide/metal-memory.md).
