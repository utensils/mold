## mold-server HTTP API surface

Router assembled in `crates/mold-server/src/routes.rs::create_router` (state routes) merged with `web_ui::router()` (SPA fallback) plus a feature-gated `/metrics`. Middleware stack (outer→inner) from `lib.rs`: **CORS → Trace → RequestID → (Metrics) → Auth → RateLimit → routes**. All request/response types unless noted are in **`mold-core`** (package `mold-ai-core`, `src/types.rs`, `src/chain.rs`, `src/chain_job.rs`, `src/catalog_wire.rs`).

Current multi-GPU servers additionally expose `GET /api/devices` and
`PATCH /api/devices/:stable-id {enabled}`. The inventory includes every
visible full GPU or MIG instance, stable identity, nullable telemetry,
lifecycle/health/activity, active work, and planned work. Disabling an active
device returns its draining state and prevents new assignments; current work
finishes. Device mutation is authenticated and rate-limited like generation.

`GET /api/queue` retains the legacy `entries` projection and adds an optional
versioned `plan` with stable device lanes, blocked/assignment reasons,
estimated start/finish plus confidence, and the sliding replan deadline.
`PATCH /api/queue/:id` accepts additive `hard_pinned_device_id`; legacy
`target_gpu` remains supported, and supplying both is valid only when they
resolve to the same device. `/api/events` adds `queue_plan_changed` and
`device_state_changed` deltas. Device events cover administrative lifecycle,
worker health, and activity transitions; raw utilization and memory stay on
`/api/resources/stream`. Clients bootstrap/refetch the snapshot endpoints after
subscribing or reconnecting and apply only newer plan versions.

### Streaming / progress mechanism

**SSE only — there are no WebSockets anywhere.** All progress is `axum::response::sse::Sse` with a 15 s keepalive `ping` comment. Two channel patterns:

- **Single-shot generation** (`/api/generate/stream`, `/api/upscale/stream`, `/api/models/pull`): an `mpsc::unbounded_channel<SseMessage>` (enum in `state.rs`: `Progress|Complete|UpscaleComplete|Error`) is drained into named SSE events. Progress payload is **`mold_core::SseProgressEvent`** (tagged enum: `StageStart, StageDone, Info, CacheHit, DenoiseStep, DownloadProgress, DownloadDone, PullComplete, Queued{position,id}, WeightLoad`). Completion is **`mold_core::SseCompleteEvent`** (base64 image _or_ video bytes + `video_*` metadata fields; additive `filename`/`original_filename` carry the server-gallery names the payload was saved under and `metadata` the recorded `OutputMetadata`, so mirroring clients keep one cross-host identity — absent on older servers). Prepared native-app siblings optionally send `original_prompt`, `batch_id`, one-based `batch_index`, and `batch_count`; the server copies them unchanged into complete-event and saved Gallery metadata. Errors are `mold_core::SseErrorEvent{message}`. Event names on the wire: `progress`, `complete`, `error`.
- A generation request with `upscale_model` auto-pulls that upscaler on the serving host before multi-GPU dispatch (the single-worker path also auto-pulls before its post-generation upscale), so remote desktop routing never depends on the model already being installed locally or remotely.
- A post-generation upscale saves both `-original` and `-upscaled` gallery artifacts. Image completion events keep `image` as the upscaled payload and add optional `original_image`, `original_width`, and `original_height` fields for remote mirroring; output metadata keeps physical `width` / `height` separate from reusable `generation_width` / `generation_height`.
- **Broadcast/telemetry** (`/api/resources/stream`, `/api/downloads/stream`, `/api/chain-jobs/:id/events`): `tokio::sync::broadcast` → `BroadcastStream`, each stream yields an initial **snapshot** frame then live deltas. `/api/events` is the same mechanism but **deltas only** (no snapshot frame): `mold_core::ServerEvent` job lifecycle, gallery adds/removes, queue replans, and semantic device transitions. Clients refetch `/api/queue` and `/api/devices` on relevant events and on every reconnect; raw device telemetry stays on `/api/resources/stream`. Older servers without the endpoint (probe `capabilities.events`) fall back to polling. Chain job events use `mold_core::chain_job::ChainJobEvent` (`Snapshot, StageStart, DenoiseStep, StageDone, Finalizing, Yielded, Finalized, StateChanged`), event name `chain_job`.

The **non-streaming `/api/generate`** returns raw bytes with headers, not SSE. Clients that want progress must use `/stream`. The SPA also **polls `GET /api/queue`** to dead-letter cards whose SSE stream silently dropped (the `Queued{id}` event lets it correlate).

**Chain generation** has two tiers: the legacy `/api/generate/chain[/stream]` shim (in `routes_chain.rs`) creates an _ephemeral_ durable job and maps runner events back to the legacy `ChainProgressEvent`/`SseChainCompleteEvent` wire shape, deleting artifacts after; the durable `/api/chain-jobs*` surface (`routes_chain_jobs.rs`) persists jobs in SQLite (`mold-db`) with resume/retake/cancel/gc and per-stage JPEG previews. Both require the metadata DB (else 503 `CHAIN_JOBS_UNAVAILABLE`). `ChainRequest` accepts the same optional `original_prompt`, `batch_id`, `batch_index`, and `batch_count` provenance as `GenerateRequest`; auto-expansion, normalization, durable resume, synthetic stitched metadata, Gallery rows, and complete events preserve them unchanged.

**Preview frames**: no live-denoising preview-frame stream exists; "previews" are (a) chain-job per-stage JPEG stills (`/api/chain-jobs/:id/stages/:idx/preview`) and (b) gallery animated-GIF sidecars (`/api/gallery/preview/:filename`). Video output (MP4/WebP/GIF/APNG) is served as whole files via `/api/gallery/image/:filename` with Range support for `<video>` scrubbing.

### Auth (MOLD_API_KEY)

`auth.rs`: `load_api_keys()` reads `MOLD_API_KEY` — single value, comma-separated list, or `@/path/to/file` (one key/line, `#` comments). Unset/empty ⇒ auth disabled. Enforced by `require_api_key` middleware checking the **`X-Api-Key`** header with constant-time compare (`subtle`). Exempt paths: `/health`, `/api/docs`, `/api/openapi.json` (and `/metrics` is mounted outside the auth layer entirely). When auth is **disabled**, `POST /api/shutdown` is restricted to loopback IPs. Rate limiting (`rate_limit.rs`) is opt-in via `MOLD_RATE_LIMIT=N/period` (sec|min|hour) + `MOLD_RATE_LIMIT_BURST`.

Pairing never copies an operator key. `POST /api/pairing/sessions` creates a
two-minute, one-use handoff; `POST /api/pairing/claim` exchanges it for a
random per-client credential whose SHA-256 digest is persisted in
`paired_clients`. Operator credentials list grants with
`GET /api/pairing/clients` and revoke one immediately with
`DELETE /api/pairing/clients/:id`. Paired credentials are accepted by normal
API routes but cannot mint or manage pairing grants.

Browser and native media elements cannot attach `X-Api-Key` to their own Range
requests. An authenticated client can POST `{ "path":
"/api/gallery/image/:filename" }` to `/api/gallery/media-token` and receive a
15-minute `media_token` plus Unix `expires` value. That query credential is
signed by a per-process secret, scoped to the exact path, accepted only for
GET/HEAD gallery-image reads, and deliberately omitted from trace paths. It is
not an API-key verifier and cannot authorize gallery deletion or any other API.
When auth is disabled the endpoint explicitly returns `auth_required: false`
and no token is needed.

### CORS / binding

`build_cors_layer()` in `lib.rs`: if `MOLD_CORS_ORIGIN` is set → restricted `CorsLayer` allowing GET/POST/DELETE and exposing the `x-mold-*`/`x-request-id`/`retry-after` headers; otherwise **`CorsLayer::permissive()`** (default). Body limit 64 MiB. Default bind is `0.0.0.0:7680` (CLI `serve`/`server start`, `--port`/`MOLD_PORT` env, `--bind`). The SPA can be overridden at runtime with `MOLD_WEB_DIR`; embedded bundle resolution order is documented in `web_ui.rs`.

### Library embedding (mold-cli → mold-server)

Single entry point (`crates/mold-server/src/lib.rs`):

```rust
pub async fn run_server(
    bind: &str, port: u16, models_dir: PathBuf,
    gpu_selection: mold_core::types::GpuSelection, queue_size: usize,
) -> anyhow::Result<()>
```

Called from `crates/mold-cli/src/commands/serve.rs::run` (line 132). It re-arms SIGPIPE ignore, discovers GPUs (`mold_inference::device`), builds a per-GPU worker pool + tokio generation queue, opens the metadata DB (`mold_db::open_default`), spawns the chain-job runner, resource aggregator, download driver and idle-evictor, then `axum::serve` with graceful shutdown (SIGTERM or `POST /api/shutdown`). `queue_size` default is 600 (CLI). `logging::init_tracing` is also a public library helper the CLI uses. A Tauri backend could call `run_server` directly to host the same API in-process, or import the router builder.

### mold-core types reusable directly by a Tauri Rust backend

All of these derive `Serialize`/`Deserialize` (and utoipa `ToSchema`) and are the exact HTTP wire types — a Tauri backend depending on `mold-ai-core` reuses them verbatim:

- **Generation**: `GenerateRequest`, `GenerateResponse`, `ImageData`, `VideoData`, `OutputFormat`, `LoraWeight`, `LoraInfo`, `KeyframeCondition`, `TimeRange`, `Ltx2PipelineMode/SpatialUpscale/TemporalUpscale`, `Scheduler`, `DevicePlacement`, `GpuSelection`.
- **SSE**: `SseProgressEvent`, `SseCompleteEvent`, `SseErrorEvent`, `SseUpscaleCompleteEvent`.
- **Chain**: `ChainRequest`, `ChainStage`, `ChainResponse`, `ChainScript`, `ChainProgressEvent`, `SseChainCompleteEvent`, `ChainFailure`; `chain_job::{ChainJobSummary, ChainJobDetail, ChainJobStageDetail, ChainJobListing, CreateChainJobResponse, RetakeRequest, RetakeMode, ChainJobEvent, ChainJobState, StageState, GcOutcome, FinalizeRecord}`.
- **Status/telemetry/gallery**: `ServerStatus`, `DiskUsage`, `ActiveGenerationStatus`, `GpuInfo`, `ResourceSnapshot`, `GpuSnapshot`, `RamSnapshot`, `CpuSnapshot`, `GpuBackend`, `GalleryImage`, `OutputMetadata`, `ServerCapabilities`/`GalleryCapabilities`/`CatalogCapabilities`, `GenerationMemoryEstimate`, `ModelInfo`, `ModelInfoExtended`, `ModelComponentsResponse`.
- **Expand/upscale/downloads/catalog**: `ExpandRequest`, `ExpandResponse`, `UpscaleRequest`, `UpscaleResponse`, `types::DownloadEvent`, `catalog_wire::{InstalledCatalogResponse, InstalledCatalogEntry, DownloadRecipeWire}`.
- Also `mold_core::client` is a ready-made HTTP client (already used by mold-discord/mold-tui) that a Tauri backend could reuse instead of hand-rolling requests.

A few wire structs live in **mold-server** (not reusable without depending on the server crate): `routes::{LoadModelBody, UnloadRequest, CreateDownloadBody, CreateDownloadResponse}`, `job_registry::{JobEntry, QueueListing, JobLifecycle}`, `chain_limits::ChainLimits`, and `catalog_api::CompanionJob`. These are simple enough to mirror if the Tauri backend only depends on `mold-core`.
