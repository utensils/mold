## mold-server HTTP API surface

Router assembled in `crates/mold-server/src/routes.rs::create_router` (state routes) merged with `web_ui::router()` (SPA fallback) plus a feature-gated `/metrics`. Middleware stack (outer→inner) from `lib.rs`: **CORS → Trace → RequestID → (Metrics) → Auth → RateLimit → routes**. All request/response types unless noted are in **`mold-core`** (package `mold-ai-core`, `src/types.rs`, `src/chain.rs`, `src/chain_job.rs`, `src/catalog_wire.rs`).

### Streaming / progress mechanism

**SSE only — there are no WebSockets anywhere.** All progress is `axum::response::sse::Sse` with a 15 s keepalive `ping` comment. Two channel patterns:

- **Single-shot generation** (`/api/generate/stream`, `/api/upscale/stream`, `/api/models/pull`): an `mpsc::unbounded_channel<SseMessage>` (enum in `state.rs`: `Progress|Complete|UpscaleComplete|Error`) is drained into named SSE events. Progress payload is **`mold_core::SseProgressEvent`** (tagged enum: `StageStart, StageDone, Info, CacheHit, DenoiseStep, DownloadProgress, DownloadDone, PullComplete, Queued{position,id}, WeightLoad`). Completion is **`mold_core::SseCompleteEvent`** (base64 image _or_ video bytes + `video_*` metadata fields). Errors are `mold_core::SseErrorEvent{message}`. Event names on the wire: `progress`, `complete`, `error`.
- **Broadcast/telemetry** (`/api/resources/stream`, `/api/downloads/stream`, `/api/chain-jobs/:id/events`): `tokio::sync::broadcast` → `BroadcastStream`, each stream yields an initial **snapshot** frame then live deltas. `/api/events` is the same mechanism but **deltas only** (no snapshot frame): `mold_core::ServerEvent` job lifecycle (emitted from `job_registry`) + gallery adds/removes (emitted from the save helpers and gallery delete). The desktop `events` store subscribes app-wide and drives live gallery updates; older servers without the endpoint (probe `capabilities.events`) fall back to a 5 s gallery poll while jobs are pending. Chain job events use `mold_core::chain_job::ChainJobEvent` (`Snapshot, StageStart, DenoiseStep, StageDone, Finalizing, Yielded, Finalized, StateChanged`), event name `chain_job`.

The **non-streaming `/api/generate`** returns raw bytes with headers, not SSE. Clients that want progress must use `/stream`. The SPA also **polls `GET /api/queue`** to dead-letter cards whose SSE stream silently dropped (the `Queued{id}` event lets it correlate).

**Chain generation** has two tiers: the legacy `/api/generate/chain[/stream]` shim (in `routes_chain.rs`) creates an _ephemeral_ durable job and maps runner events back to the legacy `ChainProgressEvent`/`SseChainCompleteEvent` wire shape, deleting artifacts after; the durable `/api/chain-jobs*` surface (`routes_chain_jobs.rs`) persists jobs in SQLite (`mold-db`) with resume/retake/cancel/gc and per-stage JPEG previews. Both require the metadata DB (else 503 `CHAIN_JOBS_UNAVAILABLE`).

**Preview frames**: no live-denoising preview-frame stream exists; "previews" are (a) chain-job per-stage JPEG stills (`/api/chain-jobs/:id/stages/:idx/preview`) and (b) gallery animated-GIF sidecars (`/api/gallery/preview/:filename`). Video output (MP4/WebP/GIF/APNG) is served as whole files via `/api/gallery/image/:filename` with Range support for `<video>` scrubbing.

### Auth (MOLD_API_KEY)

`auth.rs`: `load_api_keys()` reads `MOLD_API_KEY` — single value, comma-separated list, or `@/path/to/file` (one key/line, `#` comments). Unset/empty ⇒ auth disabled. Enforced by `require_api_key` middleware checking the **`X-Api-Key`** header with constant-time compare (`subtle`). Exempt paths: `/health`, `/api/docs`, `/api/openapi.json` (and `/metrics` is mounted outside the auth layer entirely). When auth is **disabled**, `POST /api/shutdown` is restricted to loopback IPs. Rate limiting (`rate_limit.rs`) is opt-in via `MOLD_RATE_LIMIT=N/period` (sec|min|hour) + `MOLD_RATE_LIMIT_BURST`.

### CORS / binding

`build_cors_layer()` in `lib.rs`: if `MOLD_CORS_ORIGIN` is set → restricted `CorsLayer` allowing GET/POST/DELETE and exposing the `x-mold-*`/`x-request-id`/`retry-after` headers; otherwise **`CorsLayer::permissive()`** (default). Body limit 64 MiB. Default bind is `0.0.0.0:7680` (CLI `serve`/`server start`, `--port`/`MOLD_PORT` env, `--bind`). The SPA can be overridden at runtime with `MOLD_WEB_DIR`; embedded bundle resolution order is documented in `web_ui.rs`.

### Library embedding (mold-cli → mold-server)

Single entry point (`crates/mold-server/src/lib.rs`):

```rust
pub async fn run_server(
    bind: &str, port: u16, models_dir: PathBuf,
    gpu_selection: mold_core::types::GpuSelection, queue_size: usize,
) -> anyhow::Result<()>
```

Called from `crates/mold-cli/src/commands/serve.rs::run` (line 132). It re-arms SIGPIPE ignore, discovers GPUs (`mold_inference::device`), builds a per-GPU worker pool + tokio generation queue, opens the metadata DB (`mold_db::open_default`), spawns the chain-job runner, resource aggregator, download driver and idle-evictor, then `axum::serve` with graceful shutdown (SIGTERM or `POST /api/shutdown`). `queue_size` default is 600 (CLI). `logging::init_tracing` is also a public library helper the CLI uses. A Tauri backend could call `run_server` directly to host the same API in-process, or import the router builder.

### mold-core types reusable directly by a Tauri Rust backend

All of these derive `Serialize`/`Deserialize` (and utoipa `ToSchema`) and are the exact HTTP wire types — a Tauri backend depending on `mold-ai-core` reuses them verbatim:

- **Generation**: `GenerateRequest`, `GenerateResponse`, `ImageData`, `VideoData`, `OutputFormat`, `LoraWeight`, `LoraInfo`, `KeyframeCondition`, `TimeRange`, `Ltx2PipelineMode/SpatialUpscale/TemporalUpscale`, `Scheduler`, `DevicePlacement`, `GpuSelection`.
- **SSE**: `SseProgressEvent`, `SseCompleteEvent`, `SseErrorEvent`, `SseUpscaleCompleteEvent`.
- **Chain**: `ChainRequest`, `ChainStage`, `ChainResponse`, `ChainScript`, `ChainProgressEvent`, `SseChainCompleteEvent`, `ChainFailure`; `chain_job::{ChainJobSummary, ChainJobDetail, ChainJobStageDetail, ChainJobListing, CreateChainJobResponse, RetakeRequest, RetakeMode, ChainJobEvent, ChainJobState, StageState, GcOutcome, FinalizeRecord}`.
- **Status/telemetry/gallery**: `ServerStatus`, `ActiveGenerationStatus`, `GpuInfo`, `ResourceSnapshot`, `GpuSnapshot`, `RamSnapshot`, `CpuSnapshot`, `GpuBackend`, `GalleryImage`, `OutputMetadata`, `ServerCapabilities`/`GalleryCapabilities`/`CatalogCapabilities`, `GenerationMemoryEstimate`, `ModelInfo`, `ModelInfoExtended`, `ModelComponentsResponse`.
- **Expand/upscale/downloads/catalog**: `ExpandRequest`, `ExpandResponse`, `UpscaleRequest`, `UpscaleResponse`, `types::DownloadEvent`, `catalog_wire::{InstalledCatalogResponse, InstalledCatalogEntry, DownloadRecipeWire}`.
- Also `mold_core::client` is a ready-made HTTP client (already used by mold-discord/mold-tui) that a Tauri backend could reuse instead of hand-rolling requests.

A few wire structs live in **mold-server** (not reusable without depending on the server crate): `routes::{LoadModelBody, UnloadRequest, CreateDownloadBody, CreateDownloadResponse}`, `job_registry::{JobEntry, QueueListing, JobLifecycle}`, `chain_limits::ChainLimits`, and `catalog_api::CompanionJob`. These are simple enough to mirror if the Tauri backend only depends on `mold-core`.
