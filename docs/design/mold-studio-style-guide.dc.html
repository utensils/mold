Mold design system · GUI surfaces

mold studio
style guide

How the desktop app, the browser studio and the iPhone app are built: one structure, one vocabulary, six interchangeable themes. The Mold design system already documents the TUI and the marketing site — this covers the three GUI surfaces and the token work that lets them share a skin.

Scope: mold studio (desktop), the browser studio and mold for iPhone. The TUI is unchanged and out of scope.

01 · Principles

The TUI is for people who already live in a terminal. The GUI is for people who have never heard of a diffusion model. That one sentence decides most of what follows.

01Plain words in sans, technical truth in mono, on the same row. Never delete the jargon — demote it. "Detail · 28 passes", not "Steps: 28". 02One accent, one job. A theme has exactly one accent and it means "you can press this" or "this is happening now". Status hues are for status only. Never rainbow-ify a view. 03Structure is theme-invariant. A theme changes colour, type and radius. It never changes layout, information density, wording or the icon set. 04Every state is a sentence a first-timer can act on. "Adding detail — about 12s left", with the mono truth alongside for people who want it. 05The image gets the viewport. Work in progress is context, not content: the queue lives in the sidebar, never docked under the canvas. 06No component hard-codes a hex, a font or a radius. A new theme is added by extending the token map and nothing else — the rule the shipped app already holds itself to.

03 · Theme system

Six themes ship. A theme is a complete token map — surfaces, four text ranks, borders, status hues, two font families, a seven-step type scale, two leadings and a radius scale. Nothing else in the product varies with it, and all three surfaces carry byte-identical maps.

·The queue lives in the sidebar, under the machine card — not docked beneath the canvas. Work in progress is context; the image keeps the viewport. ·Fixed chrome never shrinks (flex-shrink:0); the canvas absorbs slack and clips, so nothing escapes its region. ·No floating popovers for primary controls. Starters are an inspector tab, not a hovering panel. Result actions live inside the image's caption strip, never as a pill overlapping it. ·The status bar answers "which machine, how full, how deep is the queue" so those questions never cost a view change. Keycaps sit right, mono, in the accent. ·Master/detail for infrastructure (Machines, Styles → Browse): 326px list plus a detail pane, both bordered.

Browser — fluid, 1120px column

·The browser owns the frame. No window chrome, no traffic lights, no app-drawn title. Back and forward are the browser's, so no view may trap the user inside a pane. ·Every view is a link. Scope, collection, tag and favourite state all live in the query string (?scope=&c=&tag=&fav=1). Copy link is a first-class action; the desktop app has nothing to copy. ·One scroll context, not four. The page scrolls; panes don't. The composer sticks to the bottom of the column so Generate is always reachable. ·The queue is a strip, not a rail — a sidebar queue would scroll away. A dismissible strip under the header, plus a header chip holding the live count. ·Modals are the third pane. Cropping, masking, picking a source, expanding a prompt and saving a starter open over the page; there is no room for a permanent inspector at most widths. ·Two kinds of background work, two chips. Making pictures and fetching a style are different jobs and keep separate counts. Under 900px both chips keep their count and drop their label. ·The connection is visible. A browser has no local GPU, so which machine the tab is talking to is stated plainly, with a way to change it.

iPhone — 393pt reference

·Five tabs: Make · Queue · Images · Styles · Machines. The queue is promoted out of Make into its own tab; Settings moves behind the gear rather than occupying a tab. ·The desktop inspector collapses into one "More settings" sheet — three quality presets first, then sliders, then a grouped list. Fourteen separate sheets became one. ·Tables become rows. 52–64pt rows, 44pt minimum hit targets, numbers in mono on the right, one sentence of status per item. ·Generate is a full-width 50pt button pinned above the tab bar — the only accent-filled element on the screen. ·Feature parity is absolute. Anything the desktop can do the phone can do, including 3-D objects, style licences and machine routing. Only the number of decisions per screen changes.

05 · The timeline

A clip made of several scenes is edited on a timeline, not in a list of parameters. The one contract that makes it a timeline rather than a strip of cards is that width is duration — break it and every other affordance becomes a lie.

·One shared geometry. The ruler, the scene lane, the sound lane and the playhead all derive from a single left inset and right inset. Nothing that is not time may consume width inside the track — no gaps, no add button, no trailing spacer. ·Length is dragged, not typed. The selected scene carries a full-height grip on its trailing edge. There is no frames field; seconds are the only unit a user sees. ·Transitions live on the seam as a labelled chip centred on the boundary — Smooth, Cut, Fade — with the teaching line on hover. They are pinned into a gutter above the lane so they never cover the trim grip; two affordances on one boundary must not share a vertical band. ·Each scene shows its own frame behind its sentence, under a scrim so legibility never depends on the picture. ·Transport states the whole, not the part — play, elapsed over total, one playhead crossing every lane. ·On a phone the same model becomes one column: a proportional-width strip you tap to jump, then scene rows with drag handles and −/+ steppers, transition chips between them.

07 · Type, icons, imagery, motion

TYPESans carries meaning, mono carries fact. Anything a user could read aloud as a sentence is sans; anything they would copy, compare or count is mono — filenames, model ids, durations, memory, money, seeds, keycaps. Tabular numerals always on. Weight is flat: 400 body, 500 controls, 600 titles and the CTA, 700 for the wordmark and table emphasis only. ICONSLucide-metric line icons — 24×24 viewBox, 2px stroke, round caps and joins, currentColor. 18px in nav, 17px in the toolbar, 13–14px inline, 20–23px on iOS. If an icon is missing, substitute from Lucide at the same weight and flag it. The icon set never varies by theme. No emoji, ever. IMAGERYEvery image surface shows a real picture — the canvas result, the in-progress thumbnail (1.2–1.6px blur so it reads as mid-render), queue rows, library tiles, starters. A bordered empty box is correct only for a job whose image does not exist yet, and then it carries its queue position as a mono glyph. MOTIONMechanical, no bounce. The braille spinner becomes a 1s two-step opacity pulse on live glyphs and status dots. Meters jump, they never tween. View switches are instant. Transitions are for hover colour only, at 120ms.

08 · Contrast & fit

Six themes across three surfaces means a control that fits in one face can wrap in another. These are checks, not opinions — run them against every theme before shipping a screen. Contrast is measured against the lowest-contrast surface a rank appears on, never the base background. Which surface that is flips with the theme: in a dark theme it is --mold-surface (the lightest step); in a light theme it is --mold-bg-crust (the darkest). Test the rank against every surface it touches and take the worst number.

✓Accent-filled text clears 4.5:1 against its ink in every theme. The ink is --mold-bg-deep on dark themes and the lightest surface on light ones — never white by reflex. ✓No control wraps in any theme. Measure scrollWidth against clientWidth on every label in the densest and the widest face — Blueprint and Nebula are the two extremes. ✓A saturated row has a real spacer. If a flex:1 spacer measures 0px at rest, the row is over capacity — move something out rather than letting one child ellipsis. ✓Nothing overlaps. Floating overlays that straddle a caption or a toolbar are a layout bug; fold them into the bar they collide with. ✓--mold-text-faint is decorative only. It lands between 2.3:1 and 3.4:1 depending on theme, so nothing a person has to read may use it. Placeholder copy — the composer included — is --mold-text-dim (5.2:1 or better in every theme); text-faint is for disabled glyphs and thumbnail mocks. ✓Repeated cards pin their variable text to a min-height so a shorter one cannot pull its neighbours out of alignment. ✓iOS hit targets are never below 44pt, and desktop text never below 11px. ✓The faint rank is the one deliberate exemption. --mold-text-faint sits at 2.3–3.4:1 by design — it marks placeholder and disabled text only, and must never carry information a user has to read. Everything else clears 4.5:1.

09 · Adding a theme

01Add one entry to the theme list: id, name, tone, type pairing, accent, and a token map declaring every key in §03. Partial maps inherit stale values. 02Load the two font families. Restate all seven size steps and both leadings — a wide or a serif face needs a different scale to hold the same density. 03Declare the radius scale explicitly, even when it is the default 2/4/6. 04Mirror the entry on all three surfaces. Desktop, web and iPhone each carry the same token map and it must be byte-identical across them — anything else is drift. The web studio ships the full set like the others; only the review mock pins one theme (Mocha) inline, so the browser frames stay comparable against the desktop picker. 05Run §08 against the new theme before it ships.

Touch no component. If a new theme requires a markup change, the markup was wrong — fix it for all six.

One deliberate deviation from the base system: Mocha’s dim rank is lifted from the #7f849c that mold-tokens.css ships, and Safelight’s from its ink-3 mix, so both clear 4.5:1 on --mold-surface. The TUI values are unchanged; this applies to the GUI surfaces only.
