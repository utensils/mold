# Native Library bulk-operation responsiveness

## Evidence and root cause

On 2026-09-26 the installed native 0.31.1-nightly.1418 app showed timeout banners for This Mac and plato after selecting roughly 3,749 prints and moving them to trash. A live process sample at 11:10 Phoenix time showed the main thread idle in AppKit's event loop while a Rust blocking worker was still executing `trash_print_blocking`, including archive snapshot serialization/commits. Logs identify the external-volume gallery and 3,743 live rows at startup. This is an HTTP operation timeout and gallery starvation, not evidence of a main-thread hang.

The native store sends every owning host's filenames as one request. The server correctly uses `spawn_blocking`, but holds the gallery publication writer across the entire list and buffers events until the list finishes. Every archived print also commits a durable authority snapshot. A large request exceeds the ordinary JSON timeout, blocks gallery readers, and continues running after the client times out. The client then restores its whole pre-operation host snapshot, hiding successful partial work. There is no visible status for trash/restore/delete or organization edits. Per-file events also rebuild the merged library even when they remove nothing.

## Implementation

1. Keep filesystem/database work on the Rust blocking pool. Process trash in bounded chunks with one archive-authority commit per chunk instead of one full snapshot per print. Restore and purge retain per-item durable commits and release the gate after each item: authority-before-rename on restore and irreversible unlink/pin release on purge require a new durable completion journal before batching safely. This larger throughput optimization is deferred; these paths gain responsiveness, fairness and visible progress. The legacy empty-trash endpoint also releases between items. Preserve tombstone/row ordering, exact identities, partial-failure semantics and crash recovery, rolling back pre-commit moves where needed. Release the gate between chunks so waiting readers and other work can advance. Move each owned writer into its blocking closure: disconnecting a request must not release the gate while that closure still mutates authority. Publish events after each durable trash chunk or restore/purge item before starting the next; preserve stop-at-first-failure and existing crash/identity protections. Add operation logs with requested/completed counts and elapsed time. Do not weaken durable authority commits.
2. Native destructive operations use bounded batches, sequentially per host, with a mutation-specific timeout. Remove only acknowledged trash rows; on uncertain/partial failure invalidate listings and reconcile from the host, never restore an entire stale snapshot. Freeze host/backend identity, guard replies against host edits/removal, and prevent overlapping destructive operations.
3. Show a persistent Library status bar immediately, with verb, machine, completed/total physical copies, current work and a stop-after-current-batch control. Cover trash, restore, permanent delete, and empty trash. Empty Trash uses the server's trash-only empty endpoint, with per-machine progress and stop after the current machine. Enumerating names into the mixed live/trash delete endpoint is unsafe: a concurrently restored print or a stale listing could cause deletion of a live print. The same Library status surface covers multi-file Import, Save to folder, fleet-wide tag rename/delete and organization outbox work (favorites, tags, collections, title, undo), including retries/give-up; preserve retry and undo behavior. Local-save status remains available. Retain completion/failure feedback and clearly distinguish uncertain requests from confirmed completion.
4. Skip no-op live removal rebuilds; reconcile at batch boundaries rather than introducing repeated full-list scans for own events.
5. Add regression tests for batch bounds, live progress while requests await, stop boundaries, partial failure reconciliation, cross-host copies, host replacement/removal and organization status. Server tests prove bounded trash chunks perform one authority commit, readers advance between trash chunks and restore/purge items and a dropped waiter cannot overlap an in-flight blocking mutation. Run native lint/tests, MoldClient tests, Rust targeted tests and relevant CI gates. Verify with a disposable gallery, never repeat destructive UAT against the user's real media.

A follow-up review approved optimizing trash authority while retaining safe per-item restore/purge commits: batching those transitions requires a separate durable journal. Copy/Quick Look are capped previews and upscale is single-selection; queued generation has its existing Queue status. Stop never cancels in-flight mutations. Failed HTTP chunks carry unknown outcomes and require both authoritative listings.

Implementation review found and corrected a restored-print race in per-item empty/sweep and an unsafe native empty-trash snapshot. Server purges revalidate trash membership/expiry under the writer; native empty uses the trash-only endpoint, with honest machine-level status/stop instead of filename batching.
