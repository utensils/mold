# CLAUDE.md

Guidance for Claude Code working in this repo. Keep lean: only things not obvious from the code, `--help`, or `git log`.

## What mold is

Local AI image/video generation CLI built on [candle](https://github.com/huggingface/candle). Supports FLUX, SD1.5, SDXL, SD3.5, Z-Image, Flux.2 Klein and Dev, Qwen-Image, Wuerstchen v2, LTX-Video, and LTX-2. Runs locally on GPU or talks to a remote `mold serve` over HTTP. Single binary, everything feature-gated.

Desktop gallery authority is singular: while its local server is running or its lifecycle is unresolved, native list/save/delete/media paths use authenticated HTTP (ticketed for media elements). Direct filesystem access is allowed only while the lifecycle mutex proves `LocalServer::Off`.

## Commands

```bash
# Nix (preferred)
nix build                   # Build mold (default CUDA/Metal)
nix fmt                     # treefmt (nixfmt + rustfmt)
nix flake check             # CI-equivalent gate

# Cargo — common loops
cargo check                                                                    # type check
cargo clippy --workspace --all-targets -- -D warnings                          # what CI runs

cargo test --workspace                                                         # what CI runs
cargo check -p mold-ai --features preview,discord,expand,tui,webp,mp4         # what CI also runs
./scripts/coverage.sh [--html]                                                 # coverage

# Local dev run (MUST prefix with ensure-web-dist so the embedded SPA isn't a stub)
./scripts/ensure-web-dist.sh && cargo run --profile dev-fast -p mold-ai \
  --features metal,preview,expand -- run "a cat"
```

Inside `nix develop` the devshell exposes shortcuts (`build`, `build-release`, `serve`, `mold`, `clippy`, `run-tests`, `coverage`, `fmt`). Run `type <cmd>` to see the underlying invocation.

**CI gates** (`.github/workflows/ci.yml`): `rust` (fmt + check + clippy-deny-warnings + test + feature-combo check), `cuda-check` and `metal-check` (forced-local + server typechecks for their respective GPU backends), `coverage` (cargo-llvm-cov → Codecov), `web` (architecture + dead-code + Studio/web tests, formatting, and build), `docs` (`bun run fmt:check && bun run verify && bun run build` in `website/`), and a path-gated `release` check for release-plz synchronization scripts. All triggered gates must pass.

**Desktop updater:** signed release builds support persisted **Stable** and **Nightly** channels. Startup and menu/Settings checks are check-only; an available update is announced in persistent app chrome and by a native notification while backgrounded, and installation requires the user's explicit **Update and restart** action. Stable reads the public `mold-desktop-stable.json` manifest from the latest tagged release; Nightly reads `mold-desktop-nightly.json` from the rolling `latest` prerelease, which `.github/workflows/desktop.yml` rebuilds only after the frontend and Rust gates pass for a desktop-relevant `main` commit. Before touching the installed app, Tauri verifies the Minisign signature and Mold fully extracts the archive to temporary storage, binds its bundle ID/version to the manifest, runs strict Apple code-signature and Gatekeeper checks, validates the current app identity and install location, and proves the app's parent directory is replaceable. Only then does Mold atomically exchange the staged and installed bundles with macOS `RENAME_SWAP` and restart. There is deliberately no post-launch watchdog, probation, or Mold-owned rollback; the update either passes preflight and installs or fails while the running version remains in place. Do not add a silent downgrade comparator: selecting Stable from a newer Nightly waits for a later stable version. Distribution CI requires `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in addition to the Apple signing/notarization secrets, verifies signatures against the checked-in public key, and retains ten Nightly desktop generations. The updater private key must have controlled offline backup and must never enter the repo or logs; losing it strands installed clients, and rotation must first be delivered by an update signed with the existing key.

**Desktop model-library invariant:** the Installed shelf and download progress are all-connected-host views, host detail mirrors the selected host's pulls, and built-in manifest variants take precedence over ambiguous multi-checkpoint Hugging Face repositories so a Pull targets one runnable model rather than an aggregate repository. Remembered hosts in `connectedHostIds` are attempted immediately on launch in parallel with This Mac; an explicitly disconnected host stays remembered but is excluded from reconnects and every all-host operation until the user reconnects it.

**Command-palette model-search invariant:** the ⌘K palette on web and desktop searches the whole fleet, and every model row's wording and destination derives from `planModelInstall` plus `studio/lib/modelSearch.ts` — never a second policy. Installed rows are the union across ready machines (web's additive `HostRouting.installedModels`, desktop's `models.installed` merged with `hostModels.unionInstalled`), so a model is never hidden because the pinned target lacks it. `resolveModelHost` repins the generation target ONLY for an explicitly pinned target that lacks the model; automatic routing (web `auto`/`capable`, desktop `null`/`capable`) is already model-aware and must stay untouched. Not-installed rows come from a debounced live catalog search restricted to checkpoints, drop unsupported entries and anything the fleet already has (matched on both catalog id and server-reported name), stay appended in the server's relevance order behind the panel's `busy` indicator, and discard responses for abandoned queries via a monotonic epoch. Palette installs deliberately take the plan's first target and name it in the toast instead of opening the machine picker — that dialog is mounted by the Models page and would be invisible from any other route. Load/unload rows stay scoped to the primary; they act on this machine's GPU, not on whichever machine holds the weights.

**Model install-target invariant:** a Models row is merged across machines, so `installed` means "installed somewhere" and never "installed here". Web, desktop, and iPhone derive the row's action from `planModelInstall` in `studio/lib/modelInstallTargets.ts`: every reachable machine that lacks the model stays an install target, owners degrade to repair, and the action collapses to Repair only once every reachable machine has it. Never hide the install because some other machine has the model. A machine whose `/api/models` has not been read is not evidence of absence and is never offered as an install target on desktop or web; the host picker always names the per-machine outcome so a mixed fleet is unambiguous. Both download routes are strict about id shape — `/api/downloads` takes manifest names and `/api/catalog/:id/download` takes `cv:`/`hf:` ids, each rejecting the other — so every install path must route on the id, not on the calling surface.

## Non-obvious architectural patterns

Most are in `mold-inference`. When touching engines, these are the rules that matter:

- **Lazy load** — engines load on first `generate()`, not startup. Most hold mmap'd safetensors.
- **Drop-and-reload text encoders** — T5/CLIP/Qwen3 are dropped from GPU after encoding so the transformer has VRAM to denoise, then reloaded next request.
- **Dynamic device placement** — text encoders go to GPU or CPU based on remaining VRAM after the transformer loads (thresholds: `device.rs`).
- **Quantized encoder auto-fallback** — when FP16/BF16 doesn't fit, the largest GGUF variant that fits is auto-selected. Override: `--t5-variant` / `--qwen3-variant` / `--qwen2-variant` or `MOLD_*_VARIANT`.
- **Block-level offloading** (FLUX) — `flux/offload.rs` streams transformer blocks CPU↔GPU one at a time: ~24 GB → 2–4 GB VRAM, 3–5× slower. Auto-enabled under pressure; force with `--offload` / `MOLD_OFFLOAD=1`.
- **LoRA backend is custom** — candle has no LoRA. BF16 path: `LoraBackend` (a `SimpleBackend`) intercepts `vb.get()` during model construction and applies `W' = W + scale·(B @ A)` inline. GGUF path: `gguf_lora_var_builder()` selectively dequantizes affected tensors, merges, re-quantizes. Both work with offloading. See `flux/lora.rs`.
- **LoRA caching** — `LoraDeltaCache` (pre-computed `B @ A · scale` on CPU, ~80–120 MB) survives transformer rebuilds. `LoraFingerprint` on `FluxEngine` skips redundant rebuilds when the same LoRA/scale reappears.
- **Shared tokenizer pool** — `shared_pool.rs`: `Arc<Tokenizer>` keyed by file path, shared across engines via `create_engine_with_pool()`. Saves ~100–150 ms on model swap for FLUX variants.
- **CPU-based noise** — `seeded_randn()` in `engine.rs` generates initial noise on CPU via `StdRng`/ChaCha20, then moves to GPU. This is load-bearing for cross-backend seed determinism (CUDA/Metal/CPU produce identical images).
- **Placement preview is an authority boundary** — `POST /api/generate/placement-preview` is read-only and authoritative only for ordinary-generation plans the server can admit. Prepared clients preview the finalized sibling shape after source preprocessing and fence URL, API key, and instance identity. An authoritative `infeasible` response may carry additive `missing_components`; a `planned` response may carry additive `pending_downloads` for known encoder dependencies that admission will materialize. Pending previews use a distinct registry-identity fingerprint domain, never start downloads, report low estimate confidence only when a device selected by that candidate plan has pending artifacts, and are recomputed from landed bytes at admission. Cold installed `cv:`/`hf:` IDs resolve only from contained local sidecars; the synthesized model config travels with prepared work through coordinator planning and pre-CUDA validation so config refreshes cannot erase its authority. Clients still queue nothing on infeasible and must not promise repair/resume without exact-host grouped download ownership. A strictly valid version-1 non-authoritative `unsupported` response or legacy `404`/`405` may retain compatible routing; every other HTTP, malformed response, or exhausted transient retry queues nothing. Chain and local prompt-expansion/post-generation-upscale utility previews remain non-authoritative `unsupported` until their real CPU/GPU paths are modeled. Probes redact prompts/media but retain server-local LoRA paths needed for feasibility.
- **Frozen execution plans remain authoritative at worker dispatch.** Scheduler admission owns the family-specific estimate, placement, load strategy, offload mode, and safety policy. A worker may re-sample physical memory and reject the exact `predicted_vram_peak_bytes` if pressure changed, but it must not replace that demand with the legacy path-based resident-model estimator. Apply the recheck to fresh loads, parked reloads, and reconstructed engines; unchanged CUDA hot-cache hits may recheck only when fresh, nonzero Mold-process VRAM attribution can bound the global, potentially stale cache delta. Ambiguous zero/missing attribution in containers, MIG, Metal, or WSL2 retains the scheduler's validated grant rather than double-counting resident weights. CUDA rechecks again after dropping replaced state, while Metal retains its unified-memory single gate.
- **Learned scheduling separates setup from execution** — typed cold-load, warm-reload, prompt-encode, denoise, VAE, and upscale phases feed metadata schema v15's independent runtime EWMA. Planning adds exactly the selected cold or warm setup disposition. All client device panels render every advertised device and expose live mutation only under authoritative V2; read-only modes may expose only the supported restart-enable recovery. Queue plans classify non-device work with `planned_lane_kind`; clients never infer lane semantics from opaque `planned_device_id` strings, and the capacity-one host utility lane keeps `planned_device_id = null`.
- **Batch capability is static before engine load** — `mold-inference` owns one registry for every production family and factory alias; tests construct every advertised name and engine construction fails closed if the runtime contract differs. Production generation families currently declare only native size `[1]`. `mold-scheduler` prioritizes real initial-wave cardinality, solves homogeneous singleton fleets exactly at arbitrary size, and solves host-coupled heterogeneous singleton inputs exactly through 8 devices at arbitrary child count. Singleton plans retain one arithmetic lane per selected device with typed random access and bounded 4096-record windows; they do not materialize one record per child. Ordinary native inputs use the deterministic 64-strategy bounded fallback, while huge native parents visibly fall back to the mandatory compact singleton plan as `BoundedHeuristic`. Raw server `batch_size > 1` is routed as ordered singleton children only when Scheduler V2 is authoritative and gallery output is enabled; `/api/capabilities.queue.server_batch` advertises exactly that conjunction and remains false otherwise. No engine is represented as returning multiple native outputs.
- **Fatal CUDA contexts are never reused or reset in-process** — illegal-address, uncorrectable-ECC, launch-failure/assert, and related faults permanently quarantine that worker and stop the server with an error so service supervision can restart the process; the embedded desktop must relaunch the whole app. Apply this to normal jobs, durable chains, admin loads, and post-upscalers, and reject buffered jobs before touching CUDA. In-process `cuDevicePrimaryCtxReset_v2` is unsafe while Candle/cudarc objects may retain primary-context handles; do not downgrade fatal errors to the timed cooldown. Quantized Qwen edit keeps split CFG even on high-VRAM CUDA cards.
- **Z-Image has a bespoke quantized transformer** — `zimage/quantized_transformer.rs` lives here (not candle); GGUF tensor naming differs from BF16 (`attention.qkv` vs split Q/K/V, etc.).
- **LTX-2's source of truth is upstream, not this repo.** <https://github.com/Lightricks/LTX-2> is the reference implementation for every LTX / LTX-2 / LTX-2.3 question — sampling schedules, guidance, conditioning, VAE tiling, block streaming, quantization policy, and prompt semantics. Before changing an LTX engine or arguing about correct behaviour, read upstream rather than inferring intent from mold's port. Clone it to a scratch location and pull before consulting it (the repo moves fast; `packages/ltx-core` is the inference core and `packages/ltx-pipelines` holds the pipeline drivers plus the documented CLI flags). Keep the clone out of the worktree — `tmp/` is gitignored and is where the existing checkout lives. Cite upstream `file:line` when a change is justified by it. Note upstream's own consumer-GPU guidance is `--offload {cpu,disk}` plus `--quantization fp8-cast`; heavy block streaming is the intended way a 19B checkpoint fits a 24 GB card, not a failure mode.
- **LTX-2 is CUDA-only for real generation.** CPU is correctness-only; Metal is unsupported. Native runtime lives in `ltx2/` with its own media pipeline (MP4 first, real AAC).
- **LTX-2 runtime-asset bundling is mixed.** Catalog checkpoints may be combined or transformer-only; resolve `ltx2-vae` for v2 and `ltx2.3-vae` for v2.3. Diffusion-only LTX-2.3 exports also require `ltx2.3-text-projection`. Preserve those concrete paths in every chain-stage plan. Catalog checkpoints without a bundled spatial upscaler default to the chain-capable one-stage pipeline even though their stable `cv:` / `hf:` IDs do not contain `distilled`; UI eligibility and chain-limit lookup must use that invariant rather than parsing a pipeline label from the opaque ID. ConvRot W4A4 checkpoints use the dedicated `ltx2/convrot.rs` compatibility backend. A Gemma prompt-encoder OOM may move only Gemma to CPU; preserve the transformer and video VAE CUDA device through the retry.
- **LTX-2's frame ceiling is a duration, never a frame count.** The checkpoints ship `pos_embed_max_pos = 20` and `ltx2/model/rope.rs`'s `scale_video_time_to_seconds` normalizes the temporal RoPE axis in _seconds_, so the budget is 20 s of runtime: `frames <= LTX2_MAX_RUNTIME_SECONDS * fps + 4`, clamped by `LTX2_MAX_FRAMES_ABSOLUTE`. Derive it through `mold_core::validation::ltx2_max_frames_at_fps` / `studio/lib/videoBudget.ts` on every surface; a hard-coded scalar is wrong in both directions (too strict at 24 fps, too lax at 6). `/api/models` advertises `max_frames` at the model's own fps plus additive `max_runtime_seconds` / `max_frames_absolute`, and `/api/capabilities/chain-limits` takes `?fps=` and echoes what it used. A chain clip is one generation, so its per-clip cap is the same budget — 97 survives only as the auto-chaining _routing_ default (`LTX2_DEFAULT_CLIP_FRAMES`) that fits one consumer GPU, and `--clip-frames` clamps to the real budget. `--temporal-upscale x2` buys temporal resolution, not duration: `derive_stage1_render_shape` halves the stage-1 frame count _and_ fps.
- **Extend is the chain motion-tail handoff with a file-backed carryover.** `GenerateRequest.extend_video` / `extend_video_path` continue an existing clip in one request: the last `extend_overlap_frames` pixel frames are re-encoded through the video VAE as conditioning, `Ltx2Engine::extend_inner` routes through the existing `render_chain_stage`, and `stitch_extend_frames` drops the render's leading overlap (a duplicate of the tail) before appending. The overlap must be `8k+1` and strictly below `frames`, so a continuation always adds at least one frame. Extend is mutually exclusive with `source_video`, `source_image`, and keyframes, and it requires the render to match the source clip's resolution and fps — never rescale mid-video. Per-model additive `/api/models[].supports_extend` + `extend_default_overlap_frames` is the single capability source; clients derive everything from `studio/lib/extend.ts` and hide the control when the field is absent.
- **LTX-2 generated-audio support is checkpoint-specific.** A runnable video checkpoint may omit the audio VAE and vocoder. Derive additive `/api/models[].supports_audio` from safetensors headers, keep video generation available when false, and reject explicit audio output before prompt encoding or denoising.
- **Tier 1 perf knobs** (`MOLD_KEEP_TE_RAM`, `MOLD_LORA_BYPASS`, `MOLD_VAE_TILED`, `MOLD_ATTN`) are documented in `website/guide/configuration.md` and `.claude/skills/mold/SKILL.md`. Don't repeat their semantics here — they're opt-in / auto-on knobs that surface in those tables and in `[Unreleased]` of `CHANGELOG.md`.

## Inference modes (`mold run`)

1. **Remote** (default) — HTTP to `$MOLD_HOST` (default `http://localhost:7680`).
2. **Local fallback** — server unreachable → local GPU (auto-pulls model if missing).
3. **Forced local** — `--local` skips the server attempt.

`mold run [MODEL] [PROMPT]` disambiguates the first positional at runtime: matches a known model name → model, otherwise → prompt.

**Pipe-friendly**: `echo "a cat" | mold run flux2-klein | viu -`. stdin for prompt, stdout for image bytes when not a TTY. `--output -` forces stdout; `--image -` reads source from stdin. `IsTerminal` detection + SIGPIPE reset to default + `status!` macro route text to stderr.

**Name resolution** (`manifest::resolve_model_name`): `model:tag` (e.g. `flux-dev:q4`); bare names try `:q8` → `:fp16` → `:bf16` → `:fp8`; legacy dash `flux-dev-q4` resolves to colon form.

## Multi-prompt chain authoring

- `mold run --script shot.toml` — canonical TOML, schema `mold.chain.v1`. Per-stage `prompt` / `frames` / `transition`.
- `mold chain validate shot.toml` or `mold run --script ... --dry-run` to inspect without submitting.
- Sugar: `mold run <model> --prompt "..." --prompt "..." --frames-per-clip 97` (uniform smooth only).
- Transitions: `smooth` (default, motion-tail morph), `cut` (fresh latent), `fade` (cut + RGB crossfade).
- Per-stage source images: `source_image_path` (relative to script file) or `source_image_b64`. Resolved by `mold_core::chain_toml::read_script_resolving_paths`.

## Config

Two stores, one logical `Config` view:

| Surface                                                              | Owns                                                                                     |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `~/.config/mold/config.toml` (XDG) or `~/.mold/config.toml` (legacy) | Bootstrap: paths, ports, credentials, `[logging]`, `[runpod]`, per-model component paths |
| `mold.db` `settings` + `model_prefs`                                 | User prefs: `expand.*`, `generate.*`, `tui.*`, per-model defaults                        |
| `MOLD_*` env vars                                                    | Runtime override (highest precedence)                                                    |

Every `main()` calls `mold_db::config_sync::install_config_post_load_hook()`, which runs a one-shot idempotent `config.toml → DB` migration on first boot (renames original to `config.toml.migrated`) and overlays DB onto every `Config::load_or_default()`. Consumers still read `cfg.expand.*` unchanged.

`mold config set <key> <val>` routes by key prefix (`expand.*` → DB, `models_dir` → TOML). `mold config where <key>` prints the surface. `mold config list --json` tags each row `[db]` / `[file]` / `[env]`. Multi-profile: `settings` and `model_prefs` are keyed on `(profile, key)`; active profile resolves `MOLD_PROFILE` → `settings.profile.active` → `"default"`.

## Metadata DB

`MOLD_HOME/mold.db` (override: `MOLD_DB_PATH`; disable: `MOLD_DB_DISABLE=1`). Current `SCHEMA_VERSION` lives in `crates/mold-db/src/migrations.rs`. Tables: `generations` (gallery rows), `settings` (KV, profile-scoped), `model_prefs` (per-resolved-model generation params, profile-scoped), `prompt_history`, and machine-wide `device_preferences` (absent row = enabled by default; discovery never writes). Migrations are forward-only via `PRAGMA user_version`; add to `MIGRATIONS[]` and bump `SCHEMA_VERSION`.

Gallery writes happen in the server (`queue.rs` upserts after disk write; background `reconcile(output_dir)` on startup), CLI (`crates/mold-cli/src/metadata_db.rs` via `record_local_save`), and TUI (`gallery_scan.rs`). DB is additive — embedded PNG/JPEG `mold:parameters` still get written, and open/upsert failures log and keep working. Open-time `quick_check` and query-time gallery corruption recovery quarantine `mold.db` plus WAL/SHM as `mold.db.corrupt-<timestamp>*` under a cross-process recovery lock, recreate the schema, and reconcile gallery rows from disk; the retained quarantine is the only source for manually salvaging settings/history.

## Web UI

The frontend is one private repo-root Bun workspace with exact dependencies and one `bun.lock` / generated `bun.nix`. `ui/` owns visual tokens and low-level Vue primitives; browser-safe `studio/` owns explicit-target HTTP contracts, platform adapters, Pinia state, and shared domain logic; `web/` and `desktop/` are surface shells. Install at the repo root and use `bun run build:web`, `bun run build:desktop`, or `bun run build:mobile`; `frontend-bun-lock` refreshes both root dependency artifacts. `studio/` must never import Tauri or either application shell, and native compatibility normalization remains in `desktop/`.

The SPA in `web/` uses Vue 3, Pinia, Vite 7, and Tailwind v4. It is embedded into the `mold` binary at compile time via `rust-embed`. `crates/mold-server/build.rs` resolves the bundle from `$MOLD_WEB_DIST` → `web/dist` → a placeholder stub (detected at runtime and swapped for an inline page). The devshell `build`/`serve`/`generate` commands run `./scripts/ensure-web-dist.sh` first, so dev builds ship the real SPA. `MOLD_WEB_DIR` still overrides the embedded bundle at runtime for hot iteration.

The web IA uses Create (`/create`, also the `/` default), Library (`/library`), Models (`/models`), Machines (`/machines` + `/machines/:id`), and Settings (`/settings`). Library's grid toolbar carries the shared persisted Lightroom-style thumbnail-size slider at tablet width and above. Retired `/generate` and `/catalog` paths and all unmatched URLs render Page Not Found. Web accepts only the current storage and server wire shapes; an incompatible remote surfaces an actionable upgrade error. Create model selectors render catalog-provided descriptions for `cv:` / `hf:` entries but preserve those stable ids as form and request values; desktop follows the same rule. Sub-640px swaps the nav pills for a hamburger + bottom nav sheet. The shell owns a ⌘K palette, a downloads center, and app-frame toasts/dialogs (never `window.alert/confirm/prompt`). Per-surface Advanced policy (spec §06 surface split): web at ≥ tablet width is the power surface — Advanced renders inline in the Create controls region as always-open icon-led groups (count badge + Reset kept); mobile web keeps the same groups in its sheet; desktop keeps the simplified inspector by default and reveals those groups inline only when its Advanced toggle is on. Web Machines is browser-side multi-host: a localStorage host registry (`mold.web.hosts.v1`, origin always primary, instance-UUID dedupe) with per-host `x-api-key` headers — keys never in URLs. Its Local network flow is server-assisted: only when the primary reports `discovery.can_browse` does the browser request `GET /api/discovery/peers`, filter remembered instance UUIDs, then test-connect directly to the peer before saving; older servers are never probed. The results reflect the primary server's LAN and do not proxy traffic. Theme families persist at `mold.web.theme.v1` and apply before first paint via the inline `index.html` script. Web Settings stores Hugging Face and Civitai credentials on the serving host in owner-only `$MOLD_HOME/catalog-credentials.json`; the browser receives masked status only. Saved credentials override `HF_TOKEN` / `CIVITAI_TOKEN` defaults, and clearing a saved value returns to the environment fallback.

Sequence mode on web, desktop, and iPhone filters the picker to chain-capable installed video models and auto-selects one when available; its browse action deep-links into Discover with Video + Models filters. Explicit sequences start as two required clips, use Continue motion / Cut / Crossfade user-facing labels for context-capable LTX-2, and label LTX-Video's zero-tail fallback Join. Clip-duration choices must remain strictly greater than the active motion tail. **Validate plan** on all three Studio surfaces calls the selected authenticated host's read-only `POST /api/generate/chain/validate`, renders normalized stages/warnings/optional VRAM, creates no job, and discards a response if the draft changes in flight. Durable sequence creation, authenticated events or polling, previews, and job actions must stay on the selected host; iPhone persistence records host identity and job ID while the API key remains Keychain-only, and a saved instance identity must match exactly before recovery reattaches. Every LTX-2 pipeline renders sequence clips, two-stage included, and `/api/models[].supports_sequence` advertises that per model so pickers stop inferring it from the checkpoint name; `POST /api/generate/chain/validate` returns an advisory `vram_estimate` that is the max over stages, never their sum, and must never gate submission. Chain/job/action plus catalog-download failures remain visible in the interface.

**Activity-is-present-tense invariant (spec G15):** the Create activity strip renders only in-flight prints and sequences, plus at most `MAX_ATTENTION_ROWS` (2) dismissible failed/interrupted rows that expire after `SETTLED_VISIBLE_MS` (5 min) measured against server truth (`updated_at_unix_ms` for sequences, a client settle stamp for prints), plus one digest chip counting the settled sequences it is not listing, deep-linking to `/library?panel=history&tab=sequences`. Never render completed or cancelled rows there, never persist the dismissal set (the age rule already survives restart), and keep dismiss client-side — `Clear inactive` is a server `DELETE` and the two must not converge. `Clear inactive` and `Clean up disk` live only in the History ▸ Sequences footer, host-scoped and behind a confirm that names the host and count. The settled sequence resolves to three homes: the canvas (with **Edit sequence** / **Show in library** — settling must never blank it), the print in the Library, and the job in Library ▸ History ▸ Sequences (`HISTORY_JOBS_RENDER_CAP` 200, fetched on open because chain polling stops when nothing is active). The sidebar's **Now developing** shows running sequences with their clip counter but never settled ones. All of this derives from `partitionActivity` / `activityDigestLabel` in `studio/lib/activity.ts`; `ActivityJobVM.createdAtMs` must stay a real wall clock (it was a `clientId` counter, which sank every print below every sequence). History ▸ Sequences is deliberately out of scope on iPhone.

**Sequence-reuse invariant (spec §06):** a print stitched from a sequence is identified by saved provenance (`metadata.chain`, plus `metadata.chain_job_id` when a durable job produced it) and everything derives from `studio/lib/sequenceReuse.ts` — never a second clip loader. **Reuse settings** is one sequence-aware button: a legacy/still print keeps today's One shot restore, a sequence print loads `planSequenceReuse`'s clips into the shared draft as a NEW draft (no `editing` session) on `/create?output=sequence`, and it must never surface `metadata.prompt`, which for a sequence is every clip newline-joined. Per-clip seeds are never applied (the wire carries a `seed_offset`; deriving one from an effective u64 is guesswork), the recorded negative lands on clip 1 only, and `chain.motion_tail_frames` is validation-only — clips are always re-clamped with `clampClipsToMotionTail` against the LIVE model's tail, and any raise is disclosed, never silent. **Edit sequence** is the second, distinct action: desktop and web only, gated by `sequenceEditAvailability` on positive knowledge only (hide it when the origin host's loaded listing lacks the id; show it when the listing is unloaded), resolved ONLY from the entry's own origin bucket — never a sibling in `availableOn`, which holds auto-saved copies. It is checked once on click; `404` falls back to reuse with a toast naming the host, an unreachable host errors and changes nothing (a silent downgrade would discard cached clips), and `200` hands into the EXISTING `editSequence` path (`normalizeServerChainScript` → `chainScriptToClips` → `draft.loadFromJob`). iPhone is reuse-only until it has a chain-detail recovery route, and its model substitution must pick a sequence-capable model.

**Gallery delete is always enabled.** `DELETE /api/gallery/image/:filename` is a destructive endpoint — pair with `MOLD_API_KEY` when the server is exposed beyond localhost. `GET /api/capabilities` still returns `{ gallery: { can_delete: true } }` so older clients keep a stable shape.

## Workflow

- **TDD.** Every bug fix and feature: failing test first, then code. Prefer unit tests on exported contracts (key→action maps, focus transitions, serialization round-trips, layout invariants) over E2E. Layout constants need a test that asserts the inner area fits the rendered row count — otherwise they drift.
- **Keep user and agent docs in sync with every feature:** `CHANGELOG.md` (Keep-a-Changelog format, under `[Unreleased]`), `README.md`, this file (`AGENTS.md` is its symlink), canonical `.claude/skills/mold/SKILL.md`, the owning app README such as `apps/mobile/README.md`, relevant `desktop/docs/`, and the VitePress `website/` pages/navigation. Model, CLI flag, env-var, endpoint, and native UI changes are incomplete until every affected surface agrees; do not maintain a divergent second agent-skill copy.
- **Releases are automated by release-plz** (`release-plz.toml`, `.github/workflows/release-plz.yml`). Every push to `main` maintains a release PR: release-plz bumps the shared `[workspace.package]` version (conventional commits decide the bump; `feat:` ⇒ minor on 0.x), then a scripted bot commit (`scripts/release/sync-release-pr.sh`) promotes `CHANGELOG.md` `[Unreleased]`, syncs the desktop cargo root's version, and copies the promoted notes into the PR body — never bump versions or promote the changelog by hand. Merging the release PR makes the next `release-plz-release` run push the `vX.Y.Z` tag, which fans out to release.yml (binaries + signed/notarized desktop DMG via `desktop-distribution.yml` + GitHub release + crates.io + AUR) and FlakeHub. Public binary/crate/AUR publication remains downstream of the complete sm80/sm86/sm89/sm90/sm100/sm120 GHCR matrix and hosted `mold-sm86`/`mold-sm100`/`mold-desktop-sm86` Nix builds. Main publishes mutable rolling `latest*` image aliases. Stable `<version>*` aliases are create-once and verified, but automatic Lambda/RunPod/desktop provisioning must consume the release's exact `mold-container-digests.json` `@sha256` reference and fail closed if it is unavailable or inconsistent. Both workflow jobs authenticate as the `release-plz-mold` GitHub App (`RELEASE_PLZ_APP_ID`/`RELEASE_PLZ_APP_PRIVATE_KEY`) so CI runs on the release PR and the tag triggers workflows; the follow-up commit must retain that bot identity or release-plz will replace the PR to preserve human-authored history. Merging the release PR ships the release — treat it as outward-facing. Gotcha: release-plz refuses to run if any tracked file is also gitignored (`git ls-files -ci --exclude-standard` must stay empty).
- **Don't break centered TUI gallery thumbnails.** `crates/mold-tui/src/ui/gallery.rs` uses a fixed-protocol thumbnail path. Do not revert the grid to plain `StatefulImage` for Kitty/Sixel/iTerm2 — it reintroduces top-left-padded thumbnails instead of centered aspect-correct ones. Keep the regression tests passing. The Mold Studio spec now defines the TUI as the fifth shell (spec §05 "Terminal surface", gap G13, mockup `docs/design/mold-tui-proposed.html`) — future TUI restyling implements that, keeping this invariant and the key→action contract tests.
- **TUI Create form = essentials + Advanced accordion.** `crates/mold-tui/src/ui/create_form.rs` owns the row model (`CreateRow`, `AdvSection`, `visible_rows`) — the old `ParamField::visible_fields` is gone, Mode/Host rows never come back (routing = Machines `GenTarget`), and the inline Negative editor only renders while Advanced → Negative is expanded (`negative_visible()` is the focus/hit-test predicate). Video shows Frames/FPS for video families plus checkpoint-aware LTX-2 Audio and latent-upscale rows. Audio's tri-state `default` / `on` / `off` preserves an absent `enable_audio` until explicitly changed, enabling it selects MP4, and an advertised `supports_audio:false` hides it and clears stale authority. Spatial `native` / `1.5×` / `2×` and temporal `native` / `2×` preserve absent request fields until changed; leaving LTX-2 clears both. Accordion state persists at `tui.advanced_open`/`tui.advanced_section`; keep the `visible_rows`/summary/active-count contract tests and the `TIMELINE_HEIGHT >= TIMELINE_VISIBLE_ROWS + 2` const-assert green.
- **AUR PKGBUILDs auto-publish on `v*` tags.** `packaging/aur/{mold-ai-bin, mold-ai}/PKGBUILD` are the source of truth; CI rewrites their `pkgver` + `sha256sums` in the `publish-aur` job and pushes to the AUR git repos. The existing `-bin` package stays on the `cuda-sm89` release tarball. RTX 3090/A40, B200/B300, and RTX 50-series users build the source PKGBUILD with `CUDA_COMPUTE_CAP=86`, `100`, or `120`; do not publish an sm100 binary AUR package before real B200 qualification. ## Key design decisions

1. **Crate boundaries are clean** — `mold-cli` doesn't depend on candle; `mold-server` doesn't depend on clap; `mold-discord` only depends on `mold-core`.
2. **candle over tch/ort** — pure Rust, no libtorch. Uses a published fork (`candle-*-mold` on crates.io) for Metal quantized matmul precision + seed buffer size fixes.
3. **Single binary** — `mold` includes `serve` via `mold-server` library; GPU flags forward `mold-cli` → `mold-server` → `mold-inference`.
4. **`tokio::sync::Mutex` + `spawn_blocking`** — single-model-at-a-time fits GPU workloads. `AppState.model_cache` is an LRU (max 3) with `ModelResidency { Gpu, Parked, Unloaded }`; at most one engine is GPU-resident.
5. **Nix flake (flake-parts + crane)** — CUDA 12.8 on Linux (default sm_89 Ada; `mold-sm86` for RTX 3090/A40, `mold-sm100` for B200/B300, `mold-sm120` for RTX 50-series; `mkMold` for any), Metal on macOS. B200 is server-only and remains simulated, not hardware-qualified. Devshell sets `CPATH`/`LIBRARY_PATH`/`LD_LIBRARY_PATH` for CUDA compilation.
6. **Shell completions** — static via `clap_complete` + dynamic via `CompleteEnv` with `ArgValueCandidates` for model names.
7. **Lifecycle authority follows scheduler ownership** — `PATCH /api/devices/:id` and every client enable/disable control are available only when `/api/capabilities.devices.lifecycle` is true. Legacy, observe, CPU-fallback, and all-disabled maintenance runtimes remain read-only; never persist a live change they cannot enforce.
