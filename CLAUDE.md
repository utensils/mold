# CLAUDE.md

Guidance for Claude Code working in this repo. Keep lean: only things not obvious from the code, `--help`, or `git log`.

## What mold is

Local AI image/video generation CLI built on [candle](https://github.com/huggingface/candle). Supports FLUX, SD1.5, SDXL, SD3.5, Z-Image, Flux.2 Klein and Dev, Qwen-Image, Wuerstchen v2, LTX-Video, LTX-2, and Wan 2.1/2.2 (T2V; the family's frame grid is `4k+1` and its sampler deliberately follows the diffusers/Lightning flow-UniPC schedule, not upstream Wan's `fm_solvers_unipc.py` — see `wan/sampler.rs`). Runs locally on GPU or talks to a remote `mold serve` over HTTP. Single binary, everything feature-gated.

Desktop gallery authority is singular: while its local server is running or its lifecycle is unresolved, native list/save/delete/media paths use authenticated HTTP (ticketed for media elements). Direct filesystem access is allowed only while the lifecycle mutex proves `LocalServer::Off`.

## Commands

```bash
# Nix (preferred)
nix build                   # Build mold (default CUDA/Metal)
nix fmt                     # treefmt (nixfmt + rustfmt)
nix flake check             # CI-equivalent gate

# Cargo — common loops
cargo check                                                                    # type check
cargo clippy --workspace --all-targets -- -D warnings                          # what CI runs
cargo fmt --all -- --check                                                     # what CI runs
cargo test --workspace                                                         # what CI runs
cargo check -p mold-ai --features preview,discord,expand,tui,webp,mp4         # what CI also runs
./scripts/coverage.sh [--html]                                                 # coverage

# Local dev run (MUST prefix with ensure-web-dist so the embedded SPA isn't a stub)
./scripts/ensure-web-dist.sh && cargo run --profile dev-fast -p mold-ai \
  --features metal,preview,expand -- run "a cat"
```

Inside `nix develop` the devshell exposes shortcuts (`build`, `build-release`, `serve`, `mold`, `clippy`, `run-tests`, `coverage`, `fmt`). Run `type <cmd>` to see the underlying invocation.

**CI gates** (`.github/workflows/ci.yml`): PRs keep the required `rust` MSRV/fmt/Clippy/deterministic-test/feature gate, relevant Metal forced-local checks, `web`, `docs`, desktop/iOS compilation, and path-gated release contracts. Shipped CUDA targets compile in release workflows instead of a duplicate 40+ minute forced-local CI job. Codecov coverage, the live external-catalog monitor, and the non-shipping FlashAttention check remain on `main` without blocking PRs. Repository-owned release-plz PRs take an allowlisted fast path through locked-manifest and release-contract validation, bridged into the protected `rust` status. Required jobs fail closed if path classification fails. All triggered gates must pass.

**iPhone app** (`apps/mobile/src-tauri`, frontend entry in `desktop/src/mobile/`): a standalone thin Tauri crate, excluded from the root workspace so the desktop GPU/server dependency tree is never cross-compiled for iOS. It is always remote-only (`HostView.kind = "remote"`, `primary = false`) and owns the five Mold Studio destinations as four tabs plus a push screen: **Create**, a merged remote **Library**, **Models**, **Machines**/host detail, and a header-pushed Settings screen; a full-screen Advanced sheet hosts the sampler/negative/LoRA/format controls with an active-count badge; source media (image wells, first/last frames) lives in the primary Create stack, gated by the shared `sourceMediaPlan` policy. Reuse `desktop/src/lib` API types, explicit-target HTTP/SSE helpers, capability/request form, source fitting, gallery media, catalog, and theme logic; never import a desktop store that assumes a local **This device** engine.

Host metadata and selection live in WebView storage, but per-host API keys must remain in the native iOS Keychain under `com.utensils.mold.remote-api-key`. Host entry accepts LAN/IP/DNS/HTTPS and Tailscale MagicDNS names; Tailscale support is the existing tailnet/DNS path, not an embedded SDK. Native Apple DNS-SD discovers `_mold._tcp` under Local Network permission. Desktop and web Settings pair iPhone through authenticated `POST /api/pairing/sessions`: the QR carries an editable reachable base URL, exact instance ID, and a 256-bit random one-use ticket with a two-minute expiry, never the durable API key. Native camera scanning redeems only through `POST /api/pairing/claim`, verifies the returned instance, dedupes through the normal host path, and writes the returned key directly to Keychain; retain Bonjour and manual entry fallbacks. Authenticated image/video elements must use `POST /api/gallery/media-token` for a 15-minute, exact-path read ticket; never put the durable API key in a URL or buffer an entire video as the legacy fallback. LTX-2 guidance overrides use the shared Studio parser/serializer across web, desktop, and iPhone; native Advanced controls validate before queueing, restore metadata/templates, and keep untouched fields absent so pipeline constants remain authoritative.

Create shares the desktop capability/request contract, independently queues and cancels batch siblings, and keeps proportional resolution plus explicit Random/Fixed seed controls. On iOS, every validated one-shot or sequence submission holds a finite `UIApplication` background task across source preprocessing, legacy placement fan-out when required, reference upload, and remote admission; release it after every one-shot sibling opens its response or the sequence-create POST returns, always end it on failure/cancellation/expiration, and rely on the remote host plus foreground reconciliation after acceptance rather than declaring a continuous background mode. Its generation target is a persisted policy (`mold.mobile.generate-target.v1`: host id | `auto` | `capable`) resolved by `desktop/src/mobile/generateTarget.ts`, and **Auto** / **Most capable** are offered only while at least two connected machines are reachable — one machine keeps the single-host behaviour exactly. Canonical protocol-v2 generation never waits for placement preview: pinned work submits directly, while an automatic policy chooses from cached model/queue/GPU telemetry and durably admits to that frozen host. Older hosts keep authoritative `POST /api/generate/placement-preview` fan-out as an explicit compatibility path, choosing by predicted completion including round trip for Auto and by captured `gpu_info.backend` for Most capable. Under either path the model picker is the union across reachable machines with per-model availability. The winner is frozen into the same immutable route record the pinned path uses, so `mobileHostMatchesRoute`, prepared/quick expansion (which never re-route), and durable sequence recovery all keep the exact machine; a major-version `profileHashConflict` stops automatic routing instead of guessing, and a fleet where nothing can run the print queues nothing and names each machine. Desktop Settings exposes the effective `MOLD_HOME` with a typed path and native folder picker. An optional migration copies the complete current root through an atomic sibling staging directory, preserves the old root, and relaunches only after the destination is ready; the shared bootstrap choice is resolved by `mold-core` before config, SQLite, logging, gallery, and server initialization so every local surface retains the same `Config::mold_dir()` authority.

**Model-removal ownership invariant:** `mold_core::removal::model_owned_paths` is the single authority for "which on-disk paths does model X own", and every consumer — `build_ref_counts`, `plan_removal`'s unique/shared classification, the `mold rm` / `mold clean` orphan sweep's keep set, the TUI's removal view, and the server's `DELETE /api/models/:model` — derives from it. Ownership is read from the MANIFEST, never from the `[models]` config entry alone: a config entry is a `ModelPaths` projection with one field per component role, so it can name neither a role `ModelPaths` has no field for (`AudioVae`, `Processor`, `VideoScheduler`, `AudioScheduler`, `ModelConfig`, `TaskConfig`, the identity assets) nor the second file of a role a manifest declares twice (LTX-2.3 ships an x2 and an x1.5 `SpatialUpscaler`). Reading ownership off that projection is what let the sweep delete MiniMax H3's audio VAE and runtime support configs, and LTX-2.3's 1.09 GB x1.5 upscaler, out from under installed checkpoints. The union is manifest storage paths (those that exist) ∪ the config entry's own list ∪ derived artifacts no manifest walk can see (PuLID's converted tower and parser). Ref-counting keeps the "an incomplete owner does not hold shared bytes hostage" rule, and that completeness question is manifest-derived too (`configured_owner_is_complete`): a config entry that still lists every path it CAN name is not evidence, since the missing component may be one the projection has no field for — but the manifest half is asked only of models with manifest files on disk, so a config entry pinning every component elsewhere is still judged by its own list rather than disqualified. The SWEEP is deliberately laxer than either — `model_install_is_present` keeps a partially installed model's dependencies so `mold pull` can repair it, and `.sha256-verified` sidecars are kept with the files they attest. When ownership is uncertain, keep the file: a file wrongly kept costs disk, a file wrongly deleted breaks a running install. The sweep prints every path it actually unlinks — the shared file plus, for an hf-cache-backed orphan, its blob and each snapshot symlink — never only a count. `execute_removal` deletes each removed file's `.sha256-verified` marker with it (a marker attests to ONE file and `manifest_files_exist` accepts its presence as proof of a complete install, so a stranded one would vouch for whatever is written under that name next) and walks the emptied model directory up to — never past — the models dir.

**Model metadata presentation invariant:** Web, desktop, and iPhone Installed/Discover cards, table rows, and details use the shared model-kind labels. Mature catalog entries always carry the textual `18+ NSFW` danger badge (never color alone). Details use kind-aware weight labels and show description, tags, source, license, format, and popularity only when supplied; installed Civitai sidecars retain those fields, while missing metadata stays omitted rather than guessed. **A fixed control explains itself with the profile's own sentence, never client copy:** `IntegerControl.note` / `FloatControl.note` are additive, authored at the one place `generation_profile.rs` decides the fixedness (H3's guidance is pinned at 0 by a pipeline with no classifier-free branch; a Turbo tier's steps are its distilled schedule's terminal-inclusive grid points; a distilled FLUX/LTX recipe keeps the old CFG sentence formatted from the value it actually pinned), and web/desktop/iPhone render `controlNote(control)` from `studio/lib/generationProfile.ts` verbatim under the field — a fixed control with no note renders NOTHING, which is exactly what an older server's response deserializes to. Preset `tier` is data, not decoration: every shipped profile authors `recommended`, which `studio/lib/outputShape.ts` hides, so nothing may override it to put a mark on every size pill (`h3_private_bridge.rs`'s "Reviewed" did, and named a qualification that is not a property of the pixels).

**Model storage permissions invariant:** model weights, configs, support files, model roots, and runtime staging roots must never be rejected because of Unix owner/group identity or group/other write-mode bits. Shared storage and collaborative umasks such as `0664` are valid. Protect execution with pinned content authentication, regular-file and symlink checks, canonical containment, and descriptor identity fencing; loaders that stage into a shared parent must construct from retained process descriptors rather than a replaceable pathname. Owner-only permission requirements remain appropriate for credentials, authorization records, and retained private evidence, never for runnable model artifacts.

**Native prepared-expansion invariant:** Desktop and iPhone Batch 1 keep quick Expand/undo but freeze one concrete route through the next Generate/Develop and become stale if prompt/model/family/host inputs change. Stale quick work must present explicit recovery: re-expand starts from the original prompt on the current route, generate-anyway drops only the frozen authority and submits the visible rewrite on the current route, and restore returns the original without queueing; never leave an enabled Generate control as a text-only dead end. Desktop Generate with Batch N greater than 1, matching web, submits N ordinary siblings from the visible prompt; only the explicit Prepare N variations action expands. Explicit desktop/web preparation and iPhone Batch N preparation must resolve once, request exactly N non-empty prompts from that target, preserve the reviewed set across upstream changes as specifically named stale work, and submit one edited prompt per sibling through the stored route with the source prompt as provenance. Prepared siblings carry additive `batch_id`, one-based `batch_index`, and `batch_count` through requests, long-video chains, complete events, saved metadata, and the Library. Never silently resize, reroute, fall back, or erase prepared work. Missing-model pulls and pull-resume use the same host and retain the ordered prompt list. Desktop Generate uses `useDownloadsStore`; iPhone Generate and Catalog share `useMobileDownloadsStore` without importing desktop-primary state. Both authorities associate the returned job ID with the frozen host/model, retain compatible pre-ID snapshot behavior, and keep Connecting, Starting, Queued, Pulling, Ready, failed, and cancelled recovery inline for Batch 1 and prepared Batch N. The iPhone route additionally snapshots its selected remote host ID, URL, Keychain-supplied key, and server instance ID in one immutable recovery record. Each pull attempt temporarily leases that exact route, joins a compatible Catalog POST already in Starting, and releases on success, failure, cancellation, staleness, supersession, or abort so Retry must reacquire it; edits/removals supersede pending replacement ownership. Unique component consumer IDs plus unmount invalidation prevent dead views from queueing or tearing down remounted work. Partial prepared failures must name the one-based variation and reviewed prompt, compose any unconfirmed-cancellation caveat, and preserve successful prints. Every generation-facing label resolves catalog IDs through the current inventory for display while retaining the raw ID for requests, matching, and persistence.

**Conditioning-aware expansion invariant:** `ExpandTask` is the cross-surface semantic contract. Derive it from the concrete generation request with the shared Rust or browser helper; do not infer it independently inside a view. T2V is chronological, I2V/V2V preserve source authority, retake and keyframes preserve their boundaries, and audio-driven video follows the source audio. Prepared and quick expansion snapshots include the task so a conditioning change is named as stale work. `/api/expand` receives the task but never source image, video, keyframe, or audio bytes. Clients that omit the additive field retain family-based image/T2V behavior.

**Identity-photo invariant:** face-identity conditioning (PuLID) is one browser-side policy, `studio/lib/identityConditioning.ts`, and web/desktop render the shared `studio/components/IdentityPhotoWell.vue` — never a per-surface rule. The gate is the server's own authority: the resolved recipe's `capabilities.supports_identity` first, the additive `/api/models[].supports_identity` as the picker fallback, absence reading as NO (the client-side legacy recipe adapter never answers, because its `false` is this client talking). An unqualified checkpoint or an older host renders NOTHING rather than a disabled control, and it also refuses NOTHING: visibility and validation are gated on the SAME positive capability, so a staged photo simply parks — retained in form state, absent from the wire, Generate still enabled, and the well reappears with the photo when a qualified model is selected again. That is the LTX-2 staged-media precedent, and blocking there would refuse a print the server would happily render. On a qualified checkpoint the helper mirrors admission and invents nothing: never with a LoRA or an img2img `source_image`, no knob without a photo, PNG/JPEG within the 16 MiB / 8192 px / 32 MP bounds read by an identity-specific header walk that mirrors `mold_core::identity::header_dimensions` across the WHOLE payload (`imageDimensionsFromBase64`'s 1 MiB prefix is right for a source image and wrong here — a camera JPEG's start-of-frame can sit past it) — and those refusals are INLINE beside the control, never a toast, with Generate blocked. The photo is a face reference, not a composition input: it is never fitted, cropped, or resized to the canvas. `id_weight` / `id_start_step` stay absent until touched so the server's defaults remain authoritative, and they count toward the Advanced badge while the well — primary form, beside the source wells — does not. Saved metadata carries the name, digest, and effective values only; Reuse settings restores the knobs and re-attaches the photo from the same content-addressed local stash `source_image_sha256` uses, disclosing inline when the device no longer holds it. A request may carry SEVERAL references of one person: `id_images` is the plural shape of `id_image` and supplying both is a hard validation error, never a precedence rule, because with averaging a silently dropped photograph changes the face that renders with nothing visible to the caller. The set is bounded by `ID_IMAGES_MAX` (4 — a latency budget, since extractions serialize), plus whole-set encoded-byte and decoded-pixel caps that sit deliberately BELOW the per-image limits times the count. Averaging is `cubiq/PuLID_ComfyUI`'s, and it is POST-IDFormer: each photograph runs the whole detector → ArcFace → EVA02-CLIP → IDFormer pipeline and the final `[1, 32, 2048]` token sets are meaned (`pulid.py:406,415-419`). Averaging the raw ArcFace vectors or the EVA hidden states first is a different, untrained composition and is never done — `ToTheBeginning/PuLID` handles only one image (`pulid/pipeline_flux.py:120-194`), so ComfyUI is the reference for the multi case. The mean is order-independent but the provenance is not: the frozen fingerprint hashes the source digests in request order. A photograph with no detectable face refuses the whole request and names its one-based position. Saved metadata carries the plural names/digests ONLY for the plural form, so a single-photograph print's metadata stays byte-identical to a pre-`id_images` build's. Both `id_images` and true CFG (below) are CAPABILITY-GATED, because an older server DROPS an unknown field rather than rejecting it: `id_images` alone renders with no face in it and `true_cfg` alone renders the distilled path at a guidance value chosen for a branch that never ran. `GET /api/capabilities` → `identity` (`{ multi_photo, max_photos, true_cfg }`, built by `IdentityCapabilities::advertised()` from `mold_core::identity`'s own constants so it can never advertise a bound the validator does not enforce) is the authority, and ABSENCE READS AS NO — the whole block is `#[serde(default)]` all-false, which is exactly what an older server's response deserializes to. A client that needs either shape probes first and refuses by name; the singular `id_image` predates the block and pays no round trip. Only a genuine transport failure — `MoldClient::is_connection_error`, the same authority the local fallback already uses — falls through unrefused, because the ordinary remote attempt fails the same way and falls back to local inference. A REACHABLE server that answers 404 or garbage is read as all-false and refused, since that is precisely how an older server answers before accepting the request and dropping the fields. Multi-photo and true CFG are core, server, and CLI only so far (#1226) on every surface, web/desktop included; the single-photograph shape above is unaffected.

**True-CFG invariant:** FLUX is guidance-distilled and runs one forward per step; PuLID's true CFG (`PuLID/flux/sampling.py:136-149`) restores a real negative branch, and `mold_core::identity` is the only authority for it. Additive `true_cfg` / `cfg_start_step` reuse the existing `negative_prompt`; `request_uses_true_cfg` is the single predicate every layer reads (admission, the memory estimate, the extractor, the engine), and it is false for an absent scale, for one within `TRUE_CFG_EPSILON` of `TRUE_CFG_OFF` — upstream's own `abs(true_cfg - 1.0) > 1e-2` comparison at `sampling.py:120` — and for a zero `id_weight`. True CFG is qualified ONLY alongside active identity conditioning, because the negative branch needs the unconditional identity embedding the extractor produces beside the real one; that gate is what keeps `id_weight: 0` byte-indistinguishable from a plain request. `1.0` is accepted and inert — `validate_true_cfg` admits the `[1.0, 10.0]` range and `request_uses_true_cfg` answers false within `TRUE_CFG_EPSILON` of it, so the branch is never constructed rather than run as an identity lerp: `neg + 1.0 * (pos - neg)` is `pos` arithmetically but not bit-identically. The unconditional identity is `IDFormer(zeros, zeros)` (`pulid/pipeline_flux.py:188-192`) — not a zero tensor, and a pure function of the adapter weights, so it is computed once at extraction and only when the branch actually runs. Both halves ride on one `FrozenIdentityEmbedding` and are installed and cleared by ONE call, because a leftover unconditional embedding would condition this render's negative branch on the previous person's absence. `FluxTransformer::denoise` takes `Option<&TrueCfgBranch>` and `None` leaves the loop byte-for-byte what it always was, pinned per transformer variant in `flux/pulid_variants.rs` on the same synthetic route the zero-weight tests use. A request that asked for the branch and was frozen without an unconditional identity is an explicit error, never a silent distilled render — `guidance` is chosen for whichever regime is running. Admission charges `TRUE_CFG_VRAM_OVERHEAD_BYTES` on top of the identity overhead so a branched render is never admitted on the plain estimate. Web, desktop, iPhone, TUI, and Discord are a separate issue.

**Expansion-routing invariant:** prompt expansion follows the GENERATION route, but the generation router is model-aware about the checkpoint and knows nothing about the expansion LLM — so `studio/lib/expansionRouting.ts` is the one policy every surface calls. `resolveExpansionRoute(policy, generationRoute, candidates, rank)` keeps the generation route unless that host's `/api/capabilities.expand.model_present` is positively `false`, and only then re-ranks the eligible machines whose `model_present === true` — every ready machine under Auto/Most capable, ONLY the pinned machine when one is pinned. Unknown is never missing: an unread capability snapshot (absent or `null`) keeps the route it already earned and never qualifies a host as a reroute target. The ranking is handed in (desktop/web `pickAutoHost` / `pickMostCapableHost`) so this never becomes a second router, and Remix follows the same route because `/api/remix` runs on the same expander. The generation route is captured BEFORE the request on every surface — an Auto rerank mid-flight must never move the print's machine out from under the reviewed set. The print never follows the rewrite: desktop's prepared/quick snapshots keep the generation route in `route` and record a diverging expansion host in the additive `expansionRoute`, and the existing route-changed staleness rules are unchanged. When no eligible machine has the expander, the pull offer takes its host from `planModelInstall` — fed from the EXPAND capability, never `/api/models`, because the expander is not a generation model — and DEFAULTS to the generation route's host so prepared work still freezes one route; the machine picker is mounted by Models, so Create names its choice instead of opening it. `/api/capabilities.expand.model` names the manifest model (`qwen3-expand`) so clients stop hard-coding it — `expandModelId` falls back for older servers. iPhone pins exactly one machine, so its decision is always the generation route until mobile Auto/capable routing hands a real candidate list to the same helper. `ExpandTask` derivation is untouched, and `/api/expand` still never receives media bytes.

**Identity-photo staleness invariant:** a changed identity photo is a conditioning-media change. `studio/lib/promptTransform.ts`'s `conditioningFingerprint` reads `id_image` alongside `source_image`, the video/audio sources, keyframes, and H3 references, so reviewed prompt work (remix on iPhone; remix, prepared, and quick expansion on desktop and web) stales on a face swap exactly as on a source-image swap — there is deliberately no second, identity-only staleness rule. `ExpandTask` is untouched (a face reference does not make a text-to-image print an img2img one) and `/api/expand` still never receives media bytes. Mobile's plain (non-remix) prepared batches carry no conditioning fingerprint at all today — identity got exactly the same treatment as source images; close that gap for all conditioning media at once, never for identity alone.

**Desktop updater:** signed release builds support persisted **Stable** and **Nightly** channels. Startup and menu/Settings checks are check-only; an available update is announced in persistent app chrome and by a native notification while backgrounded, and installation requires the user's explicit **Update and restart** action. Stable reads the public `mold-desktop-stable.json` manifest from the latest tagged release; Nightly reads `mold-desktop-nightly.json` from the rolling `latest` prerelease, which `.github/workflows/desktop.yml` rebuilds only after the frontend and Rust gates pass for a desktop-relevant `main` commit. Before touching the installed app, Tauri verifies the Minisign signature and Mold fully extracts the archive to temporary storage, binds its bundle ID/version to the manifest, runs strict Apple code-signature and Gatekeeper checks, validates the current app identity and install location, and proves the app's parent directory is replaceable. Only then does Mold atomically exchange the staged and installed bundles with macOS `RENAME_SWAP` and restart. There is deliberately no post-launch watchdog, probation, or Mold-owned rollback; the update either passes preflight and installs or fails while the running version remains in place. Do not add a silent downgrade comparator: selecting Stable from a newer Nightly waits for a later stable version. Distribution CI requires `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in addition to the Apple signing/notarization secrets, verifies signatures against the checked-in public key, and retains ten Nightly desktop generations. The updater private key must have controlled offline backup and must never enter the repo or logs; losing it strands installed clients, and rotation must first be delivered by an update signed with the existing key.

**Desktop model-library invariant:** the Installed shelf and download progress are all-connected-host views, host detail mirrors the selected host's pulls, and built-in manifest variants take precedence over ambiguous multi-checkpoint Hugging Face repositories so a Pull targets one runnable model rather than an aggregate repository. Remembered hosts in `connectedHostIds` are attempted immediately on launch in parallel with This Mac; an explicitly disconnected host stays remembered but is excluded from reconnects and every all-host operation until the user reconnects it.

**Command-palette model-search invariant:** the ⌘K palette on web and desktop searches the whole fleet, and every model row's wording and destination derives from `planModelInstall` plus `studio/lib/modelSearch.ts` — never a second policy. Installed rows are the union across ready machines (web's additive `HostRouting.installedModels`, desktop's `models.installed` merged with `hostModels.unionInstalled`), so a model is never hidden because the pinned target lacks it. `resolveModelHost` repins the generation target ONLY for an explicitly pinned target that lacks the model; automatic routing (web `auto`/`capable`, desktop `null`/`capable`) is already model-aware and must stay untouched. Not-installed rows come from a debounced live catalog search restricted to checkpoints, drop unsupported entries and anything the fleet already has (matched on both catalog id and server-reported name), stay appended in the server's relevance order behind the panel's `busy` indicator, and discard responses for abandoned queries via a monotonic epoch. Palette installs deliberately take the plan's first target and name it in the toast instead of opening the machine picker — that dialog is mounted by the Models page and would be invisible from any other route. Load/unload rows stay scoped to the primary; they act on this machine's GPU, not on whichever machine holds the weights.

**Model install-target invariant:** a Models row is merged across machines, so `installed` means "installed somewhere" and never "installed here". Web, desktop, and iPhone derive the row's action from `planModelInstall` in `studio/lib/modelInstallTargets.ts`: every reachable machine that lacks the model stays an install target, owners degrade to repair, and the action collapses to Repair only once every reachable machine has it. Never hide the install because some other machine has the model. A machine whose `/api/models` has not been read is not evidence of absence and is never offered as an install target on desktop or web; the host picker always names the per-machine outcome so a mixed fleet is unambiguous. Both download routes are strict about id shape — `/api/downloads` takes manifest names and `/api/catalog/:id/download` takes `cv:`/`hf:` ids, each rejecting the other — so every install path must route on the id, not on the calling surface.

**Missing-model routing invariant:** Auto / Most capable must never dead-end on a model nobody has. `classifyMissingModel` in `studio/api/generationPlacement.ts` is the one classifier that tells an authoritative `infeasible` caused by the model's own absence (the server's "no concrete local artifacts" reason, or a missing component the requested model itself repairs) apart from a capacity refusal, a policy block, or a missing companion — only the first may be answered with a download, and every surface reads that classification rather than matching the reason string itself. Desktop's `resolveFeasible` and web's `useHostRouting` surface it per host as `missingModel`; Create then offers the pull instead of a toast, choosing the machine through `planModelInstall` (one candidate skips the picker, several open the existing `DownloadTargetDialog` / `ModelInstallTargetDialog`, which Create now mounts too), and arms the exact-host pull-and-resume — desktop's `pullResume` store, web's `usePullResume`, sharing the which-job rule in `studio/lib/pullResume.ts`. Only the machines that reported the model absent are pull targets — one that refused for capacity or policy would refuse again after the download. A resume is only ever promised for a concrete host AND a request that is already final: a source still to be fitted against the chosen machine, or a quick expansion whose provenance is stamped after routing, gets the download and an explicit "press Generate again" instead of a promise that would render different conditioning. The watch takes the server's job id whenever it reports one (`primary_job_id`, desktop's `startCatalogDownload`); otherwise it matches by model against a terminal snapshot captured BEFORE the POST, since a pull that finishes inside that window would otherwise be excluded forever. Auto's #1107 deadline must not manufacture that dead end: while no candidate has answered `planned` and a machine is still checking, it extends once (`AUTO_PLACEMENT_EXTENSION_MS`) instead of synthesising "did not answer" and collapsing a homogeneous infeasible answer into `mixed`. A restored print whose model no machine has keeps the raw id in the form and the request — desktop's `ModelPicker` renders it as the selected entry with a **Not installed** tag, web's `CreateModelPicker` as a disabled `… · not installed` option, iPhone keeps its own indicator — with a one-line disclosure on drop/Reuse; web must never silently substitute `installedModels[0]` (and that model's size/steps/guidance/LoRAs) for a model the user restored, though a genuinely unset model is still re-homed so the `<select>` is never blank.

**Feature flags** (`mold-cli`): `cuda`, `metal`, `flash-attn`, `preview`, `discord`, `expand`, `tui`, `metrics`, `webp`, `mp4`. GPU features forward through to `mold-inference`. H.264 decode is baseline for LTX-2 source ingest; `mp4` only gates AAC mux. `flash-attn` implies `cuda`, compiles 53 FlashAttention v2 kernels through nvcc, and ships in no release artifact. Building it only makes `MOLD_ATTN=flash` _available_ — the default attention backend is `Math` in every build (`attention::default_backend`, pinned by a feature-independent test, #736), so shipping the kernel is a build-time/toolchain decision rather than a seed-reproducibility one; never re-couple the default to the feature. It reaches the `crate::attention` call sites (FLUX offload + GGUF-bypass, all Flux.2, Z-Image offload, the Wan DiT's self/cross attention, and all three Qwen-Image transformers — BF16, quantized, and offloaded — on their non-Metal path); dense paths elsewhere use upstream Candle's own attention.

## Non-obvious architectural patterns

Most are in `mold-inference`. When touching engines, these are the rules that matter:

- **Lazy load** — engines load on first `generate()`, not startup. Most hold mmap'd safetensors.
- **Drop-and-reload text encoders** — T5/CLIP/Qwen3 are dropped from GPU after encoding so the transformer has VRAM to denoise, then reloaded next request.
- **Dynamic device placement** — text encoders go to GPU or CPU based on remaining VRAM after the transformer loads (thresholds: `device.rs`).
- **Quantized encoder auto-fallback** — when FP16/BF16 doesn't fit, the largest GGUF variant that fits is auto-selected. Override: `--t5-variant` / `--qwen3-variant` / `--qwen2-variant` or `MOLD_*_VARIANT`.
- **Block-level offloading** (FLUX) — `flux/offload.rs` streams transformer blocks CPU↔GPU one at a time: ~24 GB → 2–4 GB VRAM, 3–5× slower. Auto-enabled under pressure; force with `--offload` / `MOLD_OFFLOAD=1`.
- **LoRA backend is custom** — candle has no LoRA. BF16 path: `LoraBackend` (a `SimpleBackend`) intercepts `vb.get()` during model construction and applies `W' = W + scale·(B @ A)` inline. GGUF path: `gguf_lora_var_builder()` selectively dequantizes affected tensors, merges, re-quantizes. Both work with offloading. See `flux/lora.rs`.
- **LoRA caching** — `LoraDeltaCache` (pre-computed `B @ A · scale` on CPU, ~80–120 MB) survives transformer rebuilds. `LoraFingerprint` on `FluxEngine` skips redundant rebuilds when the same LoRA/scale reappears.
- **A LoRA fingerprint describes the transformer that is resident, not the request.** `QwenImageEngine::active_lora_fingerprint` mirrors FLUX's `active_lora`: same path-hash + scale-bits keying, order-sensitive, written wherever a transformer is built (eager `load`, `reload_transformer`) and cleared wherever one goes away (the VAE-decode drop, `unload`, sequential's deferred load). Every rebuild decision therefore reads residency _and_ the fingerprint — `qwen_transformer_rebuild_needed` — because an empty fingerprint means both "no LoRA merged" and "no transformer". Reading it as request state instead is what left the stay-hot quantized path rendering a new stack with the old merge baked in. Only resident paths can elide; `generate_sequential` builds a request-local transformer, and Qwen block offload refuses LoRAs outright.
- **Shared tokenizer pool** — `shared_pool.rs`: `Arc<Tokenizer>` keyed by file path, shared across engines via `create_engine_with_pool()`. Saves ~100–150 ms on model swap for FLUX variants. The same pool caches component **CPU tensor maps**, and that half is budgeted on purpose (`CPU_TENSOR_CACHE_BUDGET_BYTES`, 2 GiB total): the OS page cache already caches a component reclaimably, so a second anonymous copy in this map converts memory the kernel could drop into memory host admission must charge in full. A component is weighed by its on-disk size **before** the read, so an over-budget one is never materialized — `load_safetensors_cpu_tensors` answers `None` and the caller takes its own mmap-backed path. Eviction is LRU over entries whose `Arc` strong count is 1, so an engine still streaming from a cached map (SD3's offloaded MMDiT) is never robbed. Unbounded, this cache is what pinned FLUX's 9.79 GB `t5xxl_fp16` in host RAM for the life of the process and made a 64 GB host refuse H3 until it was restarted (#1273); an encoder that genuinely should stay in host RAM belongs behind `MOLD_KEEP_TE_RAM=1`, which parks it _inside the engine_ where `unload()` releases it.
- **CPU-based noise** — `seeded_randn()` in `engine.rs` generates initial noise on CPU via `StdRng`/ChaCha20, then moves to GPU. This is load-bearing for cross-backend seed determinism (CUDA/Metal/CPU produce identical images).
- **Placement preview is an authority boundary** — `POST /api/generate/placement-preview` is read-only and authoritative only for ordinary-generation plans the server can admit. Prepared clients preview the finalized sibling shape after source preprocessing and fence URL, API key, and instance identity. An authoritative `infeasible` response may carry additive `missing_components`; a `planned` response may carry additive `pending_downloads` for known encoder dependencies that admission will materialize. Pending previews use a distinct registry-identity fingerprint domain, never start downloads, report low estimate confidence only when a device selected by that candidate plan has pending artifacts, and are recomputed from landed bytes at admission. Cold installed `cv:`/`hf:` IDs resolve only from contained local sidecars; the synthesized model config travels with prepared work through coordinator planning and pre-CUDA validation so config refreshes cannot erase its authority. Clients still queue nothing on infeasible and must not promise repair/resume without exact-host grouped download ownership. A strictly valid version-1 non-authoritative `unsupported` response or legacy `404`/`405` may retain compatible routing; every other HTTP, malformed response, or exhausted transient retry queues nothing. Chain and local prompt-expansion/post-generation-upscale utility previews remain non-authoritative `unsupported` until their real CPU/GPU paths are modeled. Probes redact prompts/media but retain server-local LoRA paths needed for feasibility.
- **Frozen execution plans remain authoritative at worker dispatch.** Scheduler admission owns the family-specific estimate, placement, load strategy, offload mode, and safety policy. A worker may re-sample physical memory and reject the exact `predicted_vram_peak_bytes` if pressure changed, but it must not replace that demand with the legacy path-based resident-model estimator. Apply the recheck to fresh loads, parked reloads, and reconstructed engines; unchanged CUDA hot-cache hits may recheck only when fresh, nonzero Mold-process VRAM attribution can bound the global, potentially stale cache delta. Ambiguous zero/missing attribution in containers, MIG, Metal, or WSL2 retains the scheduler's validated grant rather than double-counting resident weights. CUDA rechecks again after dropping replaced state, while Metal retains its unified-memory single gate. The same discipline covers host RAM (#1099): a host reservation stays charged in the `HostMemoryLedger` until its lease settles (an OS sample can never prove a not-yet-made allocation is reflected), the worker rechecks the exact frozen `admission_host_demand_bytes` against headroom from the granting ledger — never an independent floor computation — before any fresh load, and missing ledger evidence (legacy dispatch, chain stages) retains the grant. A host rejection is an ordinary insufficient-memory error and must never route through the fatal-CUDA quarantine. Metal reserves no host RAM at all: its host claim rides the unified device gate, and admission and placement preview must move together on that rule.
- **A host-headroom refusal releases mold's own cache before it becomes an answer (#1289).** The LRU model cache is memory mold is holding by choice, so a generation refused for want of HOST memory — never device, which placement and the cache's own evict-to-fit path already own — asks `host_reclaim::reclaim_host_headroom` first: it evicts least-recently-used across the shared cache and every idle worker's, skipping the requested model, any leased engine (`ModelCache::reclaimable` excludes the take window by construction), and any worker the scheduler would not lease a hard-pinned releasing job — busy, quarantined, shutting down, or draining, each of which would leave a request waiting on a oneshot nobody sends (degraded is deliberately admitted, exactly as `DeviceSnapshot::accepts_releasing_work` admits it), with a bounded wait on top for the race that filter cannot close. A placement preview NEVER reclaims: `ExistingOnly` is the read-only probe automatic routing fans across the fleet, so one that evicted would flush every candidate machine's warm cache to answer a question about one print. Each eviction is awaited and handed back through #1273's `release_host_memory_after_unload` BEFORE the sample is re-taken — an OS sample can no more prove an unfinished release than an unsettled allocation — and admission is retried exactly once. A shortfall that survives that is refused with the post-eviction numbers plus what was released ("released 9.8 GB by unloading 2 idle models; still 2.9 GB short"), because the figure a user acts on must already include every byte mold could return. The decision reads a TYPE, never prose: `H3PrivateHostHeadroomShortfall` is what the two H3 gates raise, for the same reason #1272 stopped sniffing a refusal for the substring "host". H3 is the only family whose host admission refuses today — every other family's host shortfall is a planner `InsufficientHostRam` _block_ that resolves when the running work returns the RAM — so the module is family-blind and uncalled elsewhere on purpose.
- **A queued generation is either schedulable, running, or answered — never all three at once and never none of them.** A pending job whose execution plan does not resolve contributes zero candidates, and `classify_no_candidate` (`mold-scheduler/src/planner.rs`) then reports the untyped `NoSchedulableDevice` because it has nothing to compare against a device; `Coordinator::generation_plan_catalog` discards the real reason at `debug`. That is the right _retry_ while mold holds the resource — a lease, a preparation, or a legacy chain claim — because the running work gives it back, and the job dispatches on the first turn after it does. It is not an answer once nothing is running: #1272's H3 print logged `no_schedulable_device` three times and then nothing for the rest of a forty-minute wait. `Coordinator::settle_unschedulable_generations` is the bound: it retains the last non-terminal planning failure, accrues an idle wait ONLY while `leases`, in-flight/legacy worker claims, and non-`Ready` preparations are all empty, and after `UNSCHEDULABLE_IDLE_GRACE_MS` refuses the job with that retained text — which for a memory shortfall is `insufficient_vram_error`'s own required-vs-sampled sentence. Never bound a job waiting behind running work, and never let a non-terminal plan failure become terminal on a busy host. The H3 arm of this is that a host-headroom shortfall must be _identified_, not sniffed: `resolve_private_h3_execution_plans` asks the host question directly before revalidating the frozen evidence, because `validate_for`'s refusal is one opaque sentence that never contains the word the old substring test looked for, so every H3 job blocked on host RAM was filed as a VRAM shortfall it did not have.
- **Learned scheduling separates setup from execution** — typed cold-load, warm-reload, identity-extract, prompt-encode, denoise, legacy VAE, visual-decode, audio-decode, mux, and upscale phases feed the scheduler's independent runtime evidence (schema v15 separates setup-independent runtime; schema v17 adds synchronized A/V output phases; schema v22 adds face-identity extraction). Planning adds exactly the selected cold or warm setup disposition. All client device panels render every advertised device and expose live mutation only under authoritative V2; read-only modes may expose only the supported restart-enable recovery. Queue plans classify non-device work with `planned_lane_kind`; clients never infer lane semantics from opaque `planned_device_id` strings, and the capacity-one host utility lane keeps `planned_device_id = null`.
- **Durable-admission readiness is ONE resolved value, and its fallback rule is stated once.** The question "is durable admission available right now, and what do I do when it isn't" has exactly four conjuncts — `queue_journal.is_enabled()`, `!is_output_disabled(config)`, `scheduled_work.v2_authoritative()`, and `queue_journal.queue_media_admission().is_some()` — and `routes::DurableAdmissionReadiness::resolve(state, config)` is the only place they are composed. It is TOTAL over all four at ONE evaluation point and takes `config` as a required parameter it never reads, so a caller without a config cannot call it at all; that is what stops the conjunction being re-derived incompletely at a call site. Every consumer reads it: `capabilities.queue.heterogeneous_batch`, `capabilities.durable_media` (through `advertised_media()`, the only route to that value, so applicability cannot be forgotten), `/api/status`, `/health`, `admit_generation_batch`, and `direct_durable_admission`. **The BATCH protocol needs all four; DIRECT durable admission needs three and deliberately not `v2_authoritative` — `unready()` versus `unready_for_direct()`.** The durable feeder is spawned on `start_generation_runner` alone and runs in legacy and observe dispatch too, so a direct generation there is genuinely durable and survives a restart; a headerless client receives the same attached media bytes either way, so requiring V2 would delete real durability from every legacy and observe host in exchange for nothing observable. V2 is what `capabilities.queue.heterogeneous_batch` advertises, so V2 is what the batch route enforces. The two routes also keep OPPOSITE refusal precedence and that is deliberate: direct checks gallery output first (`DURABLE_ADMISSION_UNAVAILABLE`), batch checks scheduler/journal/admission first (`HETEROGENEOUS_BATCH_UNAVAILABLE`), so a host failing both conjuncts answers each route the way it always has. Before this existed those sites took four DIFFERENT subsets and the gaps between them were four separate defects: a host with a corrupt `generation-admission.key` advertised `admission_protocol_version: 2` and then 503'd every batch POST; `capabilities.durable_media` contradicted `/api/status`; a legacy or observe host ran durable semantics on a request whose client had negotiated the attached path; and a degraded media store refused every media-carrying and H3 generation outright. **The fallback rule:** a readiness gate refuses only when the caller explicitly asked for durable admission (an `X-Mold-Operation-Id`); every other unmet gate returns `Ok(None)` and the request takes the attached path, which is what capability discovery already told that client to do. The attached path carries its media inline, so it needs nothing the durable path provides. A future gate the attached path genuinely cannot satisfy belongs in `validate_direct_generation_request`, never in this ladder. `DurableAdmissionUnready` keeps WHICH conjunct failed rather than collapsing to a bool, because two consumers report a per-conjunct cause — the two refusal codes (`GalleryOutputDisabled` ⇒ `DURABLE_ADMISSION_UNAVAILABLE`, every other conjunct ⇒ `HETEROGENEOUS_BATCH_UNAVAILABLE`, a contract a test asserts and the only thing distinguishing the two gates) and `durable_media_status().reasons`. Note `v2_authoritative()` serves FIVE distinct roles across routes.rs and only the durability role is behind this authority: the can-this-host-execute sites are always `|| gpu_pool.worker_count() > 0` and folding them in takes legacy and observe hosts offline; lifecycle authority, validation shape, and queue-control are likewise separate questions.
- **A durable child's ordering token is its `revision`, never its timestamp.** `generation_batch_children.revision` (schema v29) is incremented by every authoritative state transition and by nothing else — a REFUSED transition must not spend one, or a reconciling client cannot tell it from one that landed. It exists because `updated_at_ms` was carrying two jobs at once: an honest wall clock, and the version every client reducer compares. SQLite commits several transitions inside one millisecond routinely, and `POST /api/queue/{id}/retry` is the ONLY route that moves a child BACKWARD through the browser's `FORWARD_PHASE_RANK` (held ⇒ accepted), so a same-millisecond collision there is not a tie to break arbitrarily: `mergeJob` drops the backward move and the retry becomes invisible in the UI. `studio/lib/generationLifecycle.ts`'s `childRevision` reads it off the child itself rather than from an action parameter nobody ever supplied, and treats BOTH absence and `0` as no authority — rows admitted before the migration sit at `0` until their next transition, so reading `0` as a real revision would let a pre-migration snapshot win ties it should lose. The wire field is additive and `#[serde(default)]`, so an older server deserializes to `0` and every client falls back to the timestamp comparison it always used; the retry path additionally keeps its `updated_at_ms = MAX(?, updated_at_ms + 1)` bump for exactly those clients. The SECOND consumer is `reconcile_ambiguous_retry_observed`: a retry POST whose response was lost is reconciled by comparing the child's revision against the one captured BEFORE the POST, because `held` alone conflates "the retry landed and the job was immediately re-held for a fresh reason" with "the retry never arrived". A child still sitting at the submitted revision when the bounded attempts run out was NOT retried, and the call now errors with the retry fence RETAINED rather than republishing the pre-retry snapshot as fresh authority while the original POST may still commit. `observed_revision == 0` (an older host) keeps the original publish-on-exhaustion behaviour, because with no version to compare there is no evidence either way and hanging forever is the worse failure.
- **A hold is durable, not eternal.** `queue_retention.rs` is the queue's peer of `gallery_trash.rs`'s retention sweeper and is shaped like it deliberately — one `sweep_held_once` pass reading `queue.held_retention_days` fresh from the live config (default 30, `0` keeps forever, env `MOLD_QUEUE_HELD_RETENTION_DAYS`), one hourly background task, one manual `POST /api/queue/held/sweep`. What it does NOT share is the deletion mechanism: a trashed print is a file to unlink, whereas a held row's encrypted media is released by the `generation_queue_media_retire` trigger the moment the queue row is deleted, so the sweeper never writes `generation_queue_media` itself — it resolves the GC candidate BEFORE the delete (the lifecycle resolves by job id, and the row is what carries the association), deletes, then collects what the trigger just marked. A failure there is reported as `media_deferred`, not hidden, because the obligation is already `gc_pending` and startup reconciliation still owns it. Age is measured from `updated_at` — when the row was HELD — not from admission, so work that queued for a week and held yesterday gets its full window. `purge_held` re-checks held-and-owned inside the transaction, so a retry or cancel landing between the listing and the purge WINS: a human's explicit decision outranks retention. The batch child is settled to `failed` rather than deleted, because after the queue row is gone that summary is the only thing a reconnecting client can read, and dropping it would report the print as never admitted. Without this sweep a deterministically-failing request kept a `GET /api/queue` row forever AND pinned its encrypted media set, because `hold_claimed` retains `media_set_id` on purpose so a retry still has its source images.

- **Batch capability is static before engine load** — `mold-inference` owns one registry for every production family and factory alias; tests construct every advertised name and engine construction fails closed if the runtime contract differs. Production generation families currently declare only native size `[1]`. `mold-scheduler` prioritizes real initial-wave cardinality, solves homogeneous singleton fleets exactly at arbitrary size, and solves host-coupled heterogeneous singleton inputs exactly through 8 devices at arbitrary child count. Singleton plans retain one arithmetic lane per selected device with typed random access and bounded 4096-record windows; they do not materialize one record per child. Ordinary native inputs use the deterministic 64-strategy bounded fallback, while huge batches visibly fall back to the mandatory compact singleton plan as `BoundedHeuristic`. Direct `/api/generate[/stream]` is permanently singleton-only; Batch N is 1–64 ordered singleton children admitted atomically through unversioned `/api/generation-batches`, capability-gated by `heterogeneous_batch`, `durable_batch_outcomes`, `admission_protocol_version = 2`, and the request's exact `durable_media` contract. Larger client batches are chunked. No engine is represented as returning multiple native outputs; the old raw-parent runtime remains recovery-only for rows persisted by older servers. A LONE singleton carries no synthesised batch provenance — `batch_id`/`batch_index`/`batch_count` are the prepared-expansion contract and stamping them on every one-shot makes "was this a prepared variation?" unanswerable to gallery and reuse consumers — and `mold run` / the TUI keep singletons on the attached path, which is the one that carries live step progress, the centered fixed-protocol denoise preview, and remote missing-model auto-pull; durability is unaffected because `/api/generate` admits through `direct_durable_admission` either way.
- **A queued generation is durable, and the retention fence is what makes that true.** One `generation_queue` row (schema v18) per admitted public singleton, written before `submit()` and owned by an RAII `QueueTicket`. Dropping the ticket deletes the row during normal operation and **retains** it once `QueueJournal::retain_all()` has been called, which is how the ~20 existing discard sites in `scheduler/mod.rs` and `gpu_worker.rs` become a resume list without any of them knowing durability exists. Order is the correctness argument: the fence goes up **before** `scheduler_shutdown.cancel()` in `begin_runtime_shutdown`, and it is raised by **all three** abnormal-exit initiators — SIGTERM, the fatal-CUDA notifier in `run_server`'s select, and `quarantine_poisoned_worker` — because fatal CUDA is the one restart mold performs on its own behalf and a SIGTERM-only fence deletes the whole queue on exactly that path. `complete()` and `discard()` delete unconditionally: a finished print must never be replayed, and an explicit cancel outranks the fence even mid-drain. `mold.db` never holds a secret — reference-upload authority, batch children, jobs with no `output_dir`, and over-`MOLD_QUEUE_JOURNAL_MAX_BYTES` payloads are excluded **at admission**, not redacted, and each is advertised per-job as `durable: false` rather than silently half-persisted. The two counters are charged at deliberately different moments and swapping them is a data-loss bug in both directions: `dispatch_attempts` (cap 2) by the same statement that claims a row for execution on the GPU owner thread, so a job waiting behind a long render through ten deploys is charged zero; `replay_seen` (cap 10) once per boot, sized for a 5 s `RestartSec` crash loop. Exceeding either **holds** the row — listed, never auto-run, never deleted. `OutputMetadata.job_id` is the replay idempotence key, stamped before the save: output filenames are wall-clock, so without it a replayed job leaves a permanently un-mergeable duplicate print. Replay is **one sequential task** (`submit_when_available` serializes on a single global `capacity_waiter`, so parallel replay lands in arbitrary order), runs before the router serves, and resubmits under the original job id through the ordinary admission path so validation, placement, frozen plans, and auto-pull all still apply. This deliberately diverges from chain jobs, whose `Interrupted` state never auto-resumes (`chain_job_runner.rs`): a chain owns partial artifacts and a stitched timeline, a queued singleton owns nothing, so re-running it from step 0 is free of consequence. Shutdown is genuinely bounded rather than merely timed: the deadline is armed when shutdown begins and runs _beside_ the drain, ending the process on expiry, because Axum's graceful shutdown waits on in-flight responses and a `spawn_blocking` join ignores a dropped handle — a timeout anywhere inside the sequence stops waiting without stopping anything. Hard exit is opt-in (`allow_hard_shutdown_exit`) so the embedded desktop engine, which runs inside a process it does not own, keeps returning instead. The row is settled on what actually reached the gallery, never on inference returning: a failed publication holds the row, because for a replayed job the gallery file is the only delivery. Queue OWNERSHIP and LIVENESS are separate, and conflating them is what four earlier attempts got wrong. The owner is a minted port-independent UUID recorded under `$MOLD_HOME/queue-owners/`; each record also carries the instance id that last held it; the lock proves only that the owner is running right now and never confers ownership. The requirement cannot be met from intrinsic state alone — two servers sharing a root differ only by port, so port-independence and per-server distinctness are contradictory — so a returning server is recognised by the recorded hint, not derived. Hint match ⇒ mine. No match and exactly one unclaimed queue ⇒ the single-server port change, adopt and log loudly (the retention promise clients render at shutdown depends on this working). That rule is knowingly wrong in one direction: a genuinely NEW second server, started while the first is stopped against a root holding one retained queue, is indistinguishable from a port change and adopts it. Accepted deliberately — an announced adoption beats a silent orphan, because nothing tells the user a stranded job is never coming — and documented for operators in `website/guide/configuration.md`. Do not "fix" it by tightening rule 2 without replacing what it protects. No match and several ⇒ adopt none, mint fresh, report each orphan with queued and held counted separately, and let a human use `MOLD_QUEUE_ADOPT_OWNER`. Never "first unlocked wins". A failed idempotence check is never reported as "nothing completed"; replay skips the whole boot with rows unspent, since re-rendering a published print leaves an unmergeable duplicate. A stable device pin is persisted next to the ordinal and re-resolved at replay, because ordinals renumber. Replay is skipped entirely when the boot has no dispatch owner (maintenance mode drops the queue receiver), and a submission that fails hands the job back so its row is explicitly retained — a dropped `GenerationJob` drops its ticket, which deletes the row for work that never ran. Every publication path settles the row and stamps the key, including the CPU-only one, or replay re-renders its prints as duplicates. A submitted job also always runs once queued — `job_supervisor` owns the result channel so a disconnected client no longer trips the fifteen `is_closed()` gates — and only `DELETE /api/queue/:id` closes it early.
- **A degraded subsystem is a standing state, never one startup line.** The encrypted queue-media store holds `master.key`, so `queue_media_store.rs` refuses a path that is not owned by the current user at `0700` (`0600` for the key and the lock files) — correctly, and never self-healed, because a widened mode is evidence an operator should see. What it must never do is refuse opaquely: `insecure_private_path` names the OBSERVED uid and mode beside the expected ones and prints the exact `chown`/`chmod` for whichever half diverged — shell-quoted, with an option terminator, because `MOLD_HOME` may hold a space and an unquoted `/srv/Mold Data` is two operands — because anything that walks the mold root (an ACL pass, `chmod -R`, a restore that drops modes, `rsync` without `-p`) turns durable request media off and the required state alone sends the reader to the source. The refusal is then published from ONE place — `reconcile_claimed_owner` wraps its several early returns so readiness and its reasons are set together by `set_durable_media_status`, and the journal retains those reasons for the life of the process. Three surfaces read them and their split is deliberate: each reason is logged once at WARN in full (never a bare `issues = N` count); authenticated `/api/status.durable_media` carries `available` plus the reason prose; and auth-exempt `/health` carries a body naming only the degraded subsystem (`HEALTH_SUBSYSTEM_DURABLE_MEDIA`) because the reasons name host filesystem paths. `/health` stays **200 while degraded** — generation is unaffected, so failing it would pull a working server out of a load balancer — and it never awaits the config lock, because a liveness probe that can block behind a `/api/config` write gets a healthy server killed. `available` is true EXACTLY when `capabilities.durable_media` is present, which is why `durable_media_is_applicable` (gallery output on, `v2_authoritative`) is one helper that capability discovery, `/api/status`, and `/health` all read; `durable_media_status()` answers `None` rather than degraded whenever that gate or the durable queue itself is off, or every `MOLD_DB_DISABLE`, output-disabled, and observe-mode host reads as broken. Both halves of the reason list are bounded to a sample plus a count — reconciliation issues (one per inconsistent obligation) and held job ids alike — because the durable queue is deliberately not capped by `queue_capacity`, so enumerating either would put an unbounded string in the log and on every `/api/status` response for the life of the process; the full detail stays in `GET /api/queue`, which pages.
- **Fatal CUDA contexts are never reused or reset in-process** — illegal-address, uncorrectable-ECC, launch-failure/assert, and related faults permanently quarantine that worker and stop the server with an error so service supervision can restart the process; the embedded desktop must relaunch the whole app. Apply this to normal jobs, durable chains, admin loads, and post-upscalers, and reject buffered jobs before touching CUDA. In-process `cuDevicePrimaryCtxReset_v2` is unsafe while Candle/cudarc objects may retain primary-context handles; do not downgrade fatal errors to the timed cooldown. Quantized Qwen edit keeps split CFG even on high-VRAM CUDA cards.
- **Qwen-Image's quantized linear arm is chosen from the weight, never from the device alone** — and every way candle's kernels can decline lands in the same BF16-hostile fallback, so each is gated. `qwen_image/quantized_transformer.rs` splits that gate in two: `select_linear_kind` is a pure function of (device class, weight GGML dtype, weight `in_features`, weight residency, `MOLD_QWEN_QMATMUL`, `FORCE_DMMV`) for everything a weight settles at load, and `qmatmul_forward_supported` re-asks the activation-shaped half (rank 2 or 3; `FORCE_DMMV` again) per forward, degrading that one call to the retained dequant path. Metal has always used `QMatMul`; CUDA joins it only for a dtype `fast_mmq::supports` accepts whose row width its `qk` divides, resident on the activations' device, because the failures are errors rather than slowdowns — the `dequantize_matmul` fallback reads the activation as `f32` and rejects BF16, and a CPU-staged `QTensor` meeting the CUDA matmul is `unreachable!`, a panic. `FORCE_DMMV` is in that set because it is a **process-global** switch mold itself flips (`MOLD_WAN_FORCE_DMMV=1`, inside Wan's denoise loop) and never clears, and candle exposes no reader — `crate::quantized_dmmv` is the mold-owned mirror every writer must route through and every reader must consult. The `QMatMul` arm also normalizes its activation to `working_dtype` exactly as the dequant arm does (the CUDA kernels return the dtype they were fed, and the bias is materialized at `working_dtype`, so an F32 activation such as `TimestepProjEmbeddings`' would meet a BF16 bias) and materializes a non-contiguous one. The same rule is why the GGUF LoRA merge must land on the device — through `mold_candle::quantized::quantize_onto`, as every peer family does — and not on the CPU. FP8 (safetensors, not GGUF) is a separate path: `scale_weight` rides on the matmul output whenever it is a scalar or per-output row, so the forward keeps exactly one full-size pass, and the block-offload path widens FP8 weights once at load — unconditionally, since `candle_nn::linear` has no FP8 arm at all, which is why `MOLD_QWEN_FP8_CACHE` does not reach it.
- **Z-Image has a bespoke quantized transformer** — `zimage/quantized_transformer.rs` lives here (not candle); GGUF tensor naming differs from BF16 (`attention.qkv` vs split Q/K/V, etc.). Its linears dispatch per backend through `select_linear_kind`: CUDA defaults to a per-forward dequant arm because candle's fast MMQ kernels return non-finite values for Z-Image's linears (solid-black renders — the same defect family as `docs/architecture/qwen-mmq-nan.md`, which records the Z-Image evidence); Metal and CPU keep `QMatMul`, the arm the #942 sd.cpp validation qualified. `MOLD_ZIMAGE_QMATMUL=1` re-enables the CUDA fast path for the kernel investigation. GGUF transformers always stay quantized at rest; the unplanned dense-map diagnostic route was removed in #1109. Any env var read through `crate::runtime_env::value` MUST be listed in `ENGINE_SHAPING_VARIABLES` plus a mold-server `runtime_semantic_variable` arm or it silently reads as unset.

- **Wan's chain carryover is a property of the checkpoint, never the family.** Wan has no latent motion tail: its smooth handoff is last-frame _image_ conditioning, which only an image-conditioned checkpoint accepts. `mold_inference::chain::wan_carryover` is a total function of the `source_image` contract `wan::pipeline::source_image_capability` derives from the checkpoint's own headers — `Required` (A14B I2V 36-channel concat) and `Optional` (TI2V-5B latent inpaint) continue, `Unsupported` (text-to-video) concatenates independent clips, and an unclassified checkpoint is "unknown" and takes the conservative path. `capability_for_family("wan")` is the floor, not the answer; callers holding a concrete model use `capability_for_model`. The seam duplicates exactly `WAN_HANDOFF_DUPLICATED_FRAMES` = **1** frame — the one the continuation was seeded with — which is deliberately not LTX-2's 17, the pixel window its VAE turns into three latent slots. That constant lives in `mold_core::validation` (the engine re-exports it) because admission, `/api/models`, and the CLI chain planner must all derive from one authority: `default_extend_overlap_frames_for_family` resolves the extend default from it, so wan advertises and defaults to 1 while LTX-2 keeps 17 — a family-blind 17 sits on wan's `4k+1` grid, clears validation, and then fails in the engine after the load is paid for. - **LTX-2's runtime session outlives the generation, but holds almost nothing (#1099).** Plain T2V writes its `Ltx2RuntimeSession` back after a successful render (mirroring the audio/chain paths; `MOLD_LTX2_KEEP_SESSION=0` opts out — read via `std::env`, deliberately not a fingerprint input). The session retains only the cached prompt encoding and device handle: the Gemma encoder is consumed on the first `prepare()` to free memory for the transformer, and neither transformer nor VAE lives in the session. So reuse (`can_reuse_for`, exact token-pair match) skips the ~24 GB Gemma reload for same-prompt repeats only; a changed prompt pays a full rebuild, and no admission-side residency credit exists because nothing large stays resident. A failed prepare/render drops the session — rebuilding is the recovery path. `unload()` (ModelCache eviction) releases it. **Host-RAM admission charges only irreclaimable bytes.** A CPU-placed BF16 Gemma reserves the streaming anon-heap peak alone (`ltx2::cpu_gemma_streaming_anon_peak_bytes`, pinned to the `device.rs` BF16 arithmetic ×F32) and **not** its shard bytes: `load_from_assets` builds through `new_streaming`, so the shards stay an mmap'd `VarBuilder` whose file-backed pages are reclaimable and are already counted as free by `MemAvailable`, the ledger's own input. Charging them asks for ~24 GB of free anonymous room for memory that cannot OOM, and refuses every job on a host whose headroom lands just under the sum (#1108, regression-tested at hal9000's exact numbers). A flat 2× estimate is wrong in the same direction and parks the host that reported #1099 (also regression-tested). The GGUF Gemma keeps quantized residency in host RAM and every other family's CPU-parked encoder is copied there, so both still reserve their bytes — the predicate is `ltx2_cpu_gemma_streams_from_mmap`, never the family alone.

Before changing an LTX engine or arguing about correct behaviour, read upstream rather than inferring intent from mold's port. Clone it to a scratch location and pull before consulting it (the repo moves fast; `packages/ltx-core` is the inference core and `packages/ltx-pipelines` holds the pipeline drivers plus the documented CLI flags). Keep the clone out of the worktree — `tmp/` is gitignored and is where the existing checkout lives. Cite upstream `file:line` when a change is justified by it. GGUF tiers run on Metal — the old "GGUF stays CUDA-only" scoping was about kernel existence, which is complete.

- **LTX-2's spatial ceiling is the trained RoPE span, and past it stage 2 tiles.** `positional_embedding_max_pos = [20, 2048, 2048]` normalizes pixel positions, so an axis past 2048 px is out of distribution — it renders, badly, without erroring. `ltx2/tiling.rs` owns the arithmetic (interval splitting, the trapezoidal window whose ramps sum to one across an overlap, tile enumeration, and the `SpatialTilePolicy` both consumers resolve); `runtime.rs`'s `TiledStage2Pass` owns execution: per-tile latent slice, positions built at the tile's own pixel shape (mold's equivalent of upstream `normalize_positions=True`), noise seeded `seed + tile_index`, conditioning sliced by the tile and by `reference_downscale_factor`, then `index_add` accumulation in token space. `--spatial-tile` / `MOLD_LTX2_SPATIAL_TILE` is one knob over both stage 2 and the VAE decode: `auto` (default) can only engage past 2048 px, so nothing currently renderable changes; `off` restores the untiled path; `<px>[:<overlap>]` forces a size, which is the only way to compare tiled against untiled at a resolution needing neither. Two invariants: a one-tile plan must stay bit-identical to the pre-tiling path (it short-circuits before the blend), and a tiled stage 2 refines video only, carrying stage 1's audio through unrefined — upstream's `hdr_ic_lora.py:504-507` runs "a tile-sized `ModalitySpec` for video only", and `Stage2AudioInputs` switches shape, latents, noise, positions, and context off as one unit because half a branch makes the transformer reject the step. Do not add a normalization pass to the blend — if the windows do not already sum to one the layout is wrong, and `clamp_dimension_tiling` refuses the triple-overlap layouts where upstream's own clamp does not.
- **LTX-2's resolution ceiling is a property of the render, not the family.** The checkpoints normalize RoPE pixel positions by 2048 px, so that span bounds _one un-tiled denoise_. A checkpoint that ships the spatial upsampler never denoises the requested shape — it renders stage 1 at half the target (`derive_stage1_render_shape`), doubles that latent with the learned upsampler, and refines it over tiles (`plan_stage2_tiling`), so its ceiling is `LTX2_COMPOSED_MAX_AXIS_PIXELS` = 2 x the span = 4096 px, with `LTX2_COMPOSED_MAX_PIXELS` = 4096x2176. The factor of two is exact, not a margin: mold applies one spatial rung, so 4096 is the widest target whose halved stage 1 still lands inside the span. Resolve it through `mold_core::validation::ltx2_spatial_composition(model, pipeline)` — never by family — which requires both a manifest `SpatialUpscaler` component and `Ltx2PipelineMode::refines_spatially()`; `ltx2::runtime::pipeline_uses_two_stage_spatial_refinement` delegates to that same predicate so admission and execution cannot drift. `/api/models` advertises per-model `max_pixels` + additive `max_axis_pixels` and omits composed rungs from `recommended_dimensions` for a checkpoint that cannot reach them; clients read those and keep the family constants only as the single-pass fallback. `LTX2_OUTPUT_RUNGS` names the ladder (1280x704 → 3840x2112, every rung /64 so the halved shape lands on the VAE's /32 grid) and its `stage1_shape()` / `stage2_tiles()` are pinned to the engine's own arithmetic by a test in `ltx2/tiling.rs`. The ceiling belongs to the **rung**, not the checkpoint: `--spatial-upscale x1.5` only divides by 1.5, so it reaches 3072px, and `validate_ltx2_stage1_span` checks the derived stage-1 shape rather than trusting the x2 ceiling. Resolve the pipeline through `ltx2_spatial_composition_for_request`, which mirrors `select_pipeline`'s implicit branch order — a request carrying `retake_range` routes to the single-pass retake before the upsampler fallback is reached. **The ladder stops below the generation ceiling on purpose**: admission allows 4096px, but the bundled OpenH264 encoder refuses past 3840x2160, so 3840x2176 renders correctly and then fails at save time — the rung rounds 2160 _down_ to 2112, which is upstream's own `CENTER_CROP` alignment. Measured on an RTX 4090 at 25 frames, 1080p/1440p/4K all peak near 18 GB because the composition bounds the forward pass; 4K needs `--spatial-tile 768` (the default 1280px tile OOMs in the VAE decode). Never let `--spatial-tile off` past the span render — it must fail.

- **Extend is the chain motion-tail handoff with a file-backed carryover.** `GenerateRequest.extend_video` / `extend_video_path` continue an existing clip in one request: the last `extend_overlap_frames` pixel frames are re-encoded through the video VAE as conditioning, `Ltx2Engine::extend_inner` routes through the existing `render_chain_stage`, and `stitch_extend_frames` drops the render's leading overlap (a duplicate of the tail) before appending. (3) The ArcFace embedding is the raw 512-d network output — `pipeline_flux.py:130`/`:156-158` never normalize it, in visible contrast to the EVA branch at `:177-178` that does — so handing #1229 a unit vector silently rescales the IDFormer's input; `l2_normalized()` exists for cosine comparisons only. (4) The pixel ops are OpenCV's conventions reimplemented in `identity/warp.rs`, not `image::imageops` (whose triangle support scales with the ratio) and not `imageproc` (a candle-workspace dep, not a mold one). (5) Both graphs are re-authenticated against the manifest pin on EVERY load, before decoding, against the digest of the EXACT bytes decoded — one BOUNDED `read_to_end`, hashed, compared, parsed, enforced by the private `AuthenticatedBytes` type and a structural test, because hashing a descriptor and then reading it is two passes and an in-place write between them authenticates one set of bytes and executes another; the bound is the manifest's own `size_bytes`, carried with the digest in one `PinnedArtifact` and checked by `fstat` BEFORE the read (a digest needs bytes in memory, so an unbounded read of an oversized replacement OOMs before it can report the mismatch), with `expected + 1` as the read cap so a file growing mid-read is refused rather than truncated, and `UNPINNED_MAX_BYTES` (1 GiB) for the tools that load arbitrary graphs; the downloader's `.sha256-verified` marker attests to the bytes that landed, not the bytes now, and `IdentityExtractor` has no unverified constructor. (6) `extract` decodes through `img_utils::decode_oriented_srgb`, the crate's single EXIF/ICC path (lifted out of `ltx2/preprocess.rs`, which re-exports it) — a phone photo stores its rotation in a tag, and an unoriented buffer hands SCRFD a sideways face. Deliberate, measured deviations: the 512 crop uses SCRFD's landmarks rather than facexlib's RetinaFace, and replaces `cv2.LMEDS` with its least-squares refinement (measured max element delta 1.14e-5). Enabling `pulid` needs `protoc` at build time — it is in the devshell; whichever issue first ships the feature must add `pkgs.protobuf` to the crane `nativeBuildInputs` and to CI.
- **PuLID's face crop is masked before the tower sees it, and the parser is a candle port because the op gate said so.** `pipeline_flux.py:161-170` is one policy in `identity/parsing.rs`: facexlib's BiSeNet segments the aligned 512 crop, the background labels `[0, 16, 18, 7, 8, 9, 14, 15]` (hair, 17, is NOT one) become exact white, and the face becomes Rec. 601 greyscale — the tower conditions on shape, never colour. The parser's own input takes the **ImageNet** statistics while the tower's takes the **OpenAI CLIP** ones, on the same crop; two normalizations, one image. The final logit upsample and its argmax are FUSED (`bilinear_align_corners_argmax`) because interpolating logits can elect a class that wins at no low-resolution sample, so upsampling the labels instead is a different function rather than an optimization. It is a candle port and not a fourth ONNX graph because the same machine-derived Step-0 gate — `pulid_face_probe gate <graph.onnx>` — refuses a real opset-11 export on three counts that are missing evaluators rather than exporter idioms: `MaxPool` pads, `Resize mode=linear`, and `Resize coordinate_transformation_mode=align_corners`. Its weights are facexlib's own pinned release, converted once to safetensors through `encoders/pickle_convert.rs` (formerly `eva_clip_convert.rs`, now describing each conversion as data) — and that release is a **legacy** pre-1.6 `torch.save` archive candle cannot read, so `encoders/legacy_pth.rs` reads the container while candle's own `Stack` still parses every pickle in it. Pinning a stranger's re-save was the alternative and is not one. **Both derived artifacts reach their loaders as `AuthenticatedArtifact` — resolved once through a retained `Dir` descriptor, `fstat`ed against a pinned length, read once into a PRIVATE buffer under a `size + 1` bound, hashed there, and handed to the `VarBuilder` as those same bytes — never as a `PathBuf` and never as a shared mapping.** Both halves are load-bearing: a pathname resolves one name twice and a rename needs only the PARENT's write bit, while a mapping is a live view and collaborative `0664` weights mean another member may write the inode in place after the digest — descriptor retention proves which inode, never which bytes. The parser's production code names no path type at all and none of the four files in the chain names a mapping type; structural tests keep it that way. The PuLID adapter stays a pathname load on purpose: it is a manifest file verified at download, with no fresher authentication to discard. **RetinaFace stays unimplemented on evidence, not on deferral**: with the mask in place, swapping SCRFD's landmarks for facexlib's moves the final identity by at most 2.8e-3 of peak, against the 1.2–1.5e-2 the mask itself was worth. Mold runs ONE detection and gives the same face to both crops — upstream takes the largest for ArcFace and the most CENTRAL for the 512 crop, from two detectors, so on a group photograph its two halves describe two people. Numbers, the gate output, and the acceptance pins: `docs/architecture/pulid-face-extraction.md`. The bundle is now five files: `pulid_assets::PulidPaths` resolves the parser's `.pth` alongside the adapter, EVA tower, detector, and recognizer, and `IdentityAssetDigests` carries a fifth digest — the derived parser — so a different parser is a different identity.
- **PuLID's identity encoders are a port, and the EVA02-CLIP release is converted before it is ever loaded.** `encoders/eva_clip_vision.rs` ports `ToTheBeginning/PuLID`'s `eva_clip/eva_vit_model.py`; candle's `eva2.rs` shares the attention/SwiGLU shapes but is a fixed-448 classifier with a different layout and no hidden-state taps. Four things are silently wrong if ported from memory: RoPE is 2D over a 16x16 trained grid interpolated to 24x24 **entirely through the position ramp**, its `rotate_half` pairs **adjacent** lanes (not split halves), it is applied to patch tokens only and never to CLS, and attention is sub-LN with `q_bias`/`v_bias` supplied out of band and **no k bias at all**. The five hidden states are the residual stream **entering** blocks 4/8/12/16/20, not their outputs (`eva_vit_model.py:526` appends before running the block), and the MLP hidden width is `int(1024 * 2.6667)` = **2730**. The CLIP projection's L2 normalization stays in the tower's working dtype — upstream's `torch.norm`/`torch.div` run on a `weight_dtype` tensor (`pipeline_flux.py:176-179`), so widening to f32 is a divergence, not an improvement. Preprocessing is torchvision's _antialiased_ bicubic with Keys `a = -0.5` — not the -0.75 of PyTorch's plain bicubic, and not the `image` crate's `CatmullRom` — on the float tensor, unclamped. BAAI ships the tower as a torch pickle and **mold's runtime never reads a pickle**: `encoders/pickle_convert.rs` (renamed from `eva_clip_convert.rs` once it also converted facexlib's BiSeNet release) is the only place one is opened, converting once to vision-only safetensors from the SHA-verified source; the EVA tower's modern zip container and the BiSeNet parser's legacy pre-1.6 `torch.save` archive (`encoders/legacy_pth.rs`) share this one authenticated conversion path. Three rules make that load authentic and none is optional. The source is parsed from a **private copy made from the retained descriptor** and hashed on that same stream, because candle's `PthTensors` re-opens by pathname per tensor — a descriptor hash plus a pathname parse authenticates nothing, an inode re-check only samples the name at two instants, and `/dev/fd/N` is `dup(N)` on macOS so candle's second open reads an exhausted offset. That copy is staged under `$XDG_RUNTIME_DIR`/`$TMPDIR` and **never in the model root**, because a `0o700` directory is only as private as its parent: renaming an entry needs write permission on the CONTAINING directory, so a group-writable model root lets another member swap the verified copy for unpinned bytes before the pickle parser reads it (`secure_dir::parent_policy` tests STICKY FIRST — sticky owned by us or root is safe however open the write bits are, and checking ownership first rejects root-owned `1777` `/tmp`, the only candidate on a headless box with neither var set; a sticky directory owned by another unprivileged user is still refused because sticky lets the directory's owner rename entries, and a non-sticky one must be ours and unwritable by group/other. No `MOLD_*` var, `TMPDIR` is the knob, and free space is checked before the 856 MB copy). Every publish is a **`renameat` between retained directory descriptors**, out of an exclusively created 0o700 staging directory — never `std::fs::write`, which follows a pre-planted symlink at the destination, and never a pathname `rename`, because renaming an entry needs write permission on the PARENT, so a group-writable model root lets another member swap the staging directory between the hash and the publish (`encoders/secure_dir.rs` owns the primitive; the published file's `(dev, ino)` is re-verified through the parent descriptor afterwards). And reuse is authenticated by the compiled-in `DERIVED_SHA256`, never by the sidecar, which mold writes and an attacker could forge to match. `flux/pulid_encoder.rs` is the IDFormer; its `proj_out` is a bare parameter used as `latents @ proj_out` and must never be transposed like an `nn.Linear` weight, the five identity tokens stay in **every** scale's key/value context, and its softmax is widened to f32 and cast back (`encoders_transformer.py:114`) — worth 4x in BF16, and deliberately NOT done in the EVA02 tower, whose upstream softmax carries no cast. Parity goldens, the full tensor mapping, and the measured tolerances live in `crates/mold-inference/testdata/pulid/README.md`; the lifecycle is `docs/architecture/pulid.md`.
- **PuLID face extraction runs inside the lease, on the render's own device, and it is a typed scheduler phase.** #1223 ran it at admission on the host for two reasons that have both expired: `candle-onnx` could not place a tensor off the CPU (#1227 phase 1 replaced it with resident candle ports), and a pre-lease phase cannot overlap the T5/CLIP encode peak by construction. Phase 2 traded the second for its cost — `docs/architecture/pulid-perf.md` §4 measured one extraction at 2,840 ms of which the EVA02-CLIP tower alone was 79% — and moved the whole stack (detector, recognizer, BiSeNet parser, tower, IDFormer) into the leased job as `ProgressPhase::IdentityExtract`, emitted **before the model load**, not merely before prompt encode. That ordering IS the drop-before-adapter rule: every one of those five is built, forwarded, and fully released in turn, so on a cold load none coexists with the transformer, let alone with the ~1.14 GB adapter `EngineIdentityState` makes resident. A warm engine cache does have the transformer resident, which is exactly why `memory_preflight::IDENTITY_EXTRACTION_VRAM_OVERHEAD_BYTES` (= `mold_core::identity::EXTRACTION_DEVICE_PEAK_BYTES`) is charged ADDITIVELY beside `IDENTITY_VRAM_OVERHEAD_BYTES` rather than as a maximum. Metal charges it ONCE through the unified device gate and nothing to the host ledger; on CUDA the host side is only the private authenticated copy the `VarBuilder` reads from, which the identity artifacts' own `is_host_only` component roles already charge. `ExtractionSlot`'s bespoke semaphore-plus-`ram_snapshot()` is RETIRED, not run beside the ledger — its own justification was "extraction happens strictly BEFORE this job has a lease", which expired with the call site, and two admission-time memory gates that can disagree is worse than one (`no_second_memory_gate_lives_in_this_module` is the structural pin). Serialization comes free: a lease is already exclusive on its device. "Exactly once per parent" is unchanged and still counted — the first sibling to reach a device extracts, the rest are answered by the cache without opening a model, and a re-prepared batch child still carries its parent's frozen value. The forced-local CLI runs the identical `mold_server::identity_extraction::resolve_identity_for_lease` at the identical point, so a CPU-only local device is just the `ExtractionPlacement::Host` arm of the same code. The tower's working dtype is `identity::extraction::eva_working_dtype`: f32 on the host (candle has no narrow CPU kernels, and every committed golden was captured there), f16 on a device — the dtype the derived file already stores, and narrower than upstream's own cast (`PuLID/pulid/pipeline_flux.py:60`, `PuLID/app_flux.py:45`). The IDFormer half computes in f32 whatever the tower did. Device and host agree on the final tokens to a measured **3.82e-5** of peak, inside the 5e-5 the whole-stack golden already states; no new tolerance was invented. Measured on halcyon (M4 Max, 5-warmup / 20-run): whole extraction **3,073.6 → 1,907.3 ms** on the CPU (the memo alone) and **395.3 ms** on Metal. CUDA is measured on plato (L40S): whole extraction **573.2 ms** on a quiet box and **688–795 ms** under normal load, device peak **637.5–643.8 MB** against a 700,000,000 charge, parity worst **4.908e-5** (98% of the 5e-5 budget, against Metal's 76%) — a future change to the tower's CUDA arithmetic fails there first, and the constant must not be loosened in response.
- **A verified derived artifact is proven once per process, never once per request.** `encoders::pickle_convert::open_authenticated` memoizes its SHA-256 pass on the file's own `(dev, ino, size, mtime, ctime)` identity PLUS the pin, re-read from the SAME retained descriptor after the private copy is taken; a mismatch falls through to an ordinary full read-and-hash. This is `mold_core::download::pinned_file_digest`'s memo applied to the one artifact that reads its bytes privately, and `ctime` is the load-bearing field — `utimensat` lets an owner set `mtime` to anything, but no userspace call holds `ctime` still across a write. The private-read-then-build contract in `AuthenticatedArtifact` is UNCHANGED: the copy is still what the `VarBuilder` reads, and the memo only ever removes a pass over it. Never degrade it to a "we checked once" flag, and never key it on the pathname — the whole point of the compiled-in `DERIVED_SHA256` is that a group-writable model root may change the file underneath us. It is worth **1,073 ms of a 3,074 ms extraction** on halcyon, because the 609 MB re-hash was the single largest line item in the entire PuLID pipeline and the drop-and-reload rule re-paid it on every conditioned request.
- **One identity photograph is extracted once per process, and the cache key is the whole pipeline.** `mold_inference::identity::extraction` holds a 16-entry LRU (fixed 256 KiB each, ~4.2 MB) of final `[1, 32, 2048]` tokens keyed by `mold_core::identity::identity_cache_key` — the photograph's SHA-256, `IDENTITY_PIPELINE_VERSION`, and all five asset digests, composed the way `fingerprint_of` composes the output fingerprint but over inputs knowable BEFORE anything is opened (`pinned_asset_digests`). **Bump `IDENTITY_PIPELINE_VERSION` in the same PR as any semantic change to SCRFD, the alignment, the warp, ArcFace, the EVA preprocessing, the tower, the mask, or the IDFormer** — it is the one invalidation case that is not structural, because none of those files moves. The key carries no device, deliberately: host and device agree to a measured tolerance rather than bit-for-bit, so keying on the device would give one fleet several fingerprints for one face. The unconditional true-CFG identity is a SEPARATE degenerate memo on the adapter digest, because it is a pure function of the checkpoint (`pipeline_flux.py:188-192`) and would otherwise force a cached request to materialize the 605 MB `pulid_encoder.*` half for a tensor that never varies; that is why its zeros are shaped from the tower's declared geometry rather than a live output. In-process only and never persisted: these are a biometric derivative, and `pulid-perf.md` §2's argument against persistence is a retention story, not a performance one. Cold 2,184.8 ms → warm 1.8 ms, opening no models at all.
- **The identity cache is SINGLE-FLIGHT, because the callers are sibling GPU threads.** A plain get/put was right while extraction ran once per parent at admission; post-lease, a `batch_size = 4` parent's children are dispatched together and all four miss a cold cache in the window between the get and the put — N times the work, and N embeddings differing at the measured 3.82e-5 device tolerance, i.e. four siblings of one print conditioned on four slightly different faces with four different frozen fingerprints. The miss path therefore takes a per-key lock and a waiter **re-reads the cache and takes the winner's tokens** rather than computing its own; sibling embeddings are byte-identical by construction. Locks are taken in SORTED key order (a multi-photograph set takes several, and two requests sharing a subset in different orders would deadlock), the unconditional identity has its own flight key because its value reaches the fingerprint, and a failed flight stores nothing and releases the key — never negative-cache an extraction failure. The children need no frozen key from the parent: the key is a pure function of the bytes each child already carries, so content addressing already gives them one, and a second copy in the plan would be an authority that could disagree with those bytes. `identity_extraction_count` counts what was COMPOSED and `ResolvedIdentity::extracted` carries that to the server, so the once-per-parent counter is checkable again AND `ProgressPhase::IdentityExtract` is emitted only by the sibling that did the work — a cache hit reporting its ~2 ms would drag `ewma_identity_extract_ms` to a figure no cold request could meet. An uncond-only miss (first true-CFG request after an ordinary one) loads the IDFormer alone and never the face stack: 60.6 ms against ~340 ms.
- **An identity extraction failure is classified before it touches worker health.** Phase 2 put the extraction on the leased GPU, so its failures now reach the reliability counter that takes a sick card out of rotation. `IdentityError::is_user_input` is the authority — `NoFaceDetected`, `Decode`, `Alignment` are about the photograph and reproducible on every card; only `Runtime` is device-attributable — and `IdentityFailure` carries that attribution to `settle_identity_extraction_failure`, which quarantines on a fatal CUDA context, counts a device failure, and counts NOTHING for an unusable photograph. Three faceless images must not degrade a single-GPU host for a minute.
- **The derived-artifact memo is fenced on timestamp granularity.** Its key is metadata, so `ArtifactIdentity::is_fine_grained` refuses to memoize when both nanosecond fields are zero (the signature of a one-second-granularity filesystem), and the key is re-read from the same retained descriptor AFTER the private copy with both readings required to agree. What remains — a same-length write inside one nanosecond, with `ctime` not settable from userspace — is exactly `mold_core::download::pinned_file_digest`'s residual, which already guards every model weight mold loads.
- **Identity installation is once per dispatch, and its lifetime is the whole invariant.** When the effective `id_weight` is above zero, `mold_core::identity` owns the contract (qualified tiers `flux-dev:q4`/`:q8`, the `0.0..=3.0` weight, the bounded decode limits, and `IDENTITY_RUNTIME_READY`, which is now `true` so a `pulid` build both advertises and executes). The reference photograph resolves into the immutable `FrozenIdentityEmbedding` (plain little-endian `f32` plus the source SHA-256s — one per photograph, in request order for the plural `id_images` form — the five asset digests including the derived BiSeNet parser, an optional unconditional embedding for true CFG, and a fingerprint over sources/assets/values) inside the leased job, as described above — never at admission any more. What admission still does is thread an `IdentityPin` cell onto `PreparedExecutionInputs` and pre-fill it whenever preparation already holds the answer, so "one extraction per parent, reused by every sibling on every device" stays structural without a second CPU-side extraction. The scheduler re-prepares dependencies for EVERY pending job including batch children, so a child is handed its parent's frozen value through `DependencyPreparationContext::frozen_identity` and skips extraction entirely; `compose_prepared_generation` carries it across as a backstop, and placement preview (`ExistingOnly`) extracts nothing at all. The GPU worker installs the resolved value through `InferenceEngine::install_identity_embedding` before EVERY dispatch and clears it otherwise — the engine is cached and the identity is not, so a stale embedding would condition the next print on the previous person; the default trait impl REFUSES a populated embedding rather than dropping it, and only `FluxEngine` overrides. Forced-local installs at the same point in `local_engine::build_local_engine_from_plan`, from the same `resolve_identity_for_lease` path the server's worker runs, which is what makes local/remote parity structural. Weight zero performs no pull, decode, load, or extraction and must stay byte-identical to an unconditioned render (the falsification case from `tmp/sdcpp/docs/pulid.md`). `EXTRACTION_HOST_PEAK_BYTES` (`mold_core::identity`) moved from 1.4 GB to 2.4 GB across #1227 phase 1 and #1225 together, and the two changes pull in opposite directions: the recognizer's 261 MB is now resident tensors rather than a retained `ModelProto` plus a per-call copy, so that transient half is gone, while the parser/tower conversion path adds a transient 609 MB (EVA tower) or 53 MB (BiSeNet parser) private copy, plus the EVA02-CLIP tower's f32 widening (~1.2 GB) that `VarBuilder`'s `DType::F32` always performed but the old figure never charged. The honest number is bigger even though the recognizer got cheaper; since phase 2 retired `ExtractionSlot` this constant describes the `ExtractionPlacement::Host` path specifically rather than gating an admission-time semaphore. Memory is measured, not declared: `IDENTITY_VRAM_OVERHEAD_BYTES` is 1.25 GB (the adapter's own resident arithmetic plus bounded cross-attention activations, resident for the whole denoise), and the detector, recognizer, EVA02-CLIP tower, and BiSeNet parser stay `is_host_only` in the memory model — their own bytes are charged as host demand rather than a per-component VRAM term — even though phase 2 now runs them on the leased device during extraction; that device-side cost is instead the flat, additive `EXTRACTION_DEVICE_PEAK_BYTES` charged beside them (the bullets above). The CLI reads `--id-image` through `commands::identity`: `open_regular_file_no_follow`, bounded from the descriptor before allocating, read from that exact descriptor, then `validate_id_image_bytes` — all before any request bytes exist; `id_image_name` is the file's own name and never the client path. The `pulid` feature ships ON in every release recipe (`flake.nix`, `release.yml`, both source PKGBUILDs, which now need `protobuf`/`protoc` for `candle-onnx`'s `prost-build`); the feature only decides whether the binary LINKS the stack, and the licence gate is the recorded InsightFace acceptance enforced at download time. `mold rm

## Inference modes (`mold run`)

1. **Remote** (default) — HTTP to `$MOLD_HOST` (default `http://localhost:7680`).
2. **Local fallback** — server unreachable → local GPU (auto-pulls model if missing).
3. **Forced local** — `--local` skips the server attempt.

`mold run [MODEL] [PROMPT]` disambiguates the first positional at runtime: matches a known model name → model, otherwise → prompt.

**Pipe-friendly**: `echo "a cat" | mold run flux2-klein | viu -`. stdin for prompt, stdout for image bytes when not a TTY. `--output -` forces stdout; `--image -` reads source from stdin. `IsTerminal` detection + SIGPIPE reset to default + `status!` macro route text to stderr.

**Name resolution** (`manifest::resolve_model_name`): `model:tag` (e.g. `flux-dev:q4`); bare names try `:q8` → `:fp16` → `:bf16` → `:fp8`; legacy dash `flux-dev-q4` resolves to colon form.

## Multi-prompt chain authoring

- `mold run --script shot.toml` — canonical TOML, schema `mold.chain.v1`. Per-stage `prompt` / `frames` / `transition`.
- `mold chain validate shot.toml` or `mold run --script ... --dry-run` to inspect without submitting.
- Sugar: `mold run <model> --prompt "..." --prompt "..." --frames-per-clip 97` (uniform smooth only).
- Transitions: `smooth` (default, motion-tail morph), `cut` (fresh latent), `fade` (cut + RGB crossfade).
- Per-stage source images: `source_image_path` (relative to script file) or `source_image_b64`. Resolved by `mold_core::chain_toml::read_script_resolving_paths`.

## Config

Two stores, one logical `Config` view:

| Surface                                                              | Owns                                                                                     |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `~/.config/mold/config.toml` (XDG) or `~/.mold/config.toml` (legacy) | Bootstrap: paths, ports, credentials, `[logging]`, `[runpod]`, per-model component paths |
| `mold.db` `settings` + `model_prefs`                                 | User prefs: `expand.*`, `generate.*`, `tui.*`, per-model defaults                        |
| `MOLD_*` env vars                                                    | Runtime override (highest precedence)                                                    |

Every `main()` calls `mold_db::config_sync::install_config_post_load_hook()`, which runs a one-shot idempotent `config.toml → DB` migration on first boot (renames original to `config.toml.migrated`) and overlays DB onto every `Config::load_or_default()`. Consumers still read `cfg.expand.*` unchanged.

`mold config set <key> <val>` routes by key prefix (`expand.*` → DB, `models_dir` → TOML). `mold config where <key>` prints the surface. `mold config list --json` tags each row `[db]` / `[file]` / `[env]`. Multi-profile: `settings` and `model_prefs` are keyed on `(profile, key)`; active profile resolves `MOLD_PROFILE` → `settings.profile.active` → `"default"`.

## Metadata DB

`MOLD_HOME/mold.db` (override: `MOLD_DB_PATH`; disable: `MOLD_DB_DISABLE=1`). Current `SCHEMA_VERSION` lives in `crates/mold-db/src/migrations.rs`. Tables: `generations` (gallery rows), `settings` (KV, profile-scoped), `model_prefs` (per-resolved-model generation params, profile-scoped), `prompt_history`, machine-wide `device_preferences` (absent row = enabled by default; discovery never writes), and the library-organization side tables `tags`, `generation_tags`, `collections`, `collection_items` (schema v20; FK `generations(id) ON DELETE CASCADE`; tag names `COLLATE NOCASE`, collections merge across hosts by `slug`). Schema **v22** adds `scheduler_estimates.ewma_identity_extract_ms`, the learned runtime for `ProgressPhase::IdentityExtract` (#1227 phase 2), appended after every existing column so no `SELECT` index moves. Migrations are forward-only via `PRAGMA user_version`; add to `MIGRATIONS[]` and bump `SCHEMA_VERSION`.

**Library organization and trash are per-host row state, never request state.** `generations.title` / `favorite` / `trashed_at_ms` are user-owned: `upsert_with_conn` excludes them from `ON CONFLICT DO UPDATE` (title is seeded once from `OutputMetadata.title` via `COALESCE`), so a reconcile/import refresh never resets them; `mold-db/src/organization.rs` and `trash.rs` are the only writers. Creation-time filing is the one thing a request seeds, and it is seed-once by construction: `GenerateRequest` / chain-body `tags` + `collection` ride `OutputMetadata` into `seed_creation_organization`, which runs only on `upsert_with_conn`'s INSERT branch, so a reconcile or re-publication never resurrects a tag the user removed. Embedded tags are re-normalized (bad ones dropped, never fatal) and the collection resolves by SLUG, created when absent, so one name means one collection across a fleet. `mold_core::organization` owns the wire rules (≤20 distinct tags post-normalization, 1..=64 scalars each, whitespace-controls collapsed and other controls refused, a leading `#` literal); clients compose the title auto-tag through `compose_client_tags` — the server never auto-tags — and a filing that cannot be applied (`MOLD_DB_DISABLE=1`, a `{id}` collection deleted between listing and admission) is dropped while the print publishes anyway, reported on `x-mold-request-warning` plus additive `request_warnings` on `GenerateResponse` / `ChainResponse`. Never split that header's value on `;` — advisory prose contains it. Trash = `<output_dir>/.trash/<filename>` + the row flag + a `<filename>.trash.json` tombstone carrying the row and its organization; reconcile validates trashed rows against `.trash/`, imports tombstoned files that lost their row, and never scans `.trash` as live. `DELETE /api/gallery/image/:filename` trashes and `?permanent=true` hard-deletes; the committed archive is NOT retired on trash (only on purge), and a restore un-retires nothing because nothing was retired — a live print already holding the name is a `409 GALLERY_RESTORE_CONFLICT`. `GET /api/gallery` applies organization and the `?view=library|trash` filter POST-overlay by filename, because `overlay_db_gallery` prefers archive records and re-adds archive filenames absent from DB rows. Retention is the one DB key `gallery.trash_retention_days` (`gallery.` ⇒ `Surface::Db`, env `MOLD_GALLERY_TRASH_RETENTION_DAYS`, 0 = forever, max 3650, default 30), read fresh by the hourly/startup sweeper and `POST /api/gallery/trash/sweep`; `capabilities.gallery = { can_delete, trash: { enabled, retention_days }, organize }` is absent/false under `MOLD_DB_DISABLE`. Titles ride `GenerateRequest.title` → `OutputMetadata.title` → the row, validated by `mold_core::validate_print_title` (trim, ≤120 chars, no control chars) and slugged into the default filename as `mold-{model}-{ts}[-{idx}]~{slug}.{ext}` (`title_slug`, `[a-z0-9-]{1,40}`; `strip_title_slug` before the legacy filename parser); renaming never renames the file. Download dialogs suggest `mold_core::download_file_name`'s `{title-slug}__{model}__s{seed}.{ext}` (independent components joined `__`, model slug capped at 80, fallback stem `print`) — a suggestion only, never a rename. `mold run --title/--tag/--collection/--no-auto-tag` (with the `generate.auto_tag_title` DB preference) and `mold trash list|restore|empty|sweep` are the CLI surfaces (HTTP to `$MOLD_HOST`, no local fallback). The TUI Library lists only live rows (`MetadataDb::list_live`), shows titles in the Details panel and full detail view, and its `d` moves to the trash — locally via `mold_db::trash` helpers when the metadata DB answered the scan, remotely via `MoldClient::trash_gallery_image` — degrading to honest hard-delete wording (`RemovalKind`) whenever any owning machine cannot trash; the Settings view edits `gallery.trash_retention_days` through the shared config_sync writer.

Gallery writes happen in the server (`queue.rs` upserts after disk write; background `reconcile(output_dir)` on startup), CLI (`crates/mold-cli/src/metadata_db.rs` via `record_local_save`), and TUI (`gallery_scan.rs`). DB is additive — embedded PNG/JPEG `mold:parameters` still get written, and open/upsert failures log and keep working. Open-time `quick_check` and query-time gallery corruption recovery quarantine `mold.db` plus WAL/SHM as `mold.db.corrupt-<timestamp>*` under a cross-process recovery lock, recreate the schema, and reconcile gallery rows from disk; the retained quarantine is the only source for manually salvaging settings/history.

Memory scales from the SAME `fl2va_observed` figures the FL2VA bounds do, by the quantity each term is a function of, so an unaffordable reference set is refused with numbers rather than by a list. **H3 audio is a family declaration, not a checkpoint probe.** `synchronized_audio: true` with `audio_disable_supported: false` means every H3 render carries audio and nothing can turn it off, so `/api/models[].supports_audio` and the profile recipe's `supports_audio` both derive from `mold_core::minimax_h3::capabilities(task)` through `catalog::declared_audio_capability` — on cold rows too, and in the private-runtime bridge row rather than a second literal there. `mold_inference::audio`'s probe registry deliberately has no `minimax-h3` arm: it answers checkpoint header questions (LTX-2's optional audio VAE + vocoder) and only for downloaded entries, which would leave the family's own contract null. Leaving it null is what forced every surface to hard-code H3's AV behaviour from the family name (#841). **The reviewed envelope's text-row ceiling is a PROMPT budget, not a transcribed observation.** The FL2VA conditioner sequence is `"<Picture 1>: "` + the endpoint's 1,008 merged vision pads + the prompt's own tokens, so `max_qwen_output_text_rows` = 2,048 leaves roughly a thousand prompt tokens; the earlier 1,058 was the qualifying render's own 1,050-row measurement and budgeted about forty, refusing every ordinary app prompt (#1245) even though the conditioner context is 262,144 tokens. `max_total_packed_rows` is derived from the four axes the prepared request sums, never transcribed beside it. An over-budget prompt is refused BEFORE the ~37 GB artifact pass, by a precheck whose reported budget is the ceiling minus the overhead the tokenizer actually produced — never a second constant — and the authenticated envelope check remains the backstop, naming every axis a refusal differs on rather than one bare sentence. **The compact envelope is a RULE, not a pinned shape.** `is_admitted_compact_canvas` is the one canvas authority — both axes on `VIDEO_ROW_STRIDE` (32 = the VAE's 16x spatial compression x the DiT's `patch_size [1,2,2]`), each at least `MIN_COMPACT_AXIS_PIXELS` (256), total area within `COMPACT_MAX_PIXELS` (1,032,192 = the area of 1344x768, the shape every memory bound was measured at), aspect inside the family's `MIN_ASPECT_RATIO..=MAX_ASPECT_RATIO`. The clip length is the family grid (`valid_frame_count`, 107..=345 on `17n+5` at the fixed 24 fps) and the base tag's step count is `COMPACT_MIN_STEPS..=COMPACT_MAX_STEPS` (2..=50; a Turbo tag keeps its distilled adapter's EXACT count, which is its schedule length rather than a qualification pin). `REVIEWED_COMPACT_CANVASES` survives as the RECOMMENDED preset list — a test pins every entry to the rule — and `REVIEWED_COMPACT_FRAMES` (aliased `DEFAULT_COMPACT_FRAMES`) as the default alone; `fixed_frames_for_model` answers `None`. The generation profile is a `Dynamic` range with those presets, never `Buckets` + `OffBucketPolicy::Reject`. The area ceiling is load-bearing beyond memory: one packed row is a 32x32 cell, so `rows = pixels/1024` and no admitted canvas can exceed the 1,008 rows the measured canvas packs — which is what keeps the measured conditioning ceilings ceilings, pinned exhaustively by `no_admitted_canvas_packs_more_rows_per_latent_than_the_default`. `public_runtime_envelope_for_shape(canvas, frames, steps)` derives its generated-side rows through `mold_core::minimax_h3`'s packed-row functions — the ONE authority `h3_admission` and `h3_factory` also charge against — and `public_runtime_bounds_for_shape` scales #827/#1245's observations by the quantity each term is a function of: attention/FFN by packed rows, audio decode by frames, and the video decode + condition encode by canvas AREA (the video VAE is temporally chunked at a fixed `tokens_per_chunk` over the full canvas, never spatially tiled, despite `decoder_tile_workspace_device_bytes`' name). Steps scale nothing — a step is time. The scaling passes through the same `public_runtime_bound` margin/64-MiB-grid policy, so at the measured shape the record is byte-identical (regression-pinned), and a 345-frame clip asks a ~24.3 GB device floor against 9.7 GB at the default: refused with numbers rather than by a list. `validate_shape` runs before everything in `validate_prepared_with_adapter`, so a request cannot mint an authority for a shape nobody would run. Source fitting renders the SOURCE's own aspect at the largest admitted size (`largest_admitted_compact_canvas`) instead of picking the nearest of two fixed canvases. The canvas refusal stays a DOOR check, never part of `validate_request_contract`: the engine's own `prepare_request` runs that contract on the tiny synthetic canvases its pipeline tests use, so the rule lives in `minimax_h3::validate_reviewed_canvas`, called by `validation::validate_h3_private_uat_request` for authenticated private ingress and reached by every ordinary client through the profile's range. Only 1344x768 and 768x768 at 124 frames are MEASURED (`docs/qualification/minimax-h3.md`); every other admitted shape rides a derived estimate.

**H3's Metal path is a correctness tier: it ships and is admitted, and it has never rendered (#1164, #1296).** The candle layer executes on Apple Silicon: `H3AttentionBackend::MetalChunkedDenseMath` runs the identical dense F32 arithmetic over query chunks sized by `H3_METAL_DENSE_CHUNK_MAX_SCORE_ELEMENTS`, because the unchunked `N x N` score matrix at released geometry is ~358 TiB and Metal has no FlashAttention kernel to escape to; the chunk is a pure function of the shape, frozen into the plan and hashed into its identity, so admission, the plan, and the executor cannot disagree. `metal_reduce` moved to `mold-candle` (mold-inference keeps a `crate::metal_reduce` alias) so the H3 audio VAE's rank-4 head mean folds like every other Metal-reachable reduction. INT8 ConvRot resolves through `select_h3_int8_linear_kind`, where Metal always takes the portable dequant arm — no Metal twin of the cuBLASLt kernel exists, and unlike Qwen-Image there is no candle Metal quantized kernel to qualify; NVFP4-AWQ has no native MATMUL kernel on any backend — the linear is always a full-precision `f32` matmul over a dequantized weight chunk — but since #1317 the DEQUANTIZATION is dispatched by `select_h3_nvfp4_linear_kind`: CUDA uploads the packed payload bytes and the unswizzled FP8 scale bytes and widens both on the device through `index_select` lookup tables, while Metal and CPU keep the host scalar loop. The two arms are bit-identical (`nvfp4_device_dequantize_is_bit_identical_to_the_host_loop`, and #1317's probe over all 115,605,504 elements of the shipped `attn.qkv_proj` weight), so this is a cost choice and never a numerical one; Metal is excluded only because no Apple device is in reach of that gate, which is the one thing a Metal arm would need. The device arm's one trap is candle's own: `candle-kernels/src/indexing.cu:60` reserves `max_value<I>()` as a zero-padding sentinel, so `U8` ids can never address a 256-entry table and `0xff` — an ordinary payload byte, two `-6.0` E2M1 nibbles — would silently decode to `0.0`; the ids are cast to `U32` on the device while the stored weight stays `U8` at rest. The FP8 block scales still reach no backend AS FP8: they are unswizzled on the host at their own one-byte width and widened through a 256-entry table (#1316 — an `f32` cache cost 4.57 GB of host RAM on the shipped conditioner for identical arithmetic), on the host per lookup or by gathering that same table on the device, so they never need a Metal or CUDA fp8 cast. `h3_nvfp4_weight_staging_bytes` is the one accounting authority for both arms and a memory authority must charge the larger. fp8-scaled linears are refused by name. `H3CandleBackendDevice::Metal` and `H3ConditionerExecution::MetalResident` exist and validate device-exactly (`matches_candle`, never a literal `is_cuda()`), and the factory input's compute capability is `Option` where `None` IS Metal. `h3` no longer implies `cuda` at any level — `h3-cuda` is the shipping CUDA edge, and `mold-server` gains no Metal forwarding feature because it has TWO exact reviewed public build graphs rather than one: `PUBLIC_H3_SERVER_FEATURES` (`h3` + `cuda` + `h3-cuda` + `h3-private-bridge` + `mp4` + `nvml`) and `PUBLIC_H3_METAL_SERVER_FEATURES` (`h3` + `metal` + `h3-private-bridge` + `mp4`, NVML absent because there is nothing NVIDIA to read), both pinned in `crates/mold-server/build_support/h3_server_features.rs` as exact sets rather than relaxations, so "CUDA optional" can never admit a build with neither device. Since #1323 the Metal route reaches a SHIPPED binary: `h3_admission` admits `GpuBackend::Cuda | GpuBackend::Metal` and places the conditioner through `AssignedMetalThenDrop`, `PUBLIC_RUNTIME_PROFILE_DECISION` is `supported-compact-fl2va-cuda-sm89-or-metal`, and the macOS release recipe builds `h3,metal` (`flake.nix`, `release.yml`) with macOS CI compiling both the forced-local and the reviewed Metal server recipe. What does NOT exist yet is a RENDER: a Metal attempt is refused below a unified-memory floor of `max(device floor, host floor)` before the artifact pass, the compact stack's ~42.5 GB unified working set stalls a 48 GB M4 Max, and hardware qualification (#1164, #1296) stays open — `metal: CorrectnessOnly` is the advertised tier and CPU is still refused. Ref2VA shares that device rule exactly (`supported-compact-ref2va-cuda-sm89-or-metal`), because backend applicability is a FAMILY declaration and a task-only Metal refusal would contradict the capability every client reads. `mold-core::minimax_h3` advertises `metal: CorrectnessOnly` for the path while `runtime_available` still gates whether any engine is registered. Everything else stays fail-closed: arbitrary raw H3 repositories, aliases, and manifests are rejected, catalog identities must pass the policy both before a raw `hf:` request and after opaque `cv:` metadata resolution, and weight presence never implies authorization. The #831 governance decision (recorded in `docs/architecture/minimax-h3-authorization.md`, delivered via #1085) permits H3 use universally — every territory, local/remote/shared/hosted, output distribution, and redistribution — with no H3-specific clickthrough, geolocation, generated-content label, or surface control required; the README and H3 user guide are the complete user-facing license/attribution/disclosure delivery. Re-review the pinned license (SHA-pinned, verifier-enforced) before every release that touches H3.

## Workflow

- **TDD.** Every bug fix and feature: failing test first, then code. Prefer unit tests on exported contracts (key→action maps, focus transitions, serialization round-trips, layout invariants) over E2E. Layout constants need a test that asserts the inner area fits the rendered row count — otherwise they drift.
- **Cancellation capability.** Current servers advertise `queue.cooperative_cancellation`: queued work and running singleton generations cancel through `DELETE /api/queue/:id`, with the worker stopping at the next model safe point. iPhone Host detail keeps its 44pt two-step action and exact Keychain-authenticated route for both states; older hosts keep running rows read-only. This supersedes the older queued-only mobile sentence above.
- **Port from upstream reference implementations, never from memory.** When implementing or debugging any model family, sampler, scheduler, VAE, or pipeline in Rust, consult the authoritative upstream implementation first — the official model repo (e.g. Wan-Video/Wan2.2, Lightricks/LTX-2, black-forest-labs/flux), ComfyUI, and/or Hugging Face diffusers — and mirror it. Clone references into gitignored `tmp/` and `git pull` before consulting; justify behavioural changes with upstream `file:line` citations rather than inferring intent from mold's existing port. Upstream is read-only reference material: the port itself is always pure Rust (candle) — never call into Python, link Python runtimes, shell out to upstream scripts, or add non-Rust dependencies to make a port work. Running upstream code in a scratch venv to capture golden fixtures/expected tensors for parity tests is fine; shipping any of it is not. Where mold deliberately tracks a different reference than the official repo (e.g. the Wan sampler follows the diffusers/Lightning flow-UniPC schedule, not upstream's `fm_solvers_unipc.py`), that choice is documented in this file — follow the documented reference and never silently switch it. **Prefer a reference you can run over one you can only read.** A code read establishes that a port "looks equivalent"; an executable oracle on the same hardware, fed the same checkpoint, tells you in one command whether the difference is yours. Where such an oracle exists it is the documented primary reference — Z-Image's is stable-diffusion.cpp (see the Z-Image entry above), which renders the same GGUF files mold downloads, on Metal, correctly. Reach for it before theorising about the backend, the file, or the quantization. The LTX-2 rule below is the template; it applies to every family.
- **Keep user and agent docs in sync with every feature:** a release note as `changelog.d/<slug>.md` (one Keep-a-Changelog bullet per PR — NEVER edit `CHANGELOG.md`'s `[Unreleased]` section by hand; two open PRs inserting at that line is what made every PR conflict, the release PR assembles and deletes the fragments, and the advisory `changelog` CI check flags direct edits (it is not a required status, so a red check is a request to fix, not a hard block) — `changelog.d/README.md` has the format; `skip-changelog` label for PRs that ship nothing user-visible), `README.md`, this file (`AGENTS.md` is its symlink), canonical `crates/mold-cli/src/skill/SKILL.md`, the owning app README such as `apps/mobile/README.md`, relevant `desktop/docs/`, and the VitePress `website/` pages/navigation. Model, CLI flag, env-var, endpoint, and native UI changes are incomplete until every affected surface agrees; do not maintain a divergent second agent-skill copy.
- **Releases are automated by release-plz** (`release-plz.toml`, `.github/workflows/release-plz.yml`). Every push to `main` maintains a release PR: release-plz bumps the shared `[workspace.package]` version (conventional commits decide the bump; `feat:` ⇒ minor on 0.x), then a scripted bot commit (`scripts/release/sync-release-pr.sh`) assembles every `changelog.d/*.md` fragment into `CHANGELOG.md` `[Unreleased]` (newest first, by the commit that added it), deletes the fragments, promotes `[Unreleased]` to the new version, syncs the desktop cargo root's version, and copies the promoted notes into the PR body — never bump versions or promote the changelog by hand. release-plz itself never touches `CHANGELOG.md` (`changelog_update = false`); the CI trusted-release-PR file-scope check allows exactly `D changelog.d/*.md` beyond the modified version files, and the release tag job refuses to tag while an unassembled fragment is still on `main` (a fragment merged between the release PR's last sync and its merge would otherwise ship its code now and its note next version). After that PR merges, `release-plz-release` waits for the exact main SHA's published notarized macOS Nightly and `VALID` TestFlight build, then pushes the `vX.Y.Z` tag that fans out to release.yml and FlakeHub. Tagged publication is priority-staged: signed/notarized Apple artifacts and the stable updater manifest publish first, native Linux archives and AUR follow their CUDA builds, and the lower-priority container matrix attaches exact digest/provenance metadata last. Best-effort Nix distribution builds run independently and populate Cachix; they never block native or Apple publication. Main publishes mutable rolling `latest*` image aliases. Stable `<version>*` container aliases are create-once and verified, but automatic Lambda/RunPod/desktop provisioning must consume the release's exact `mold-container-digests.json` `@sha256` reference and fail closed until it is available and consistent. Both workflow jobs authenticate as the `release-plz-mold` GitHub App (`RELEASE_PLZ_APP_ID`/`RELEASE_PLZ_APP_PRIVATE_KEY`) so CI runs on the release PR and the tag triggers workflows; the follow-up commit must retain that bot identity or release-plz will replace the PR to preserve human-authored history. Merging the release PR ships the release — treat it as outward-facing. Gotcha: release-plz refuses to run if any tracked file is also gitignored (`git ls-files -ci --exclude-standard` must stay empty).
- **Don't break centered TUI image protocols.** `crates/mold-tui/src/ui/gallery.rs` uses a fixed-protocol thumbnail path, and `ui/preview.rs` uses the same centered fixed-protocol rule for transient SSE denoise previews. Do not revert either path to plain `StatefulImage` for Kitty/Sixel/iTerm2 — it reintroduces top-left padding instead of centered aspect fit. A new preview frame must invalidate only the transient geometry cache; start, completion, and error clear it so latent pixels never become final-output authority. Keep the regression tests passing. The Mold Studio spec now defines the TUI as the fifth shell (spec §05 "Terminal surface", gap G13, mockup `docs/design/mold-tui-proposed.html`) — future TUI restyling implements that, keeping this invariant and the key→action contract tests.
- **TUI Create form = essentials + Advanced accordion.** `crates/mold-tui/src/ui/create_form.rs` owns the row model (`CreateRow`, `AdvSection`, `visible_rows`) — the old `ParamField::visible_fields` is gone, Mode/Host rows never come back (routing = Machines `GenTarget`), and the inline Negative editor only renders while Advanced → Negative is expanded (`negative_visible()` is the focus/hit-test predicate). Video shows Frames/FPS for video families plus checkpoint-aware LTX-2 Audio, latent-upscale, and guidance-override rows. Audio's tri-state `default` / `on` / `off` preserves an absent `enable_audio` until explicitly changed, enabling it selects MP4, and an advertised `supports_audio:false` hides it and clears stale authority. Spatial `native` / `1.5×` / `2×` and temporal `native` / `2×` preserve absent request fields until changed. STG scale/blocks, CFG rescale, modality scale, and guidance skip likewise keep `guidance_overrides` absent until touched; block input is validated before it can close, and leaving LTX-2 clears every stale video override. **File under** is the last section and has no capability gate — every model produces a print. Its Title/Tags/Collection rows are absent-until-touched popups validated through `mold_core::organization` _before_ they can close, and Title and Tags validate against each other because a titled print may pick up its own slug as a tag. That auto tag is composed by the same `mold_core::compose_client_tags` the CLI uses (the server never auto-tags) and is disclosed on the Tags row and in the section summary; the helper's one CLI-flavoured message (`--no-auto-tag`) is rewritten by `create_form::compose_filing_tags` to name Settings ▸ Library ▸ **Tag by title**, the TUI's own `generate.auto_tag_title` toggle, whose value the form snapshots into `GenerateParams.auto_tag_title` so the disclosure and the request cannot disagree. Filing is per-print intent, so `TuiSession` gains no slot and `model_prefs` no column, and only Reset to model defaults clears it; a forced-local save stamps it into `OutputMetadata` (where the DB seeds the row on insert) and uses `default_output_filename_titled`. Unlike web/desktop the TUI does not gate on `capabilities.gallery.organize` — it matches the CLI, whose target may be a local engine with no host at all, and lets the host drop-and-warn. Settings labels must stay shorter than `ui::settings::LABEL_WIDTH` or they render flush against their value. Accordion state persists at `tui.advanced_open`/`tui.advanced_section`; keep the `visible_rows`/summary/active-count contract tests and the `TIMELINE_HEIGHT >= TIMELINE_VISIBLE_ROWS + 2` const-assert green.
- **Runtime video-pipeline provenance is output authority.** `VideoData.pipeline` records the recipe that actually completed, including an implicit Auto choice. CLI and TUI client-side saves must apply that response value rather than infer it from `GenerateRequest.pipeline`, and TUI Library details render `OutputMetadata.pipeline` only when present so older and non-LTX prints remain valid.
- **AUR PKGBUILDs auto-publish on `v*` tags.** `packaging/aur/{mold-ai-bin, mold-ai}/PKGBUILD` are the source of truth; CI rewrites their `pkgver` + `sha256sums` in the `publish-aur` job and pushes to the AUR git repos. The existing `-bin` package stays on the `cuda-sm89` release tarball. RTX 3090/A40, B200/B300, and RTX 50-series users build the source PKGBUILD with `CUDA_COMPUTE_CAP=86`, `100`, or `120`; do not publish an sm100 binary AUR package before real B200 qualification. GH200, GB200, and GB300 Grace systems remain unsupported until linux/arm64 artifacts exist. `mold-ai-git` is hand-pushed when the build recipe changes. AUR packages declare `conflicts=('mold')` because they collide with the rui314 linker at `/usr/bin/mold`. The in-tree `mold update` correctly bows out on `/usr/bin/mold` and `/usr/sbin/mold` Linux installs.

## Key design decisions

**Hidden collections invariant:** A collection's additive `hidden` flag fans out to every host copy. Hidden collections stay visible and openable in Collections, but their member prints are excluded from the default Prints grid and every text-search result on web, desktop, iPhone, and Android; collection drill-in always reveals them.

1. **Crate boundaries are clean** — `mold-cli` doesn't depend on candle; `mold-server` doesn't depend on clap; `mold-discord` only depends on `mold-core`.
2. **candle over tch/ort** — pure Rust, no libtorch. Application-owned models and public-API extensions live in `mold-ai-candle`; backend changes that cannot be implemented outside Candle live in the `utensils/candle` fork and are removed as upstream accepts them. **Every candle crate — `candle-core`, `candle-nn`, `candle-transformers`, `candle-flash-attn`, `candle-onnx` — is a direct git dependency on ONE fork revision, in every cargo root (workspace, desktop, mobile).** `candle_core::Tensor` and `Error` are nominal types, so a single crate left on crates.io pulls the upstream-named `candle-core` in beside the fork's `candle-core-mold` and every call site handing a tensor across that seam stops compiling — which is exactly how #1393 broke CUDA for four consecutive `main` merges by moving three crates and leaving `mold-candle`'s `candle-flash-attn` behind (#1399). `[patch.crates-io]` cannot express this (a patch must keep the patched package's name, and the fork's are renamed), so the pin is the whole contract and `scripts/tests/candle-single-identity.sh` enforces it on the PR-visible release-contract route — the `--features flash-attn` compile gate is push-only and cannot warn a PR. `cargo tree -d` must never report candle from two sources.
3. **Single binary** — `mold` includes `serve` via `mold-server` library; GPU flags forward `mold-cli` → `mold-server` → `mold-inference`.
4. **`tokio::sync::Mutex` + `spawn_blocking`** — single-model-at-a-time fits GPU workloads. `AppState.model_cache` is an LRU (max 3) with `ModelResidency { Gpu, Parked }` — eviction removes the entry rather than adding a third state; at most one engine is GPU-resident.
5. **Nix flake (flake-parts + crane)** — CUDA 12.8 on Linux (default sm_89 Ada; `mold-sm86` for RTX 3090/A40, `mold-sm100` for B200/B300, `mold-sm120` for RTX 50-series; `mkMold` for any), Metal on macOS. B200 is server-only and remains simulated, not hardware-qualified. Devshell sets `CPATH`/`LIBRARY_PATH`/`LD_LIBRARY_PATH` for CUDA compilation.
6. **Shell completions** — static via `clap_complete` + dynamic via `CompleteEnv` with `ArgValueCandidates` for model names.
7. **Lifecycle authority follows scheduler ownership** — `PATCH /api/devices/:id` and every client enable/disable control are available only when `/api/capabilities.devices.lifecycle` is true. Legacy, observe, CPU-fallback, and all-disabled maintenance runtimes remain read-only; never persist a live change they cannot enforce.
