# MiniMax H3 policy and runtime

Moved verbatim from the root CLAUDE.md; loaded only when working under the paths above.

**MiniMax H3 policy is reviewed-IDs-only.** `mold-core::model_policy` remains the single authority, but since #1013/#1026 the reviewed compact manifest IDs — FL2VA, Ref2VA, and the eight Turbo LoRA tags `minimax-h3-fl2va:comfy-pruned-int8-turbo-8step` / `-turbo-4step-768p` / `-turbo-4step-768p-v1.1` / `-turbo-8step-768p` / `-turbo-4step-768p-r21` / `-turbo-8step-r21` and `minimax-h3-ref2va:comfy-pruned-int8-turbo-4step` / `-turbo-4step-r21` (`mold_core::minimax_h3::REVIEWED_TURBO_MANIFEST_TIERS`; the three `-r21` tags are lossy SVD-resized tiers — drbaph's per-module dynamic-rank derivatives of the full-rank adapters; the gate ran 2026-09-02, the measured A/B ran against each full-rank source, and all three tiers ship on the maintainer's call (2026-09-02, PR #1555); the qualification record holds the measured PSNR/SSIM rows and the decision in `docs/qualification/minimax-h3.md`, "The rank-21 Turbo tiers campaign (2026-09-02)") — are ordinary model identities on every build: they list, download, repair, inventory, remove, and auto-pull like other registered models, with no family-wide `model_access` restriction advertised and no private authorization or qualification-record files required. Since #1319 that reviewed-runnable tier is one of three: `is_pinned_unrunnable_minimax_h3_identity` (`model_policy.rs`) exact-matches a second tier of pinned manifest identities — the `official-bf16` qualification references and the two `comfy-pruned-nvfp4` tags — that are acquirable (download, verify, inventory, remove, and appear in Discover/Installed) but refused at generation as `ModelActivation::RuntimeUnavailable` / `ModelActivationError(ActivationRefusal::RuntimeUnavailable)`, reported as `MINIMAX_H3_RUNTIME_UNAVAILABLE` over HTTP 501 (never the compliance 451) with `/api/models[].runtime_available: false`; everything else still fails closed as `ComplianceGated`. Since #1276 that gate answers for THIS BUILD and not for the layout alone, and `mold_core::minimax_h3::model_runtime_availability` is the ONE authority every layer reads — the `/api/models` row, `model_activation`, and the HTTP 501 refusal — so the sentence a client shows before a 21-42 GB pull is byte-identical to the one generation returns. That authority has to be REACHED to answer, which is why `classify_h3_private_ingress` — which runs ahead of `model_activation` in `prepare_generation` and otherwise claims every identity `capability_contract_for_model` resolves — returns `Ok(None)` for an `is_pinned_unrunnable_minimax_h3_identity` row before its credential check and its runtime lookup (#1354); the private boundary is an authorization gate for identities mold can RUN, and claiming one it cannot answered the 422 partition refusal where the row promised the 501. The deferral is LAYOUT-level only: deferring on `UnsupportedTask` would hand a private task ingress seam to public activation, and on `EngineNotBuilt` would take the whole `h3-private-uat` runtime off its own path. It composes three questions in most-permanent-first order (`runtime_availability_for`): `layout_runtime_available` (no engine arm — the `official-bf16` references, now honestly `false`, and the NVFP4 tags), `task_runtime_available` (both released partitions execute since #825, so this axis refuses nothing today and survives for a future task), then `engine_is_built` (the macOS and Linux sm89 recipes compile `h3`; sm86, sm100, sm120, and Windows ship every H3 row download-only). The order is load-bearing: telling an sm120 user "this build lacks the engine" about a partition mold has no route for at all would imply the sm89 artifact runs it. `ActivationRefusal::RuntimeUnavailable` carries the `RuntimeUnavailableReason`, `ModelInfoExtended` carries the additive serde-default `runtime_unavailable_reason`, and `studio/lib/modelRuntimeAvailability.ts` is the one browser policy web/desktop/iPhone render from (a `Download only` badge and the server's sentence on Discover rows and detail panes, never a toast, never disabling Pull, resolved from the host's own `/api/models` so a not-yet-downloaded row is answered too). ACQUISITION is deliberately untouched — `model_acquisition` still answers `Available`, so pull, verify, inventory, repair, and `mold rm` work on every build; that split is what "downloadable but not runnable" means. `mold pull` prints the reason in place of the `mold run` hint (`post_pull_hint`), `mold run --local` refuses before opening a checkpoint, and the TUI repeats the server's sentence rather than its own layout-only guess. The CLI's REMOTE auto-pull gate is deliberately `require_model_acquisition` (`require_remote_auto_pull_acquisition`), never activation: the machine that downloads and then runs the model there is the remote server, which enforces its own activation on the resubmitted request, so a CLI compiled without `h3` must still be able to ask an sm89 host to pull the model that host runs. The match is deliberately exact rather than alias-resolving — `minimax-h3` still resolves to the reviewed FL2VA model and stays on the compliance path — because `is_reviewed_minimax_h3_acquisition_identity` resolving aliases is what makes an unqualified match wrong here. `Layout::ComfyPrunedNvfp4ConvrotNvfp4Awq` (`minimax_h3.rs`) is a real layout so manifest, provenance, dtype, and envelope resolvers stay exact; `layout_runtime_available` narrows the task-keyed `capabilities()` for it, but the actual gate is `base_compact_model` answering `None` for a pinned-unrunnable identity — the loader's trailing-data check on the third-party file is a backstop, not the authority. The NVFP4 transformer is pinned from `Abiray/Minimax-H3-nvfp4-INT4-INT8-Convrot` (the first non-MiniMaxAI/non-Comfy-Org H3 source), with an appended per-file marker that sits inside the pinned size+digest, so verification pins the marker along with the payload. A Turbo tag is the exact compact stack OF ITS OWN TASK plus one pinned adapter (stored once under `shared/minimax-h3/loras/`, revision-pinned through `file_revision` from the adapter's OWN pinned source — Comfy-Org `loras/`, or `lightx2v/Minimax-h3-Turbo` or `drbaph/MiniMax-H3-Turbo-Lora-ComfyUI` at their repository roots — through `TurboManifestTier::adapter_hf_repo`/`adapter_hf_revision`) and moves ONE axis, the reviewed step count — each tier's own distilled schedule length, 9 or 5 terminal-inclusive, read off `REVIEWED_TURBO_MANIFEST_TIERS` rather than restated here as an ordered list a table reorder could falsify. A reviewed adapter is one of TWO SHAPES (`H3TurboLoraShape`, mold-candle `turbo_lora.rs`), and the contract generalizes rather than forks: rank-UNIFORM is the published PEFT export — 208 modules x {`lora_A`, `lora_B`, `alpha`} = 624 tensors, every rank exactly `training_rank` (tripled on the fused Q/K/V module, whose `alpha` is tripled with it so `alpha / rank` is unchanged), and the runtime scale is that `alpha / rank` read off the file; SVD-RESIZED is a derivative of ONE uniform tier of its OWN task — 208 x {`lora_A`, `lora_B`} = 416 tensors, a PER-MODULE rank read from the header and bounded by the source rank (and by the exact-compact-SVD ceiling `min(in_features, out_features)`, per PROJECTION on the fused module), an `alpha` tensor refused by name, a REQUIRED numeric `__metadata__.baked_scale` equal to the pin and a REQUIRED `resized_from` equal to the source tier's own file name (the same repository publishes other resized exports that carry a sentence there and no `resized_from` at all), and a runtime scale of exactly `1.0` because the source `alpha / rank` is already inside `lora_B` — applying the pinned scale again would apply it twice. The two hash under DIFFERENT structure-identity domains, so every `adapter_identity_sha256` already recorded for a uniform tier is byte identical. A `/api/models` row names ONE `hf_repo` and it is always the BASE stack's — `catalog` derives it from the manifest's Transformer file — so a tag whose adapter comes from `lightx2v/Minimax-h3-Turbo` or `drbaph/MiniMax-H3-Turbo-Lora-ComfyUI` still reads `Comfy-Org/MiniMax-H3` on Discover; adapter provenance is per-FILE (the manifest row, the authorization record, and the model page), never inferred from that summary field. `storage_identity` and the manifest builder both resolve that base through `task_for_model`, never a literal `FL2VA_COMFY`, and an adapter's `compatible_tasks` is its own partition, so a `ref2v` adapter can never mint an FL2VA qualification; selection is by model identity, and `MOLD_H3_TURBO_ADAPTER`/`MOLD_H3_TURBO_TIER` survive only as the capture-scope UAT override under `h3-private-uat` — a set pair in any other build is a hard contradictory-authority error, never silently ignored. Execution limits are real capability limits reported truthfully (the CPU backend is unimplemented, not license-gated). **Ref2VA executes since #825.** Its execution slice is the same one-shot owner protocol FL2VA uses — `into_runtime_parts` hands back the TASK-shaped `H3PrivatePreparedTaskRequest`, `H3PrivateConcretePreparedRunner` retains the ordered `GenerationReferenceBinding`s (owned, because a binding holds its opened staged descriptor and is deliberately not `Clone`), and `run` dispatches on the FROZEN task to `bind_private_comfy_ref2va_phase_owner` + `run_private_comfy_ref2va_attempt`, which consumes the RETAINED preparation rather than re-deriving one from the request. Its authority is a SECOND compiled public profile: `PUBLIC_REF2VA_RUNTIME_PROFILE_SCHEMA`/`_DECISION`, `public_ref2va_runtime_envelope_for_shape`, and `public_ref2va_runtime_bounds_for_shape`, minted by the same `public_runtime_qualification` keyed on task through `public_runtime_profile_identities` — never inherited from FL2VA's record, which pins its own schema, decision, model, and task. The Ref2VA envelope is DERIVED PER REQUEST, because its conditioning is the ordered reference set rather than one endpoint on the canvas: `ref2va_reference_rows` reads `mold_core::minimax_h3::reference_prepared_shapes_for_target` — the same authority admission's own preparation packs rows from — for the conditioning latents, the Qwen vision rows AND pads, and the largest normalized reference canvas, then adds `REVIEWED_REF2VA_PROMPT_AND_LABEL_ROWS` (2,048) for the prompt, the twelve `<Picture n>`/`<Video n>`/`<Audio n>` labels, and the per-block `<t.t seconds>` stamps. A fixed 4,096-row-per-reference ceiling would have been wrong in the direction that matters: an image is normalized DOWN to a 2048 short edge and never up (a 4032x3024 camera photograph packs 5,440 pads on its own; a 1080p one keeps its 2,040). **Qwen vision rows and Qwen vision pads are two grids, never one number.** `qwen_vision_rows` is the conditioner's PRE-MERGE 16-px ViT patch count — `mold_core::minimax_h3::qwen_vision_patch_rows_per_block`, four per packed row — because that is what the runtime's `pixel_values.dim(0)` carries, what `validate_prepared_authority` compares the frozen authority against, what FL2VA's evidence reads off its prepared conditioner (4,032 at 1344x768), and what the observed activation workspace's `2,033 + 4,032` denominator was measured over; the merged 32-px pads (`qwen_vision_pad_rows_per_block`, one per packed row) are the part of the TEXT sequence a visual occupies and feed only the text ceiling. `h3_reference_charges` and `reference_qwen_vision_rows` charge patches, and a pin test holds them together; charging pads there admitted a 2048-square image at 4,096 rows the runtime prepared as 16,384 and held every Ref2VA image reference at execution (#1418). The conditioner's OUTPUT vision rows are a third count: `PresentationBuilder::vision` (mold-candle `presentation.rs`) tags `pads + 2` per span because upstream tags the flanking `<|vision_start|>`/`<|vision_end|>` rows video-modality too (ComfyUI `comfy/text_encoders/minimax.py:75-82`, `:163-167`; one span per image, one per 2-frame video block), so `ref2va.rs`'s `validate_text_vision_rows` expects pads plus `VISION_SPAN_MARKER_ROWS` per span — comparing against the bare pad count refused every visual reference right after the #1418 hold was fixed. And a reference's visual-VAE condition arrives on the HOST on every route — `official_seed42_sample` (mold-candle `visual_condition.rs`) does the official FP16 round-trip on the CPU — so `ref2va.rs` moves it onto the frozen device before `validate_visual_condition`, exactly as `pipeline.rs` does for FL2VA's endpoint; validating the encoder's own placement was the third refusal the #1418 UAT hit, 40 minutes into every render. The fourth was the runtime-bound observer (`private_runtime_observer.rs`): `captured_phase` and `build_observation` read the condition-VAE workspace from whichever encoder phase ran (`CONDITION_ENCODE_PHASES`: FL2VA's `VisualConditionEncode` or Ref2VA's `ReferenceVisualEncode`), because requiring FL2VA's alone failed every fully muxed Ref2VA print at `finish()` — and `ref2va.rs` reports `observe_staged_host_bytes` at its `Staged` checkpoint exactly as `pipeline.rs` does (a parity test counts both), because the observer's zero-byte guard refused the fifth render for the two staged capacities Ref2VA had never reported. **A Ref2VA image reference may carry a user CROP, never a fit.** `studio/lib/referenceCrop.ts` is the one policy on web, desktop, and iPhone: a rectangle in SOURCE pixels (64 px minimum per axis; Free / 1:1 / 4:3 / 3:2 / 16:9 presets in the source's own orientation) that the shared `ReferenceCropEditor.vue` edits from the panel's **Crop** action, stored as `MinimaxH3ReferenceDraft.crop` OUTSIDE the wire type and applied at the ORIGINAL resolution by `applyMinimaxH3ReferenceCrops` in each surface's async preprocessing hook — before the wire projection is uploaded or previewed — which re-encodes the crop as PNG through the shared `SourceFitCanvasOps` (`applyReferenceCropTransform` is the same `SourceFitTransform` shape, so `fitImage` executes it unchanged) and recomputes `width`/`height`/`provenance.sha256`, so upload conversion, placement, and `conditioningFingerprint` all see the cropped reference (the projection also stamps a PENDING crop into `provenance.crop`, so reviewed prompt work stales on it before the bytes change). The additive `provenance.crop { x, y, width, height, source_width, source_height, source_sha256 }` is validated by `GenerationReferenceCrop::validate_for_image` — non-degenerate, inside the source, and EQUAL to the reference's own dimensions, so a projection that reached the server unapplied is refused as `MINIMAX_H3_REFERENCE_CROP` rather than rendered uncropped — and then retained verbatim through `OutputMetadata.references`, where Reuse settings restores it as a pending crop over the uncropped source facts that a byte-identical reattached original re-applies (any other file clears it with an inline disclosure). It never touches `width`/`height` or `CanvasIntent`: the server normalizes every oversized image reference DOWN onto its own 2048-short-edge canvas and keeps a smaller one at native /32 geometry, never upscaling (`reference_image_dimensions`, mirroring ComfyUI `nodes_minimax_h3.py`'s `min(1.0, 2048/short)` — the 2026-08-29 incident upscaled two 582x1200 phone photos to 2048x4224 each, ~67k ViT patch rows, and an 82.7 GB host demand no 64 GB host could admit; `REFERENCE_PREPROCESS_VERSION` 3 fences the old shapes), so a `SourceFitPolicy` for references would contradict the server, and `referencePadEstimate` — the TS mirror of that arithmetic plus `(w/32)*(h/32)`, pinned to a Rust fixture test — is a hint only; `reference_prepared_shapes_for_target` stays the authority. This is deliberately distinct from the identity-photo rule, which forbids fitting, cropping, or resizing a face reference TO THE CANVAS: a user-chosen crop of an H3 reference is composition intent, not canvas fitting. The audio ceiling is `max(generated, conditioning)` because `conditioning_mismatches` compares the request's condition-audio rows against the same `max_target_audio_rows` field. Memory scales from the SAME `fl2va_observed` figures the FL2VA bounds do, by the quantity each term is a function of, so an unaffordable reference set is refused with numbers rather than by a list. **H3 audio is a family declaration, not a checkpoint probe.** `synchronized_audio: true` with `audio_disable_supported: false` means every H3 render carries audio and nothing can turn it off, so `/api/models[].supports_audio` and the profile recipe's `supports_audio` both derive from `mold_core::minimax_h3::capabilities(task)` through `catalog::declared_audio_capability` — on cold rows too, and in the private-runtime bridge row rather than a second literal there. `mold_inference::audio`'s probe registry deliberately has no `minimax-h3` arm: it answers checkpoint header questions (LTX-2's optional audio VAE + vocoder) and only for downloaded entries, which would leave the family's own contract null. Leaving it null is what forced every surface to hard-code H3's AV behaviour from the family name (#841). **The reviewed envelope's text-row ceiling is a PROMPT budget, not a transcribed observation.** The FL2VA conditioner sequence is `"<Picture 1>: "` + the endpoint's 1,008 merged vision pads + the prompt's own tokens, so `max_qwen_output_text_rows` = 2,048 leaves roughly a thousand prompt tokens; the earlier 1,058 was the qualifying render's own 1,050-row measurement and budgeted about forty, refusing every ordinary app prompt (#1245) even though the conditioner context is 262,144 tokens. `max_total_packed_rows` is derived from the four axes the prepared request sums, never transcribed beside it. An over-budget prompt is refused BEFORE the ~37 GB artifact pass, by a precheck whose reported budget is the ceiling minus the overhead the tokenizer actually produced — never a second constant — and the authenticated envelope check remains the backstop, naming every axis a refusal differs on rather than one bare sentence. **The compact envelope is a RULE, not a pinned shape.** `is_admitted_compact_canvas` is the one canvas authority — both axes on `VIDEO_ROW_STRIDE` (32 = the VAE's 16x spatial compression x the DiT's `patch_size [1,2,2]`), each at least `MIN_COMPACT_AXIS_PIXELS` (256), total area within `COMPACT_MAX_PIXELS` (1,032,192 = the area of 1344x768, the shape every memory bound was measured at), aspect inside the family's `MIN_ASPECT_RATIO..=MAX_ASPECT_RATIO`. The clip length is the family grid (`valid_frame_count`, 107..=345 on `17n+5` at the fixed 24 fps) and the base tag's step count is `COMPACT_MIN_STEPS..=COMPACT_MAX_STEPS` (2..=50; a Turbo tag keeps its distilled adapter's EXACT count, which is its schedule length rather than a qualification pin). `REVIEWED_COMPACT_CANVASES` survives as the RECOMMENDED preset list — a test pins every entry to the rule — and `REVIEWED_COMPACT_FRAMES` (aliased `DEFAULT_COMPACT_FRAMES`) as the default alone; `fixed_frames_for_model` answers `None`. The generation profile is a `Dynamic` range with those presets, never `Buckets` + `OffBucketPolicy::Reject`. The area ceiling is load-bearing beyond memory: one packed row is a 32x32 cell, so `rows = pixels/1024` and no admitted canvas can exceed the 1,008 rows the measured canvas packs — which is what keeps the measured conditioning ceilings ceilings, pinned exhaustively by `no_admitted_canvas_packs_more_rows_per_latent_than_the_default`. `public_runtime_envelope_for_shape(canvas, frames, steps)` derives its generated-side rows through `mold_core::minimax_h3`'s packed-row functions — the ONE authority `h3_admission` and `h3_factory` also charge against — and `public_runtime_bounds_for_shape` scales #827/#1245's observations by the quantity each term is a function of: attention/FFN by packed rows, audio decode by frames, and the video decode + condition encode by canvas AREA (the video VAE is temporally chunked at a fixed `tokens_per_chunk` over the full canvas, never spatially tiled, despite `decoder_tile_workspace_device_bytes`' name). Steps scale nothing — a step is time. The scaling passes through the same `public_runtime_bound` margin/64-MiB-grid policy, so at the measured shape the record is byte-identical (regression-pinned), and a 345-frame clip asks a ~24.3 GB device floor against 9.7 GB at the default: refused with numbers rather than by a list. `validate_shape` runs before everything in `validate_prepared_with_adapter`, so a request cannot mint an authority for a shape nobody would run. Source fitting renders the SOURCE's own aspect at the largest admitted size (`largest_admitted_compact_canvas`) instead of picking the nearest of two fixed canvases. The canvas refusal stays a DOOR check, never part of `validate_request_contract`: the engine's own `prepare_request` runs that contract on the tiny synthetic canvases its pipeline tests use, so the rule lives in `minimax_h3::validate_reviewed_canvas`, called by `validation::validate_h3_private_uat_request` for authenticated private ingress and reached by every ordinary client through the profile's range. Only 1344x768 and 768x768 at 124 frames are MEASURED (`docs/qualification/minimax-h3.md`); every other admitted shape rides a derived estimate.

**An H3 admission identity is hashed over the PERSISTED request, and a scrubbed row's media presence comes from the projection (#1427).** `mold_core::request_media::scrub_request_media` is the ONE list of fields the durable journal strips (mold-server's `queue_media::scrub_request_media` delegates to it), and `private_h3_request_identity` hashes `persisted_request_form(request)` — the same rule the ingress grant's `request_authority_sha256` follows — so a hydrated request at admission or on the worker and the payload-free row the scheduler resolves produce one digest. `H3PrivateFl2VaAdmissionEvidence::validate_for` takes a `mold_core::minimax_h3::ResolvedMediaPresence`: the resolver (`resolve_private_h3_execution_plans`) and dependency preparation derive it from the queue-media projection's `source_image`, and the worker's live revalidation from the OWNER'S OWN HYDRATED COPY (`from_request(&request)`, pinned structurally) — never `job.request`, which stays payload-free for the whole attempt and would resolve the same print as text-only — and the prepared MEDIA CONTRACT (`H3PreparedMediaContract::from_request_with_media` / `validate_for_request_with_media`) takes the same presence, which the worker reads off the job through `job_media_presence` (request OR `deferred_media.projection().source_image`) at both its claim fence and its publication contract, and `validate_resolved_request_contract_with_media` keeps a scrubbed FL2VA row at `FirstFrameToAudioVideo`. Hashing the hydrated request and deriving the mode from the scrubbed row is what blocked every FL2VA job since #1417 as a phantom "device memory" shortage with `required < headroom` — and the sentence that would have said why was an unlogged `DeviceInfeasibility.advice`, so `validate_for` now names its failing conjunct and the resolver logs it at WARN. The IDEMPOTENCY subject beside it binds whatever the build graph gives it (`private_ingress_subject_sha256`): a build without public `h3` refuses to classify an unauthenticated request at all and binds the caller's restart-stable durable identity, while a PUBLIC keyless H3 host has no key to bind and binds the server INSTANCE — one shared anonymous idempotency subject per process, deliberately new after every restart. Both arms are intended; the structural test asserts whichever the graph selects rather than one of them. **H3's conditioner placement is a device fit, not a backend rule (#1423).** `private_h3_qwen_route` (`private_server.rs`) is the one decision: Metal is always `AssignedMetalThenDrop` (the streamed route, #1323); CUDA takes `AssignedCudaThenDrop` — the `Accelerated` placement, 14.5 GB NVFP4 payload host-resident and 1.19 GB of dense tensors on the device — exactly when `fixed_runtime_device + dense residency + qwen_activation_workspace_demand_bytes + output state <= available_device_bytes`, and keeps `HostCpuThenDrop` otherwise, so a small card or an over-large reference set renders as before rather than refusing. From #919 through #1425 CUDA was pinned to the host regardless of memory, which put every FL2VA/Ref2VA prefill on the CPU (40 minutes for one 2048-square Ref2VA image on a 4090). The reason a 16,384-patch image reference can fit at all is `mold-candle` `vision.rs`: `VisionAttention::forward` chunks the QUERY axis under `VISION_ATTENTION_SCORE_ELEMENT_BUDGET` (2^28 `heads x Q x N` elements, ~2 GiB of bf16 scores + f32 softmax + bf16 probabilities per chunk) — exact, because softmax is per row — while FL2VA's 4,032-patch endpoint and every 2-frame video block stay single-chunk and byte-identical; the unchunked `[1, 16, N, N]` at N = 16,384 was ~34 GB per layer and the whole of the CPU route's host peak. **The Qwen conditioner OUTPUT is cached too, orthogonally to where it ran (#814).** `minimax_h3::conditioner_cache` is a process-global, byte-bounded cache (default 512 MiB, `MOLD_H3_CONDITIONER_CACHE=off|<MiB>`) keyed on the prompt, the endpoint or reference bytes (crop and, for Ref2VA, frame count included), the conditioner's route AND device id, and every artifact/support identity that produced the tensor, so a hit — served through the ledger's `H3PrivatePhaseState::QwenServedFromCache` state rather than a synthetic load/drop pair — restores the SAME BF16 bytes a fresh encode would have produced while withholding the runtime-bound observation and the `PromptEncode` scheduler-estimate sample instead of fabricating either; it is cleared both by `release_host_memory_after_unload` and by `prepare_private_h3_allocation_boundary` when sampled host headroom is short, stays inert under `h3-private-uat` so a capture run always exercises the conditioner, and needs no exclusion against a future step cache or PDD tier because it changes no pixels and its key carries the CONDITIONER's own artifact and support pins, which every distill tier leaves untouched. **Nothing minted per attempt may join that key.** It hashes the frozen conditioner component's CONTENT digest — every member's path, revision, `sha256`, structural contract, header identity, policy identity, size and tensor count — and never its VALIDATION digest, because `private_h3_component_digests` folds the attempt's runtime qualification identity into that one and `runtime_qualification_identity` hashes the request ENVELOPE (`public_runtime_envelope_for_shape(canvas, frames, steps)`), so one conditioner file presents a different validation digest at every clip length, step count and canvas. A per-attempt identity in a cache key never produces a stale hit; it produces a cache that never hits, and that is exactly what the 2026-09-02 plato UAT measured before it was removed — a 141-frame FL2VA render stored key `ccbfa21f…`, an otherwise identical 124-frame render missed it while that entry was still resident and nothing had cleared it, and a second 141-frame render hit it again — `canonical_model` is the base compact model for every Turbo tag (`private_opened_evidence.rs` freezes `contract::FL2VA_COMFY` / `contract::REF2VA_COMFY` whatever the tier, which is why `require_ref2va` can compare against the literal), so entries are deliberately SHARED across tiers and no reader may infer tier separation from that axis. **An H3 pipeline face takes its integrator from the frozen quantization authority, never from a literal (#1432).** Both `H3Fl2VaBackend` and `H3Ref2VaBackend` on `H3PrivatePhaseBackend` answer `sampler_kind` / `sampler_video_shift` with `self.admitted.quantization.*`, and both pipelines build their `H3DualSchedule` through `new_for_sampler_with_video_shift`; the Ref2VA face's hard-coded `ComfyResMultistep` rendered every Turbo 4-step clip in full and then failed `validate_private_sampler_provenance`, which is the guard that caught it and the reason a literal there can never be right. **The base tag's step floor is a schedule, not a recipe:** `COMPACT_MIN_STEPS` admits 2 grid points, but the undistilled checkpoint's reviewed schedule is 50 (ComfyUI's example 21), and a 4-grid-point request is THREE forwards — sigmas 1.0 → 0.96 → 0.86 → 0 — whose decoded print flashes once per latent frame and ghosts the reference (the 2026-08-28 Ref2VA UAT). Only a Turbo tag's distilled schedule is 4 or 8 steps. **H3's Metal path is a correctness tier: it ships and is admitted, and it has never rendered (#1164, #1296).** The candle layer executes on Apple Silicon: `H3AttentionBackend::MetalChunkedDenseMath` runs the identical dense F32 arithmetic over query chunks sized by `H3_METAL_DENSE_CHUNK_MAX_SCORE_ELEMENTS`, because the unchunked `N x N` score matrix at released geometry is ~358 GB and Metal has no FlashAttention kernel to escape to; the chunk is a pure function of the shape, frozen into the plan and hashed into its identity, so admission, the plan, and the executor cannot disagree. Each Metal query chunk copies into a preallocated output and synchronizes before the next chunk: collecting chunk tensors can retain oversized pooled score buffers, and dropping Tensor handles alone does not retire GPU work. The portable INT8 reference forward uses the same lifetime rule for output-row chunks: one destination, copy, drop temporary tensors, and synchronize before the next row pass; native CUDA returns before this Metal-only assembly. `metal_reduce` moved to `mold-candle` (mold-inference keeps a `crate::metal_reduce` alias) so the H3 audio VAE's rank-4 head mean folds like every other Metal-reachable reduction. INT8 ConvRot resolves through `select_h3_int8_linear_kind`, where Metal always takes the portable dequant arm — no Metal twin of the cuBLASLt kernel exists, and unlike Qwen-Image there is no candle Metal quantized kernel to qualify; NVFP4-AWQ has no native MATMUL kernel on any backend — the linear is always a full-precision `f32` matmul over a dequantized weight chunk — but since #1317 the DEQUANTIZATION is dispatched by `select_h3_nvfp4_linear_kind`: CUDA uploads the packed payload bytes and the unswizzled FP8 scale bytes and widens both on the device through `index_select` lookup tables, while Metal and CPU keep the host scalar loop. The two arms are bit-identical (`nvfp4_device_dequantize_is_bit_identical_to_the_host_loop`, and #1317's probe over all 115,605,504 elements of the shipped `attn.qkv_proj` weight), so this is a cost choice and never a numerical one; Metal is excluded only because no Apple device is in reach of that gate, which is the one thing a Metal arm would need. The device arm's one trap is candle's own: `candle-kernels/src/indexing.cu:60` reserves `max_value<I>()` as a zero-padding sentinel, so `U8` ids can never address a 256-entry table and `0xff` — an ordinary payload byte, two `-6.0` E2M1 nibbles — would silently decode to `0.0`; the ids are cast to `U32` on the device while the stored weight stays `U8` at rest. The FP8 block scales still reach no backend AS FP8: they are unswizzled on the host at their own one-byte width and widened through a 256-entry table (#1316 — an `f32` cache cost 4.57 GB of host RAM on the shipped conditioner for identical arithmetic), on the host per lookup or by gathering that same table on the device, so they never need a Metal or CUDA fp8 cast. `h3_nvfp4_weight_staging_bytes` is the one accounting authority for both arms and a memory authority must charge the larger. fp8-scaled linears are refused by name. `H3CandleBackendDevice::Metal` and `H3ConditionerExecution::MetalResident` exist and validate device-exactly (`matches_candle`, never a literal `is_cuda()`), and the factory input's compute capability is `Option` where `None` IS Metal. `h3` no longer implies `cuda` at any level — `h3-cuda` is the shipping CUDA edge, and `mold-server` gains no Metal forwarding feature because it has TWO exact reviewed public build graphs rather than one: `PUBLIC_H3_SERVER_FEATURES` (`h3` + `cuda` + `h3-cuda` + `h3-private-bridge` + `mp4` + `nvml`) and `PUBLIC_H3_METAL_SERVER_FEATURES` (`h3` + `metal` + `h3-private-bridge` + `mp4`, NVML absent because there is nothing NVIDIA to read), both pinned in `crates/mold-server/build_support/h3_server_features.rs` as exact sets rather than relaxations, so "CUDA optional" can never admit a build with neither device. Since #1323 the Metal route reaches a SHIPPED binary: `h3_admission` admits `GpuBackend::Cuda | GpuBackend::Metal` and places the conditioner through `AssignedMetalThenDrop`, `PUBLIC_RUNTIME_PROFILE_DECISION` is `supported-compact-fl2va-cuda-sm89-or-metal`, and the macOS release recipe builds `h3,metal` (`flake.nix`, `release.yml`) with macOS CI compiling both the forced-local and the reviewed Metal server recipe. What does NOT exist yet is a RENDER: a Metal attempt is refused below a unified-memory floor of `max(device floor, host floor)` before the artifact pass, the ~42.5 GB artifact size is not simultaneous residency (Metal streams Qwen language layers and DiT blocks; admission takes the maximum per-phase host-plus-device sum), and hardware qualification (#1164, #1296) stays open — `metal: CorrectnessOnly` is the advertised tier and CPU is still refused. Ref2VA shares that device rule exactly (`supported-compact-ref2va-cuda-sm89-or-metal`), because backend applicability is a FAMILY declaration and a task-only Metal refusal would contradict the capability every client reads. `mold-core::minimax_h3` advertises `metal: CorrectnessOnly` for the path while `runtime_available` still gates whether any engine is registered. Everything else stays fail-closed: arbitrary raw H3 repositories, aliases, and manifests are rejected, catalog identities must pass the policy both before a raw `hf:` request and after opaque `cv:` metadata resolution, and weight presence never implies authorization. The #831 governance decision (recorded in `docs/architecture/minimax-h3-authorization.md`, delivered via #1085) permits H3 use universally — every territory, local/remote/shared/hosted, output distribution, and redistribution — with no H3-specific clickthrough, geolocation, generated-content label, or surface control required; the README and H3 user guide are the complete user-facing license/attribution/disclosure delivery. Re-review the pinned license (SHA-pinned, verifier-enforced) before every release that touches H3.

**The H3 tokenizer follows the official MiniMax repo, NOT the ComfyUI port it otherwise tracks.** H3's `processor/tokenizer_config.json` declares twenty `additional_special_tokens`; thirteen already carry ids in `tokenizer.json`, and the remaining seven — `<d>`, `</d>`, `<|cutoff|>`, `<|lyrics_start|>`, `<|lyrics_end|>`, `<|caption_start|>`, `<|caption_end|>` — do not. The released `tokenizer.json` stops at id 151668, and HuggingFace assigns the missing seven 151669..=151675 in declaration order when a tokenizer is built from the directory. Building from `tokenizer.json` alone skips that step, which is what #1430 was: byte-level BPE smeared an unregistered `<d>` into its neighbours (`>` merged rightward with the `[` of `[English]`, `</d>` merged leftward with the preceding period), so nothing delimited the dialogue span and the delimiter was not even recoverable downstream. `mold_candle::minimax_h3::register_extra_special_tokens` is the ONE registrar, called by both conditioner load paths from the pinned `tokenizer_config.json` bytes each already holds; it fails closed when the declared set is not exactly those seven and re-verifies every id before returning. **ComfyUI does not do this** — at HEAD `a464ac33` `comfy/text_encoders/minimax.py` has only ever had one commit, has never carried a `MINIMAX_EXTRA_TOKENS` table, and describes its presentation as "raw prompt/label text (no special tokens)"; the citation of such a table in #1430's original report does not reproduce. The divergence is deliberate and rests on the model authors' own contract: the official README states the H3 tokenizer configuration files "are required", MiniMax's own reproducible request writes `<d>[English] Follow the wind, live free.</d>`, and `model.embed_tokens.weight` is `[151936, 5120]` so 151669..=151675 are addressable rows (the shape proves addressability, NOT that those rows were trained -- a per-row dequantized-std probe puts all seven inside Qwen's untrained padding band, where `<think>` sits at z=+57 and `<|vision_start|>` at z=+110, so do not claim a quality win without a render). Do not "restore parity" with ComfyUI here. **The tokenizer layer and the prompting layer use different spellings, and the prompting corpus follows the prompting guide.** MiniMax's `docs/VIDEO_PROMPT_WRITING_GUIDE_base_en.md:142` and `..._ref_en.md:221` tell authors to write the BARE `<scenetrans>` and `<cutoff>`, even though the tokenizer's own name for the latter is `<|cutoff|>`; `<scenetrans>` has no registered token at all. Do not "correct" the corpus from `tokenizer_config.json` -- that is inferring a guide from a different layer, which the corpus rule forbids. Validation is deliberately TWO-STAGE — the released shape (151643 base / 26 added / max 151668) is checked before registration so a swapped `tokenizer.json` is still refused at its own fingerprint, and the registered shape (33 added / max 151675) after — so never collapse them into one pin. The reviewed envelope's prompt-row precheck reads what the tokenizer actually produced, so a `<d>`-bearing prompt now costs FEWER rows than before; headroom only grows.

Runtime reports distinguish expected SHA pins, observed digests when available, and installed identities. Keep task/support/authorization document checks and bounded header validation.
