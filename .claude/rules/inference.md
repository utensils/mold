# Engine invariants (mold-inference, mold-candle)

Moved verbatim from the root CLAUDE.md; loaded only when working under the paths above.

**Feature flags** (`mold-cli`): `cuda`, `cudnn`, `nvml`, `metal`, `flash-attn`, `h3`, `h3-cuda`, `pulid`, `preview`, `discord`, `expand`, `tui`, `metrics`, `webp`, `mp4`, `mdns`. GPU features forward through to `mold-inference`. H.264 decode is baseline for LTX-2 source ingest; `mp4` only gates AAC mux. `flash-attn` implies `cuda` and compiles 53 FlashAttention v2 kernels through nvcc. The sm89 `h3-cuda` release recipe compiles it (the kernels were already linked there through `h3-attention-rc`, so the edge costs no extra build time) and every other release recipe omits it; `scripts/verify-h3-release-exclusion.sh` accepts the `global-flash=compiled` marker only beside `h3-rc=compiled`. Building it makes `MOLD_ATTN=flash` available, and the default that then applies is **per family** (`attention::AttentionPolicy` / `default_backend_for`): `AttentionPolicy::Image` is `Math` in every build, pinned by a feature-independent test (#736), so shipping the kernel never changes the bytes an archived still renders; `AttentionPolicy::Video` (the Wan DiT and LTX-2's BF16 dispatch) is `Flash` wherever the kernel is compiled in, because the seed-archival argument is about stills and the math path costs a measured 2.1x on Wan. The `flash_compiled()` guard inside the video arm is load-bearing: without it a build lacking the kernel would fall back per block and warn about a request nobody made. Never re-couple the IMAGE default to the feature, and the H3 visual VAE's `Auto` backend is likewise gated on the env-resolved `MOLD_ATTN` answer (`vae_runtime.rs::visual_attention_backend_for`) so shipping the kernel moves no H3 pixel. It reaches the `crate::attention` call sites (FLUX offload + GGUF-bypass, all Flux.2, Z-Image offload, the Wan DiT's self/cross attention, and all three Qwen-Image transformers — BF16, quantized, and offloaded — on their non-Metal path); dense paths elsewhere use upstream Candle's own attention.

**`cudnn` is the same shape as `flash-attn`, one layer down** (#1483). It implies `cuda`, is never implied BY it — cudarc links `libcudnn` and needs its headers, so folding it into `cuda` would break every `cargo check --features cuda` on a machine without the cuDNN SDK — and every Linux CUDA release recipe enables it while a bare `cargo build --features cuda` does not. Compiling it only makes the path reachable; `conv_policy::ConvPolicy` decides per family, mirroring `AttentionPolicy` on the identical clips-versus-stills argument, and a unit test asserts the two family lists never diverge. Three things make it safe. (1) The process default is im2col, installed once from `factory::create_engine_with_frozen_config_and_h3_factory`: candle defaults ITS switch on, so without that pin every family would take cuDNN the moment the feature compiled, moving still bytes. (2) `ConvScope` is RAII and restores the previous backend on drop, so a Wan render that fails halfway cannot leave the next still on cuDNN. (3) Inside the fork, dispatch is per convolution — 1x1 kernels and shapes whose im2col column buffer is below a measured threshold stay on im2col, and any cuDNN error falls back rather than failing the render. The win is 4.4x on the Wan VAE decode's convolutions (845 -> 192 ms per latent frame, RTX 4090, 832x480), and most of it was NOT cuDNN: candle left every descriptor at `CUDNN_DEFAULT_MATH`, which refuses tensor cores for bf16 and admits TF32 for f32, so enabling the feature alone bought 1.63x of the 4.4x. `MOLD_CONV={cudnn,im2col}` overrides, and is engine-shaping.


**True-CFG invariant:** FLUX is guidance-distilled and runs one forward per step; PuLID's true CFG (`PuLID/flux/sampling.py:136-149`) restores a real negative branch, and `mold_core::identity` is the only authority for it. Additive `true_cfg` / `cfg_start_step` reuse the existing `negative_prompt`; `request_uses_true_cfg` is the single predicate every layer reads (admission, the memory estimate, the extractor, the engine), and it is false for an absent scale, for one within `TRUE_CFG_EPSILON` of `TRUE_CFG_OFF` — upstream's own `abs(true_cfg - 1.0) > 1e-2` comparison at `sampling.py:120` — and for a zero `id_weight`. True CFG is qualified ONLY alongside active identity conditioning, because the negative branch needs the unconditional identity embedding the extractor produces beside the real one; that gate is what keeps `id_weight: 0` byte-indistinguishable from a plain request. `1.0` is accepted and inert — `validate_true_cfg` admits the `[1.0, 10.0]` range and `request_uses_true_cfg` answers false within `TRUE_CFG_EPSILON` of it, so the branch is never constructed rather than run as an identity lerp: `neg + 1.0 * (pos - neg)` is `pos` arithmetically but not bit-identically. The unconditional identity is `IDFormer(zeros, zeros)` (`pulid/pipeline_flux.py:188-192`) — not a zero tensor, and a pure function of the adapter weights, so it is computed once at extraction and only when the branch actually runs. Both halves ride on one `FrozenIdentityEmbedding` and are installed and cleared by ONE call, because a leftover unconditional embedding would condition this render's negative branch on the previous person's absence. `FluxTransformer::denoise` takes `Option<&TrueCfgBranch>` and `None` leaves the loop byte-for-byte what it always was, pinned per transformer variant in `flux/pulid_variants.rs` on the same synthetic route the zero-weight tests use. A request that asked for the branch and was frozen without an unconditional identity is an explicit error, never a silent distilled render — `guidance` is chosen for whichever regime is running. Admission charges `TRUE_CFG_VRAM_OVERHEAD_BYTES` on top of the identity overhead so a branched render is never admitted on the plain estimate. Web, desktop, iPhone, TUI, and Discord are a separate issue.

Most are in `mold-inference`. When touching engines, these are the rules that matter:

- **Lazy load** — engines load on first `generate()`, not startup. Most hold mmap'd safetensors.
- **Drop-and-reload text encoders** — T5/CLIP/Qwen3 are dropped from GPU after encoding so the transformer has VRAM to denoise, then reloaded next request.
- **Dynamic device placement** — text encoders go to GPU or CPU based on remaining VRAM after the transformer loads (thresholds: `device.rs`).
- **Quantized encoder auto-fallback** — when FP16/BF16 doesn't fit, the largest GGUF variant that fits is auto-selected. Override: `--t5-variant` / `--qwen3-variant` / `--qwen2-variant` or `MOLD_*_VARIANT`.
- **Block-level offloading** (FLUX) — `flux/offload.rs` streams transformer blocks CPU↔GPU one at a time: ~24 GB → 2–4 GB VRAM, 3–5× slower. Auto-enabled under pressure; force with `--offload` / `MOLD_OFFLOAD=1`.
- **LoRA backend is custom** — candle has no LoRA. BF16 path: `LoraBackend` (a `SimpleBackend`) intercepts `vb.get()` during model construction and applies `W' = W + scale·(B @ A)` inline. GGUF path: `gguf_lora_var_builder()` selectively dequantizes affected tensors, merges, re-quantizes. Both work with offloading. See `flux/lora.rs`.
- **LoRA caching** — `LoraDeltaCache` (pre-computed `B @ A · scale` on CPU, ~80–120 MB) survives transformer rebuilds. `LoraFingerprint` on `FluxEngine` skips redundant rebuilds when the same LoRA/scale reappears.
- **A LoRA fingerprint describes the transformer that is resident, not the request.** `QwenImageEngine::active_lora_fingerprint` mirrors FLUX's `active_lora`: same path-hash + scale-bits keying, order-sensitive, written wherever a transformer is built (eager `load`, `reload_transformer`) and cleared wherever one goes away (the VAE-decode drop, `unload`, sequential's deferred load). Every rebuild decision therefore reads residency _and_ the fingerprint — `qwen_transformer_rebuild_needed` — because an empty fingerprint means both "no LoRA merged" and "no transformer". Reading it as request state instead is what left the stay-hot quantized path rendering a new stack with the old merge baked in. Only resident paths can elide; `generate_sequential` builds a request-local transformer, and Qwen block offload refuses LoRAs outright.
- **Shared tokenizer pool** — `shared_pool.rs`: `Arc<Tokenizer>` keyed by file path, shared across engines via `create_engine_with_pool()`. Saves ~100–150 ms on model swap for FLUX variants. The same pool caches component **CPU tensor maps**, and that half is budgeted on purpose (`CPU_TENSOR_CACHE_BUDGET_BYTES`, 2 GiB total): the OS page cache already caches a component reclaimably, so a second anonymous copy in this map converts memory the kernel could drop into memory host admission must charge in full. A component is weighed by its on-disk size **before** the read, so an over-budget one is never materialized — `load_safetensors_cpu_tensors` answers `None` and the caller takes its own mmap-backed path. Eviction is LRU over entries whose `Arc` strong count is 1, so an engine still streaming from a cached map (SD3's offloaded MMDiT) is never robbed. Unbounded, this cache is what pinned FLUX's 9.79 GB `t5xxl_fp16` in host RAM for the life of the process and made a 64 GB host refuse H3 until it was restarted (#1273); an encoder that genuinely should stay in host RAM belongs behind `MOLD_KEEP_TE_RAM=1`, which parks it _inside the engine_ where `unload()` releases it.
- **CPU-based noise** — `seeded_randn()` in `engine.rs` generates initial noise on CPU via `StdRng`/ChaCha20, then moves to GPU. This is load-bearing for cross-backend seed determinism (CUDA/Metal/CPU produce identical images).
- **Fatal CUDA contexts are never reused or reset in-process** — illegal-address, uncorrectable-ECC, launch-failure/assert, and related faults permanently quarantine that worker and stop the server with an error so service supervision can restart the process; the embedded desktop must relaunch the whole app. Apply this to normal jobs, durable chains, admin loads, and post-upscalers, and reject buffered jobs before touching CUDA. In-process `cuDevicePrimaryCtxReset_v2` is unsafe while Candle/cudarc objects may retain primary-context handles; do not downgrade fatal errors to the timed cooldown. Quantized Qwen edit keeps split CFG even on high-VRAM CUDA cards.
- **Qwen-Image's quantized linear arm is chosen from the weight, never from the device alone** — and every way candle's kernels can decline lands in the same BF16-hostile fallback, so each is gated. `qwen_image/quantized_transformer.rs` splits that gate in two: `select_linear_kind` is a pure function of (device class, weight GGML dtype, weight `in_features`, weight residency, `MOLD_QWEN_QMATMUL`, `FORCE_DMMV`) for everything a weight settles at load, and `qmatmul_forward_supported` re-asks the activation-shaped half (rank 2 or 3; `FORCE_DMMV` again) per forward, degrading that one call to the retained dequant path. Metal has always used `QMatMul`; CUDA joins it only for a dtype `fast_mmq::supports` accepts whose row width its `qk` divides, resident on the activations' device, because the failures are errors rather than slowdowns — the `dequantize_matmul` fallback reads the activation as `f32` and rejects BF16, and a CPU-staged `QTensor` meeting the CUDA matmul is `unreachable!`, a panic. `FORCE_DMMV` is in that set because it is a **process-global** switch mold itself flips (`MOLD_WAN_FORCE_DMMV=1`, inside Wan's denoise loop) and never clears, and candle exposes no reader — `crate::quantized_dmmv` is the mold-owned mirror every writer must route through and every reader must consult. The `QMatMul` arm also normalizes its activation to `working_dtype` exactly as the dequant arm does (the CUDA kernels return the dtype they were fed, and the bias is materialized at `working_dtype`, so an F32 activation such as `TimestepProjEmbeddings`' would meet a BF16 bias) and materializes a non-contiguous one. The same rule is why the GGUF LoRA merge must land on the device — through `mold_candle::quantized::quantize_onto`, as every peer family does — and not on the CPU. FP8 (safetensors, not GGUF) is a separate path: `scale_weight` rides on the matmul output whenever it is a scalar or per-output row, so the forward keeps exactly one full-size pass, and the block-offload path widens FP8 weights once at load — unconditionally, since `candle_nn::linear` has no FP8 arm at all, which is why `MOLD_QWEN_FP8_CACHE` does not reach it.
- **Z-Image has a bespoke quantized transformer** — `zimage/quantized_transformer.rs` lives here (not candle); GGUF tensor naming differs from BF16 (`attention.qkv` vs split Q/K/V, etc.). Its linears dispatch per backend through `select_linear_kind`: CUDA defaults to a per-forward dequant arm because candle's fast MMQ kernels return non-finite values for Z-Image's linears (solid-black renders — the same defect family as `docs/architecture/qwen-mmq-nan.md`, which records the Z-Image evidence); Metal and CPU keep `QMatMul`, the arm the #942 sd.cpp validation qualified. `MOLD_ZIMAGE_QMATMUL=1` re-enables the CUDA fast path for the kernel investigation. GGUF transformers always stay quantized at rest; the unplanned dense-map diagnostic route was removed in #1109. Any env var read through `crate::runtime_env::value` MUST be listed in `ENGINE_SHAPING_VARIABLES` plus a mold-server `runtime_semantic_variable` arm or it silently reads as unset.
- **Z-Image's primary reference is stable-diffusion.cpp, not the Python upstream.** <https://github.com/leejet/stable-diffusion.cpp> (`src/model/diffusion/z_image.hpp`, `src/model/name_conversion.cpp`, `docs/z_image.md`) is the authority for every Z-Image question — forward composition, RoPE, the fused-QKV layout, quantization policy, and prompt semantics. It is chosen over <https://github.com/Tongyi-MAI/Z-Image> because it is a **runnable oracle on the same hardware**: it publishes the `leejet/Z-Image-Turbo-GGUF` checkpoints mold downloads, it supports Metal, and it renders those exact files correctly. Reading the Python upstream established that mold's port "matches" while mold still rendered garbage; running sd.cpp on the identical GGUF settled in one command that the file, the quantization, and the Metal backend were all fine and the fault was mold's. Prefer an executable comparison to a code read. Build it once and keep it: clone into gitignored `tmp/` and `cmake -B build -DSD_METAL=ON -DGGML_ACCELERATE=OFF -DGGML_BLAS=OFF -DCMAKE_OSX_DEPLOYMENT_TARGET=<major>.0 -DCMAKE_C_FLAGS=-Wno-error` (Accelerate off avoids Apple's own `vDSP.h`/`lapack.h` failing `-Welaborated-enum-base` on recent SDKs; the deployment target avoids `MTL4CommandQueue` availability errors). Then `./build/bin/sd-cli --diffusion-model <gguf> --vae <flux ae> --llm <qwen3 gguf> --cfg-scale 1.0 --steps 8`. Cite `file:line` from sd.cpp when a change is justified by it. The Python upstream remains useful for the pipeline-level contract (scheduler shift, `(1000-t)/1000` timestep, output negation, `hidden_states[-2]` conditioning, chat template) — all of which mold already matches.
- **Flux.2's sampling regime is a property of the checkpoint tier, and only the base tier branches.** Three tiers share one engine and one `Flux2Config` shape. Distilled [klein] carries no guidance embedding and ignores the guidance value entirely (4 steps, scale 1.0). [dev] carries one (`guidance_embed: true`) and consumes the scale through `guidance_in` — which the GGUF path silently dropped before quantized dev tiers existed, so a quantized dev render would have denoised at the unguided vector regardless of the request; `comfy/ldm/flux/model.py:171-173` is the term, and it loads only when `cfg.guidance_embed`, so Klein GGUFs (which ship no such tensors) still load. The UNDISTILLED [klein] base tier carries no embedding either, so its scale can only reach the render as real classifier-free guidance: `Flux2TransformerWrapper::denoise` takes an `Option<&Flux2CfgBranch>` and both passes go through one `forward_once`, so `None` is byte-identical to the pre-CFG loop and the two passes cannot drift apart. The gate mirrors `diffusers`' `pipeline_flux2_klein.py:593` (`guidance_scale > 1 and not is_distilled`), the default negative prompt is `""` (`:748`), and the combination is `neg + scale * (pos - neg)` (`:875`). **"Undistilled" is a NAME test** — `mold_core::validation::is_flux2_base_model`, the one authority `GuidanceCapabilities::for_recipe`, the studio fallback, and the engine all read — because `transformer/config.json` is byte-for-byte identical between the base and distilled checkpoints, so neither the header nor the GGUF metadata can tell them apart; an opaque catalog ID is therefore sampled as distilled, which is the conservative direction (one forward, a scale the checkpoint ignores). The prompt cache is asked for the render's prompts as a SET so one encoder load serves whichever half missed, and a fully cached CFG render still skips the encoder entirely.
- **A gated repo is a dependency of a TIER, not of a family.** BFL's `FLUX.2-dev` repo holds the transformer and the Mistral3 encoder together, so pinning the runtime assets there would have put the ungated community quantizations behind a license acceptance for bytes that are published ungated elsewhere. `shared_flux2_dev_open_files` pins Comfy-Org's mirrors instead — the VAE's sha256 is IDENTICAL to the gated file the manifest already pinned, and the Mistral3 single-file's language model is pruned to layers 0-29 plus `model.norm`, exactly the prefix `encoders::mistral3` streams, under HF-native keys the loader resolves from the header (it also ships a vision tower and projector, which an mmap never pages in because nothing requests them). Verify a mirror by its digest or its tensor inventory before pinning it; never assume a re-upload is the same bytes. The two sets land in one `shared/flux2-dev/` bucket and cannot collide (`split_files/...` and a bare `tokenizer.json` against BFL's `text_encoder/`, `vae/`, `tokenizer/` prefixes), so a host may install both.
- **An FP8 checkpoint without its scale is not a slightly worse render, it is noise.** `quantize` divides by the per-tensor scale (`comfy/quant_ops.py:138`), so dropping a scale of ~2e-3 inflates every weight in the layer ~500x. Two spellings exist for the same thing — BFL's own conversions and Comfy-Org's `fp8mixed` write `<base>.weight_scale`, ComfyUI's re-exports write `<base>.scale_weight` — and the single-file backend normalizes both to the one subkey `Flux2Linear::new` probes for. The other half is dtype: the backend must hand FP8 weights back at their ON-DISK dtype (`preserve_fp8`), because casting them to the VarBuilder's dtype makes `Flux2Linear::new` take its BF16 arm, which never looks for a scale — both halves had to be wrong together for the bug to be silent. Mixed files are the norm (Comfy-Org's dev `fp8mixed` leaves all attention in BF16), so the decision is per tensor, like `collect_nvfp4_bases`. A rank-0 scale rides on the matmul OUTPUT, never on the dequantized slab — the Qwen-Image FP8 rule.
- **Wan's chain carryover is a property of the checkpoint, never the family.** Wan has no latent motion tail: its smooth handoff is last-frame _image_ conditioning, which only an image-conditioned checkpoint accepts. `mold_inference::chain::wan_carryover` is a total function of the `source_image` contract `wan::pipeline::source_image_capability` derives from the checkpoint's own headers — `Required` (A14B I2V 36-channel concat) and `Optional` (TI2V-5B latent inpaint) continue, `Unsupported` (text-to-video) concatenates independent clips, and an unclassified checkpoint is "unknown" and takes the conservative path. `capability_for_family("wan")` is the floor, not the answer; callers holding a concrete model use `capability_for_model`. The seam duplicates exactly `WAN_HANDOFF_DUPLICATED_FRAMES` = **1** frame — the one the continuation was seeded with — which is deliberately not LTX-2's 17, the pixel window its VAE turns into three latent slots. That constant lives in `mold_core::validation` (the engine re-exports it) because admission, `/api/models`, and the CLI chain planner must all derive from one authority: `default_extend_overlap_frames_for_family` resolves the extend default from it, so wan advertises and defaults to 1 while LTX-2 keeps 17 — a family-blind 17 sits on wan's `4k+1` grid, clears validation, and then fails in the engine after the load is paid for. Clip lengths are `4k+1`; the auto-chain routing default is the selected tier's own manifest default frame count over a VRAM-envelope floor (53 A14B / 121 5B), not the 257-frame request cap — a default raised on a measurement must render as one clip rather than silently routing to a stitched sequence. Never advertise `supports_sequence` for a family whose engine does not implement `ChainStageRenderer` — wan's did not, and the capability arm shipped a promise the worker could not execute; the static `batch.rs` family table's `chain` flag is pinned to `chain::capability_for_family` by a contract test for the same reason. An extend carries source frames too: `validation::request_carries_source_frames` is the one predicate the #772 source-image contract gate is asked, and omitting the extend case refused every Wan I2V continuation with the very contract that makes it extend-capable.
- **LTX-2's runtime session outlives the generation, but holds almost nothing (#1099).** Plain T2V writes its `Ltx2RuntimeSession` back after a successful render (mirroring the audio/chain paths; `MOLD_LTX2_KEEP_SESSION=0` opts out — read via `std::env`, deliberately not a fingerprint input). The session retains only the cached prompt encoding and device handle: the Gemma encoder is consumed on the first `prepare()` to free memory for the transformer, and neither transformer nor VAE lives in the session. So reuse (`can_reuse_for`, exact token-pair match) skips the ~24 GB Gemma reload for same-prompt repeats only; a changed prompt pays a full rebuild, and no admission-side residency credit exists because nothing large stays resident. A failed prepare/render drops the session — rebuilding is the recovery path. `unload()` (ModelCache eviction) releases it. **Host-RAM admission charges only irreclaimable bytes.** A CPU-placed BF16 Gemma reserves the streaming anon-heap peak alone (`ltx2::cpu_gemma_streaming_anon_peak_bytes`, pinned to the `device.rs` BF16 arithmetic ×F32) and **not** its shard bytes: `load_from_assets` builds through `new_streaming`, so the shards stay an mmap'd `VarBuilder` whose file-backed pages are reclaimable and are already counted as free by `MemAvailable`, the ledger's own input. Charging them asks for ~24 GB of free anonymous room for memory that cannot OOM, and refuses every job on a host whose headroom lands just under the sum (#1108, regression-tested at hal9000's exact numbers). A flat 2× estimate is wrong in the same direction and parks the host that reported #1099 (also regression-tested). The GGUF Gemma keeps quantized residency in host RAM and every other family's CPU-parked encoder is copied there, so both still reserve their bytes — the predicate is `ltx2_cpu_gemma_streams_from_mmap`, never the family alone.
- **LTX-2's source of truth is upstream, not this repo.** <https://github.com/Lightricks/LTX-2> is the reference implementation for every LTX / LTX-2 / LTX-2.3 question — sampling schedules, guidance, conditioning, VAE tiling, block streaming, quantization policy, and prompt semantics. Before changing an LTX engine or arguing about correct behaviour, read upstream rather than inferring intent from mold's port. Clone it to a scratch location and pull before consulting it (the repo moves fast; `packages/ltx-core` is the inference core and `packages/ltx-pipelines` holds the pipeline drivers plus the documented CLI flags). Keep the clone out of the worktree — `tmp/` is gitignored and is where the existing checkout lives. Cite upstream `file:line` when a change is justified by it. Note upstream's own consumer-GPU guidance is `--offload {cpu,disk}` plus `--quantization fp8-cast`; heavy block streaming is the intended way a 19B checkpoint fits a 24 GB card, not a failure mode.
- **Wan supports CUDA and a Metal correctness path (#800).** Metal is `CorrectnessOnly` pending perf UAT. Four things make it real, and all four are load-bearing: the VAE's rank-5 channel norm and rank-6 group mean route through the shared `crate::metal_reduce` fold (candle's Metal backend silently mis-reduces rank ≥ 5 tensors over non-final dims — the LTX-2 black-clip bug; never call `sum`/`mean` directly on such shapes in a Metal-reachable path), math attention auto-chunks on Metal as on CUDA (unchunked, the score matrix is a single 9.5–71 GB buffer), the compute dtype is family-scoped BF16 via `wan/backend.rs` (mirrors `ltx2/backend.rs`; `CastBoundary`'s F32 into QMatMul is a Metal _panic_ guard, not just a VRAM choice — never remove it), and fp8-scaled checkpoints are refused by name on Metal (no F8E4M3 cast kernel). GGUF tiers run on Metal — the old "GGUF stays CUDA-only" scoping was about kernel existence, which is complete.
- **LTX-2 supports CUDA and Metal; CPU is correctness-only.** Metal is performance-qualified (#597): family-scoped BF16, fused SDPA, streamed FP8 LUT widening, framewise VAE decode, measured on the 19B/22B distilled FP8 tiers on Apple Silicon (#1030 campaign). Native runtime lives in `ltx2/` with its own media pipeline (MP4 first, real AAC).
- **LTX-2 runtime-asset bundling is mixed.** Catalog checkpoints may be combined or transformer-only; resolve `ltx2-vae` for v2 and `ltx2.3-vae` for v2.3. Diffusion-only LTX-2.3 exports also require `ltx2.3-text-projection`. Preserve those concrete paths in every chain-stage plan. Catalog checkpoints without a bundled spatial upscaler default to the chain-capable one-stage pipeline even though their stable `cv:` / `hf:` IDs do not contain `distilled`; UI eligibility and chain-limit lookup must use that invariant rather than parsing a pipeline label from the opaque ID. ConvRot W4A4 checkpoints use the dedicated `ltx2/convrot.rs` compatibility backend. A Gemma prompt-encoder OOM may move only Gemma to CPU; preserve the transformer and video VAE CUDA device through the retry.
- **LTX-2's spatial ceiling is the trained RoPE span, and past it stage 2 tiles.** `positional_embedding_max_pos = [20, 2048, 2048]` normalizes pixel positions, so an axis past 2048 px is out of distribution — it renders, badly, without erroring. `ltx2/tiling.rs` owns the arithmetic (interval splitting, the trapezoidal window whose ramps sum to one across an overlap, tile enumeration, and the `SpatialTilePolicy` both consumers resolve); `runtime.rs`'s `TiledStage2Pass` owns execution: per-tile latent slice, positions built at the tile's own pixel shape (mold's equivalent of upstream `normalize_positions=True`), noise seeded `seed + tile_index`, conditioning sliced by the tile and by `reference_downscale_factor`, then `index_add` accumulation in token space. `--spatial-tile` / `MOLD_LTX2_SPATIAL_TILE` is one knob over both stage 2 and the VAE decode: `auto` (default) can only engage past 2048 px, so nothing currently renderable changes; `off` restores the untiled path; `<px>[:<overlap>]` forces a size, which is the only way to compare tiled against untiled at a resolution needing neither. Two invariants: a one-tile plan must stay bit-identical to the pre-tiling path (it short-circuits before the blend), and a tiled stage 2 refines video only, carrying stage 1's audio through unrefined — upstream's `hdr_ic_lora.py:504-507` runs "a tile-sized `ModalitySpec` for video only", and `Stage2AudioInputs` switches shape, latents, noise, positions, and context off as one unit because half a branch makes the transformer reject the step. Do not add a normalization pass to the blend — if the windows do not already sum to one the layout is wrong, and `clamp_dimension_tiling` refuses the triple-overlap layouts where upstream's own clamp does not.
- **LTX-2's resolution ceiling is a property of the render, not the family.** The checkpoints normalize RoPE pixel positions by 2048 px, so that span bounds _one un-tiled denoise_. A checkpoint that ships the spatial upsampler never denoises the requested shape — it renders stage 1 at half the target (`derive_stage1_render_shape`), doubles that latent with the learned upsampler, and refines it over tiles (`plan_stage2_tiling`), so its ceiling is `LTX2_COMPOSED_MAX_AXIS_PIXELS` = 2 x the span = 4096 px, with `LTX2_COMPOSED_MAX_PIXELS` = 4096x2176. The factor of two is exact, not a margin: mold applies one spatial rung, so 4096 is the widest target whose halved stage 1 still lands inside the span. Resolve it through `mold_core::validation::ltx2_spatial_composition(model, pipeline)` — never by family — which requires both a manifest `SpatialUpscaler` component and `Ltx2PipelineMode::refines_spatially()`; `ltx2::runtime::pipeline_uses_two_stage_spatial_refinement` delegates to that same predicate so admission and execution cannot drift. `/api/models` advertises per-model `max_pixels` + additive `max_axis_pixels` and omits composed rungs from `recommended_dimensions` for a checkpoint that cannot reach them; clients read those and keep the family constants only as the single-pass fallback. `LTX2_OUTPUT_RUNGS` names the ladder (1280x704 → 3840x2112, every rung /64 so the halved shape lands on the VAE's /32 grid) and its `stage1_shape()` / `stage2_tiles()` are pinned to the engine's own arithmetic by a test in `ltx2/tiling.rs`. The ceiling belongs to the **rung**, not the checkpoint: `--spatial-upscale x1.5` only divides by 1.5, so it reaches 3072px, and `validate_ltx2_stage1_span` checks the derived stage-1 shape rather than trusting the x2 ceiling. Resolve the pipeline through `ltx2_spatial_composition_for_request`, which mirrors `select_pipeline`'s implicit branch order — a request carrying `retake_range` routes to the single-pass retake before the upsampler fallback is reached. **The ladder stops below the generation ceiling on purpose**: admission allows 4096px, but the bundled OpenH264 encoder refuses past 3840x2160, so 3840x2176 renders correctly and then fails at save time — the rung rounds 2160 _down_ to 2112, which is upstream's own `CENTER_CROP` alignment. Measured on an RTX 4090 at 25 frames, 1080p/1440p/4K all peak near 18 GB because the composition bounds the forward pass; 4K needs `--spatial-tile 768` (the default 1280px tile OOMs in the VAE decode). Never let `--spatial-tile off` past the span render — it must fail.
- **LTX-2's frame ceiling is a duration, never a frame count.** The checkpoints ship `pos_embed_max_pos = 20` and `ltx2/model/rope.rs`'s `scale_video_time_to_seconds` normalizes the temporal RoPE axis in _seconds_, so the budget is 20 s of runtime: `frames <= LTX2_MAX_RUNTIME_SECONDS * fps + 4`, clamped by `LTX2_MAX_FRAMES_ABSOLUTE`. Derive it through `mold_core::validation::ltx2_max_frames_at_fps` / `studio/lib/videoBudget.ts` on every surface; a hard-coded scalar is wrong in both directions (too strict at 24 fps, too lax at 6). `/api/models` advertises `max_frames` at the model's own fps plus additive `max_runtime_seconds` / `max_frames_absolute`, and `/api/capabilities/chain-limits` takes `?fps=` and echoes what it used. The executable oracle is stable-diffusion.cpp (`tmp/sdcpp`: `src/model/adapter/pulid.hpp`, `src/model/diffusion/flux.hpp:993-1004` and `:1120-1161`, `docs/pulid.md`'s three-way SHA falsification), and `ToTheBeginning/PuLID` is the reference port; module parity is pinned to a golden captured from upstream in `crates/mold-inference/testdata/pulid/`.
- **PuLID's SDXL adapter is a UNet cross-attention injection, and its layer table is a permutation.** `crates/mold-inference/src/sdxl/pulid.rs` ports `pulid/attention_processor.py:275-422` under the module globals this checkpoint was trained with — `NUM_ZERO = 0`, `ORTHO = ORTHO_v2 = False`, so the shipped arithmetic is the plain additive branch at `:378`. The IDFormer is shared: `identity::extraction::idformer_prefix` is the single family-specific fact (`id_adapter` versus `pulid_encoder`) because upstream instantiates the same `IDFormer()` class in both pipelines, and the extraction cache key takes the family's own adapter digest so one photograph never serves one family the other's embedding. `sdxl_unet_layout()` is mold's copy of SDXL's published `unet/config.json` because candle keeps `StableDiffusionConfig.unet` private; the fixture test and the two runtime guards are what keep it honest.
- **PuLID face extraction runs through resident candle modules, not `candle-onnx`, and the embedding it produces is RAW.** `mold-inference/src/identity/` (feature `pulid`) ports InsightFace and facexlib, never mold's intuition — every function cites the upstream file and line range, and `docs/architecture/pulid-face-extraction.md` is the Step-0 decision record with the measured numbers. Six things are load-bearing. (1) The two graphs are **weight containers, not a runtime**: `identity/onnx_weights.rs` reads their initializers ONCE at load through the same authenticated bounded read, and `identity/scrfd_net.rs` / `identity/arcface_net.rs` run them as ordinary resident `candle-core`/`candle-nn` modules (#1227). `candle_onnx::simple_eval` survives only as `reference_forward`, the parity oracle — never a production path, because it re-materializes every initializer on `Device::Cpu` on every call. Both modules take a device, and it is HONOURED as of #1227 phase 2: phase 2 moved the whole extraction inside the leased job, so there is finally a device to name (the bullet below), and `IdentityExtractor::load`'s earlier CPU-only assertion — "extraction runs at admission, before a device is leased" — described the call site rather than the arithmetic, and the call site moved. The qualifying latency is still warm-repeated, 5 warmups / 20 runs, and `pulid_face_probe bench` re-measures instead of re-arguing: `--compare` runs both evaluators alternately in one loop, `--full` adds the EVA tower and the IDFormer, and `--regress-against` checks a p95 against the committed per-host baselines. **The re-materialization was not the cost centre** — measured 1.04x, not the 25% #1227 set out to find, because a 261 MB copy is cheap next to 23 GFLOP of f32 convolution. §4 records the numbers, and the EVA02-CLIP tower, unmeasured until #1227, is **79%** of a real extraction (2,237 ms of 2,840 ms p50 on halcyon) against the face stack's 13%. (2) `scrfd_10g_bnkps.onnx`'s `Resize` nodes pass an **empty tensor** for the absent `scales`, and candle-onnx presence-tests the input NAME, not the tensor, so it bails "Scales and sizes cannot both be set"; `onnx_graph::normalize_empty_optional_resize_inputs` rewrites that one case, scoped to `Resize` only, until the one-condition candle fix lands. Since #1227 that rewrite only affects `simple_eval`, i.e. the parity oracle; the resident port reads the `Resize` nodes' target size from the tensor it is adding to. (3) The ArcFace embedding is the raw 512-d network output — `pipeline_flux.py:130`/`:156-158` never normalize it, in visible contrast to the EVA branch at `:177-178` that does — so handing #1229 a unit vector silently rescales the IDFormer's input; `l2_normalized()` exists for cosine comparisons only. (4) The pixel ops are OpenCV's conventions reimplemented in `identity/warp.rs`, not `image::imageops` (whose triangle support scales with the ratio) and not `imageproc` (a candle-workspace dep, not a mold one). (5) Both graphs are re-authenticated against the manifest pin on EVERY load, before decoding, against the digest of the EXACT bytes decoded — one BOUNDED `read_to_end`, hashed, compared, parsed, enforced by the private `AuthenticatedBytes` type and a structural test, because hashing a descriptor and then reading it is two passes and an in-place write between them authenticates one set of bytes and executes another; the bound is the manifest's own `size_bytes`, carried with the digest in one `PinnedArtifact` and checked by `fstat` BEFORE the read (a digest needs bytes in memory, so an unbounded read of an oversized replacement OOMs before it can report the mismatch), with `expected + 1` as the read cap so a file growing mid-read is refused rather than truncated, and `UNPINNED_MAX_BYTES` (1 GiB) for the tools that load arbitrary graphs; the downloader's `.sha256-verified` marker attests to the bytes that landed, not the bytes now, and `IdentityExtractor` has no unverified constructor. (6) `extract` decodes through `img_utils::decode_oriented_srgb`, the crate's single EXIF/ICC path (lifted out of `ltx2/preprocess.rs`, which re-exports it) — a phone photo stores its rotation in a tag, and an unoriented buffer hands SCRFD a sideways face. Enabling `pulid` needs `protoc` at build time: `pkgs.protobuf` is already in the devshell, in crane's and the desktop derivation's `nativeBuildInputs`, and installed by CI on both Linux (`protobuf-compiler`) and macOS (`brew install protobuf`).

The final logit upsample and its argmax are FUSED (`bilinear_align_corners_argmax`) because interpolating logits can elect a class that wins at no low-resolution sample, so upsampling the labels instead is a different function rather than an optimization. It is a candle port and not a fourth ONNX graph because the same machine-derived Step-0 gate — `pulid_face_probe gate <graph.onnx>` — refuses a real opset-11 export on three counts that are missing evaluators rather than exporter idioms: `MaxPool` pads, `Resize mode=linear`, and `Resize coordinate_transformation_mode=align_corners`. Pinning a stranger's re-save was the alternative and is not one. **Both derived artifacts reach their loaders as `AuthenticatedArtifact` — resolved once through a retained `Dir` descriptor, `fstat`ed against a pinned length, read once into a PRIVATE buffer under a `size + 1` bound, hashed there, and handed to the `VarBuilder` as those same bytes — never as a `PathBuf` and never as a shared mapping.** Both halves are load-bearing: a pathname resolves one name twice and a rename needs only the PARENT's write bit, while a mapping is a live view and collaborative `0664` weights mean another member may write the inode in place after the digest — descriptor retention proves which inode, never which bytes. The parser's production code names no path type at all and none of the four files in the chain names a mapping type; structural tests keep it that way. The PuLID adapter stays a pathname load on purpose: it is a manifest file verified at download, with no fresher authentication to discard. **RetinaFace stays unimplemented on evidence, not on deferral**: with the mask in place, swapping SCRFD's landmarks for facexlib's moves the final identity by at most 2.8e-3 of peak, against the 1.2–1.5e-2 the mask itself was worth. Mold runs ONE detection and gives the same face to both crops — upstream takes the largest for ArcFace and the most CENTRAL for the 512 crop, from two detectors, so on a group photograph its two halves describe two people. Numbers, the gate output, and the acceptance pins: `docs/architecture/pulid-face-extraction.md`. The bundle is now five files: `pulid_assets::PulidPaths` resolves the parser's `.pth` alongside the adapter, EVA tower, detector, and recognizer, and `IdentityAssetDigests` carries a fifth digest — the derived parser — so a different parser is a different identity.
- **PuLID's identity encoders are a port, and the EVA02-CLIP release is converted before it is ever loaded.** `encoders/eva_clip_vision.rs` ports `ToTheBeginning/PuLID`'s `eva_clip/eva_vit_model.py`; candle's `eva2.rs` shares the attention/SwiGLU shapes but is a fixed-448 classifier with a different layout and no hidden-state taps. Four things are silently wrong if ported from memory: RoPE is 2D over a 16x16 trained grid interpolated to 24x24 **entirely through the position ramp**, its `rotate_half` pairs **adjacent** lanes (not split halves), it is applied to patch tokens only and never to CLS, and attention is sub-LN with `q_bias`/`v_bias` supplied out of band and **no k bias at all**. The five hidden states are the residual stream **entering** blocks 4/8/12/16/20, not their outputs (`eva_vit_model.py:526` appends before running the block), and the MLP hidden width is `int(1024 * 2.6667)` = **2730**. The CLIP projection's L2 normalization stays in the tower's working dtype — upstream's `torch.norm`/`torch.div` run on a `weight_dtype` tensor (`pipeline_flux.py:176-179`), so widening to f32 is a divergence, not an improvement. Preprocessing is torchvision's _antialiased_ bicubic with Keys `a = -0.5` — not the -0.75 of PyTorch's plain bicubic, and not the `image` crate's `CatmullRom` — on the float tensor, unclamped. BAAI ships the tower as a torch pickle and **mold's runtime never reads a pickle**: `encoders/pickle_convert.rs` (renamed from `eva_clip_convert.rs` once it also converted facexlib's BiSeNet release) is the only place one is opened, converting once to vision-only safetensors from the SHA-verified source; the EVA tower's modern zip container and the BiSeNet parser's legacy pre-1.6 `torch.save` archive (`encoders/legacy_pth.rs`) share this one authenticated conversion path. Three rules make that load authentic and none is optional. The source is parsed from a **private copy made from the retained descriptor** and hashed on that same stream, because candle's `PthTensors` re-opens by pathname per tensor — a descriptor hash plus a pathname parse authenticates nothing, an inode re-check only samples the name at two instants, and `/dev/fd/N` is `dup(N)` on macOS so candle's second open reads an exhausted offset. That copy is staged under `$XDG_RUNTIME_DIR`/`$TMPDIR` and **never in the model root**, because a `0o700` directory is only as private as its parent: renaming an entry needs write permission on the CONTAINING directory, so a group-writable model root lets another member swap the verified copy for unpinned bytes before the pickle parser reads it (`secure_dir::parent_policy` tests STICKY FIRST — sticky owned by us or root is safe however open the write bits are, and checking ownership first rejects root-owned `1777` `/tmp`, the only candidate on a headless box with neither var set; a sticky directory owned by another unprivileged user is still refused because sticky lets the directory's owner rename entries, and a non-sticky one must be ours and unwritable by group/other. No `MOLD_*` var, `TMPDIR` is the knob, and free space is checked before the 856 MB copy). Every publish is a **`renameat` between retained directory descriptors**, out of an exclusively created 0o700 staging directory — never `std::fs::write`, which follows a pre-planted symlink at the destination, and never a pathname `rename`, because renaming an entry needs write permission on the PARENT, so a group-writable model root lets another member swap the staging directory between the hash and the publish (`encoders/secure_dir.rs` owns the primitive; the published file's `(dev, ino)` is re-verified through the parent descriptor afterwards). And reuse is authenticated by the compiled-in `DERIVED_SHA256`, never by the sidecar, which mold writes and an attacker could forge to match. `flux/pulid_encoder.rs` is the IDFormer; its `proj_out` is a bare parameter used as `latents @ proj_out` and must never be transposed like an `nn.Linear` weight, the five identity tokens stay in **every** scale's key/value context, and its softmax is widened to f32 and cast back (`encoders_transformer.py:114`) — worth 4x in BF16, and deliberately NOT done in the EVA02 tower, whose upstream softmax carries no cast. Parity goldens, the full tensor mapping, and the measured tolerances live in `crates/mold-inference/testdata/pulid/README.md`; the lifecycle is `docs/architecture/pulid.md`.
- **PuLID face extraction runs inside the lease, on the render's own device, and it is a typed scheduler phase.** #1223 ran it at admission on the host for two reasons that have both expired: `candle-onnx` could not place a tensor off the CPU (#1227 phase 1 replaced it with resident candle ports), and a pre-lease phase cannot overlap the T5/CLIP encode peak by construction. Phase 2 traded the second for its cost — `docs/architecture/pulid-perf.md` §4 measured one extraction at 2,840 ms of which the EVA02-CLIP tower alone was 79% — and moved the whole stack (detector, recognizer, BiSeNet parser, tower, IDFormer) into the leased job as `ProgressPhase::IdentityExtract`, emitted **before the model load**, not merely before prompt encode. That ordering IS the drop-before-adapter rule: every one of those five is built, forwarded, and fully released in turn, so on a cold load none coexists with the transformer, let alone with the ~1.14 GB adapter `EngineIdentityState` makes resident. A warm engine cache does have the transformer resident, which is exactly why `memory_preflight::IDENTITY_EXTRACTION_VRAM_OVERHEAD_BYTES` (= `mold_core::identity::EXTRACTION_DEVICE_PEAK_BYTES`) is charged ADDITIVELY beside `IDENTITY_VRAM_OVERHEAD_BYTES` rather than as a maximum. Metal charges it ONCE through the unified device gate and nothing to the host ledger; on CUDA the host side is only the private authenticated copy the `VarBuilder` reads from, which the identity artifacts' own `is_host_only` component roles already charge. `ExtractionSlot`'s bespoke semaphore-plus-`ram_snapshot()` is RETIRED, not run beside the ledger — its own justification was "extraction happens strictly BEFORE this job has a lease", which expired with the call site, and two admission-time memory gates that can disagree is worse than one (`no_second_memory_gate_lives_in_this_module` is the structural pin). Serialization comes free: a lease is already exclusive on its device. "Exactly once per parent" is unchanged and still counted — the first sibling to reach a device extracts, the rest are answered by the cache without opening a model, and a re-prepared batch child still carries its parent's frozen value. The forced-local CLI runs the identical `mold_server::identity_extraction::resolve_identity_for_lease` at the identical point, so a CPU-only local device is just the `ExtractionPlacement::Host` arm of the same code. The tower's working dtype is `identity::extraction::eva_working_dtype`: f32 on the host (candle has no narrow CPU kernels, and every committed golden was captured there), f16 on a device — the dtype the derived file already stores, and narrower than upstream's own cast (`PuLID/pulid/pipeline_flux.py:60`, `PuLID/app_flux.py:45`). The IDFormer half computes in f32 whatever the tower did. Device and host agree on the final tokens to a measured **3.82e-5** of peak, inside the 5e-5 the whole-stack golden already states; no new tolerance was invented. Measured on halcyon (M4 Max, 5-warmup / 20-run): whole extraction **3,073.6 → 1,907.3 ms** on the CPU (the memo alone) and **395.3 ms** on Metal. CUDA is measured on plato (L40S): whole extraction **573.2 ms** on a quiet box and **688–795 ms** under normal load, device peak **637.5–643.8 MB** against a 700,000,000 charge, parity worst **4.908e-5** (98% of the 5e-5 budget, against Metal's 76%) — a future change to the tower's CUDA arithmetic fails there first, and the constant must not be loosened in response.
- **Installed derived artifacts are loaded without integrity hashes.** `pickle_convert::open_installed` retains size/read/descriptor fences; newly converted outputs are verified once. Legacy conversion stages an installed source without hashing it. Identity cache keys resolve all five actual installed assets before cache lookup; expected pins are not observed digests.
- **One identity photograph is extracted once per process, and the cache key is the whole pipeline.** `mold_inference::identity::extraction` holds a 16-entry LRU (fixed 256 KiB each, ~4.2 MB) of final `[1, 32, 2048]` tokens keyed by `mold_core::identity::identity_cache_key` — the photograph's SHA-256, `IDENTITY_PIPELINE_VERSION`, and all five asset digests, composed the way `fingerprint_of` composes the output fingerprint but over inputs knowable BEFORE anything is opened (`pinned_asset_digests`). **Bump `IDENTITY_PIPELINE_VERSION` in the same PR as any semantic change to SCRFD, the alignment, the warp, ArcFace, the EVA preprocessing, the tower, the mask, or the IDFormer** — it is the one invalidation case that is not structural, because none of those files moves. The key carries no device, deliberately: host and device agree to a measured tolerance rather than bit-for-bit, so keying on the device would give one fleet several fingerprints for one face. The unconditional true-CFG identity is a SEPARATE degenerate memo on the adapter digest, because it is a pure function of the checkpoint (`pipeline_flux.py:188-192`) and would otherwise force a cached request to materialize the 605 MB `pulid_encoder.*` half for a tensor that never varies; that is why its zeros are shaped from the tower's declared geometry rather than a live output. In-process only and never persisted: these are a biometric derivative, and `pulid-perf.md` §2's argument against persistence is a retention story, not a performance one. Cold 2,184.8 ms → warm 1.8 ms, opening no models at all.
- **The identity cache is SINGLE-FLIGHT, because the callers are sibling GPU threads.** A plain get/put was right while extraction ran once per parent at admission; post-lease, a `batch_size = 4` parent's children are dispatched together and all four miss a cold cache in the window between the get and the put — N times the work, and N embeddings differing at the measured 3.82e-5 device tolerance, i.e. four siblings of one print conditioned on four slightly different faces with four different frozen fingerprints. The miss path therefore takes a per-key lock and a waiter **re-reads the cache and takes the winner's tokens** rather than computing its own; sibling embeddings are byte-identical by construction. Locks are taken in SORTED key order (a multi-photograph set takes several, and two requests sharing a subset in different orders would deadlock), the unconditional identity has its own flight key because its value reaches the fingerprint, and a failed flight stores nothing and releases the key — never negative-cache an extraction failure. The children need no frozen key from the parent: the key is a pure function of the bytes each child already carries, so content addressing already gives them one, and a second copy in the plan would be an authority that could disagree with those bytes. `identity_extraction_count` counts what was COMPOSED and `ResolvedIdentity::extracted` carries that to the server, so the once-per-parent counter is checkable again AND `ProgressPhase::IdentityExtract` is emitted only by the sibling that did the work — a cache hit reporting its ~2 ms would drag `ewma_identity_extract_ms` to a figure no cold request could meet. An uncond-only miss (first true-CFG request after an ordinary one) loads the IDFormer alone and never the face stack: 60.6 ms against ~340 ms.
- **An identity extraction failure is classified before it touches worker health.** Phase 2 put the extraction on the leased GPU, so its failures now reach the reliability counter that takes a sick card out of rotation. `IdentityError::is_user_input` is the authority — `NoFaceDetected`, `Decode`, `Alignment` are about the photograph and reproducible on every card; only `Runtime` is device-attributable — and `IdentityFailure` carries that attribution to `settle_identity_extraction_failure`, which quarantines on a fatal CUDA context, counts a device failure, and counts NOTHING for an unusable photograph. Three faceless images must not degrade a single-GPU host for a minute.
- **The derived-artifact memo is fenced on timestamp granularity.** Its key is metadata, so `ArtifactIdentity::is_fine_grained` refuses to memoize when both nanosecond fields are zero (the signature of a one-second-granularity filesystem), and the key is re-read from the same retained descriptor AFTER the private copy with both readings required to agree. What remains — a same-length write inside one coarse-clock tick (Linux stamps inodes from `ktime_get_coarse_real_ts64`, so "nanosecond" fields advance every 1–4 ms), with `ctime` not settable from userspace — is exactly `mold_core::download::pinned_file_digest`'s residual, which already guards every model weight mold loads.
- **Identity installation is once per dispatch, and its lifetime is the whole invariant.** When the effective `id_weight` is above zero, `mold_core::identity` owns the contract (the family-derived qualified set — `identity_family` / `IDENTITY_EXCLUDED_SDXL_MODELS` — the `0.0..=3.0` weight, the bounded decode limits, and `IDENTITY_RUNTIME_READY`, which is now `true` so a `pulid` build both advertises and executes). The reference photograph resolves into the immutable `FrozenIdentityEmbedding` (plain little-endian `f32` plus the source SHA-256s — one per photograph, in request order for the plural `id_images` form — the five asset digests including the derived BiSeNet parser, an optional unconditional embedding for true CFG, and a fingerprint over sources/assets/values) inside the leased job, as described above — never at admission any more. What admission still does is thread an `IdentityPin` cell onto `PreparedExecutionInputs` and pre-fill it whenever preparation already holds the answer, so "one extraction per parent, reused by every sibling on every device" stays structural without a second CPU-side extraction. The scheduler re-prepares dependencies for EVERY pending job including batch children, so a child is handed its parent's frozen value through `DependencyPreparationContext::frozen_identity` and skips extraction entirely; `compose_prepared_generation` carries it across as a backstop, and placement preview (`ExistingOnly`) extracts nothing at all. The GPU worker installs the resolved value through `InferenceEngine::install_identity_embedding` before EVERY dispatch and clears it otherwise — the engine is cached and the identity is not, so a stale embedding would condition the next print on the previous person; the default trait impl REFUSES a populated embedding rather than dropping it, and only `FluxEngine` overrides. Forced-local installs at the same point in `local_engine::build_local_engine_from_plan`, from the same `resolve_identity_for_lease` path the server's worker runs, which is what makes local/remote parity structural. Weight zero performs no pull, decode, load, or extraction and must stay byte-identical to an unconditioned render (the falsification case from `tmp/sdcpp/docs/pulid.md`). `EXTRACTION_HOST_PEAK_BYTES` (`mold_core::identity`) moved from 1.4 GB to 2.4 GB across #1227 phase 1 and #1225 together, and the two changes pull in opposite directions: the recognizer's 261 MB is now resident tensors rather than a retained `ModelProto` plus a per-call copy, so that transient half is gone, while the parser/tower conversion path adds a transient 609 MB (EVA tower) or 53 MB (BiSeNet parser) private copy, plus the EVA02-CLIP tower's f32 widening (~1.2 GB) that `VarBuilder`'s `DType::F32` always performed but the old figure never charged. The honest number is bigger even though the recognizer got cheaper; since phase 2 retired `ExtractionSlot` this constant describes the `ExtractionPlacement::Host` path specifically rather than gating an admission-time semaphore. Memory is measured, not declared: `IDENTITY_VRAM_OVERHEAD_BYTES` is 1.25 GB (the adapter's own resident arithmetic plus bounded cross-attention activations, resident for the whole denoise), and the detector, recognizer, EVA02-CLIP tower, and BiSeNet parser stay `is_host_only` in the memory model — their own bytes are charged as host demand rather than a per-component VRAM term — even though phase 2 now runs them on the leased device during extraction; that device-side cost is instead the flat, additive `EXTRACTION_DEVICE_PEAK_BYTES` charged beside them (the bullets above). The CLI reads `--id-image` through `commands::identity`: `open_regular_file_no_follow`, bounded from the descriptor before allocating, read from that exact descriptor, then `validate_id_image_bytes` — all before any request bytes exist; `id_image_name` is the file's own name and never the client path. The `pulid` feature ships ON in every release recipe (`flake.nix`, `release.yml`, both source PKGBUILDs, which now need `protobuf`/`protoc` for `candle-onnx`'s `prost-build`); the feature only decides whether the binary LINKS the stack, and the licence gate is the recorded InsightFace acceptance enforced at download time. `mold rm pulid-flux` deletes the derived EVA safetensors and its sidecar, whose names live in `mold_core::pulid_assets` because removal cannot see `mold-inference`.

- **Wan's activation estimate is backend-aware, and its two calibrations are fitted separately.** `device::wan_activation_budget_bytes_for` charges the math-attention score tile (`2 * heads * WAN_ATTENTION_QUERY_CHUNK * BF16`, 81,920 B/token at A14B — as much as the whole rest of the block) and charges ZERO under flash, whose online softmax never writes the tile to global memory. Both admission and `wan::block_offload`'s parking decision read this one authority, so an estimate blind to the backend parks blocks against a shortfall the running render does not have: at 81 frames / 832x480 that was `need_mib=14624` and all forty blocks parked, every one a host round-trip on the critical path of every step. **Never let the flash path inherit math's 2.14 slope.** The derived sum shrinks 44% while the residual the slope stands in for — LayerNorm F32 copies, RoPE, the q/k RMS norms, statement-scoped temporaries — does not, so the ratio has to RISE even as the absolute per-token cost falls; flash is 2.92 with a 1,949 MiB workspace against math's 2.14 / 2,301 MiB. Fit measurements are taken with `MOLD_WAN_OFFLOAD_BLOCKS=0`: parking lowers the peak, so a fit taken while the policy is engaged measures the policy rather than the render and then tells the policy to park less, which is the wrong direction and OOMs. `both_wan_calibrations_reproduce_their_measured_fits` pins each pair against the renders it was fitted to.
- **Wan retains what it can afford to, not what is expensive.** `MOLD_WAN_STEP_CACHE` defaults to `auto` (FBCache, measured 1.85x on the non-distilled tiers) because `WanStepCachePolicy::resolve` already refuses the two configurations where reuse cannot help. The engine caches its ~4 MB prompt ENCODING — compared on every field that changes the tensors, since a false hit conditions a render on the previous prompt — rather than the 11.37 GB encoder, which is the trade `Ltx2RuntimeSession` makes for Gemma. Retaining the ENCODER across a sequence was built, measured, and removed: the load is 15.3 s cold but ~5 s once the file is page-cached, against a ~90 s stage, and holding it costs 11.37 GB of host RAM for the sequence's length — 5% of a stage is not worth that much headroom on the axis video renders are already tight on. `MOLD_KEEP_TE_RAM=1` remains the opt-in; a quantized encoder (Q8 GGUF, 3.2 s on GPU) is the better lever. Do not re-add chain-scoped encoder retention without a measurement that beats those numbers. The charge that makes that default safe is `device::wan_step_cache_bytes`, and it is added in `wan_calibrated_activation_bytes_for` AFTER the fitted slope, beside `cfg` and `workspace` — never inside `wan_activation_budget_bytes_for`. The slope is a measured multiplier on the tensors a block materializes; the cache's buffers are an exact, nameable allocation like the attention score tile, and folding them into the derived sum inflates them 2.14x (math) or 2.92x (flash). That error is silent: the calibration test prices `wan22-t2v-a14b:q5`, a distilled 4-step tier whose cache is refused, so the charge is zero there and nothing fails — the render just parks too many blocks and gives back the 1.85x. The charge also delegates engagement to `WanStepCachePolicy::resolve` rather than re-deriving `steps >= 12 && !distilled`, so the estimate cannot price a cache the engine refuses.
- **Wan's synchronous block offload is not the bottleneck it looks like, and the VAE decode is compute-bound.** Both were measured on an RTX 4090 (`wan22-t2v-a14b:q5`, 832x480) rather than argued. Parking is CHEAP at the counts the backend-aware estimate now produces: 81 frames with 15 of 40 blocks parked renders in 111.5 s at a 22,403 MiB peak, while the same shape with `MOLD_WAN_OFFLOAD_BLOCKS=0` takes 116.5 s at 23,139 MiB — parking is *faster*, so pinned host memory and a copy stream would buy nothing here. The documented 3-5x streaming penalty belongs to the park-EVERYTHING mode, which is exactly what the score-matrix over-charge used to force. If a shape starts parking all 40 blocks again, revisit; until then do not build async offload. The decode is 23.4 s of a 111.5 s 81-frame render (21%) and is COMPUTE-bound: batching the per-frame 2-D stages into one launch and widening the decode chunk were both built and measured, neither moved the number, and the wider chunk added an OOM — so the remaining lever is a better conv kernel (candle hardcodes `USE_IM2COL_CONV2D = true` in `cuda_backend/mod.rs` and has an unused `cudnn` feature), which is fork work, not engine work. In-render expert loads are ~10 s of that same render (9%), and retaining the transformer to avoid them would hold ~10.8 GB resident across the VAE decode — the same trade the encoder-retention experiment already failed.
