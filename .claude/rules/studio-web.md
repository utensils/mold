# Cross-surface Studio / web / desktop / iPhone UI invariants

Moved verbatim from the root CLAUDE.md; loaded only when working under the paths above.

**Model metadata presentation invariant:** Web, desktop, and iPhone Installed/Discover cards, table rows, and details use the shared model-kind labels. Mature catalog entries always carry the textual `18+ NSFW` danger badge (never color alone). Details use kind-aware weight labels and show description, tags, source, license, format, and popularity only when supplied; installed Civitai sidecars retain those fields, while missing metadata stays omitted rather than guessed. **A fixed control explains itself with the profile's own sentence, never client copy:** `IntegerControl.note` / `FloatControl.note` are additive, authored at the one place `generation_profile.rs` decides the fixedness (H3's guidance is pinned at 0 by a pipeline with no classifier-free branch; a Turbo tier's steps are its distilled schedule's terminal-inclusive grid points; a distilled FLUX/LTX recipe keeps the old CFG sentence formatted from the value it actually pinned), and web/desktop/iPhone render `controlNote(control)` from `studio/lib/generationProfile.ts` verbatim under the field — a fixed control with no note renders NOTHING, which is exactly what an older server's response deserializes to. Preset `tier` is data, not decoration: every shipped profile authors `recommended`, which `studio/lib/outputShape.ts` hides, so nothing may override it to put a mark on every size pill (`h3_private_bridge.rs`'s "Reviewed" did, and named a qualification that is not a property of the pixels).

**Native prepared-expansion invariant:** Desktop and iPhone Batch 1 keep quick Expand/undo but freeze one concrete route through the next Generate/Develop and become stale if prompt/model/family/host inputs change. Stale quick work must present explicit recovery: re-expand starts from the original prompt on the current route, generate-anyway drops only the frozen authority and submits the visible rewrite on the current route, and restore returns the original without queueing; never leave an enabled Generate control as a text-only dead end. Desktop Generate with Batch N greater than 1, matching web, submits N ordinary siblings from the visible prompt; only the explicit Prepare N variations action expands. Explicit desktop/web preparation and iPhone Batch N preparation must resolve once, request exactly N non-empty prompts from that target, preserve the reviewed set across upstream changes as specifically named stale work, and submit one edited prompt per sibling through the stored route with the source prompt as provenance. Prepared siblings carry additive `batch_id`, one-based `batch_index`, and `batch_count` through requests, long-video chains, complete events, saved metadata, and the Library. Never silently resize, reroute, fall back, or erase prepared work. Missing-model pulls and pull-resume use the same host and retain the ordered prompt list. Desktop Generate uses `useDownloadsStore`; iPhone Generate and Catalog share `useMobileDownloadsStore` without importing desktop-primary state. Both authorities associate the returned job ID with the frozen host/model, retain compatible pre-ID snapshot behavior, and keep Connecting, Starting, Queued, Pulling, Ready, failed, and cancelled recovery inline for Batch 1 and prepared Batch N. The iPhone route additionally snapshots its selected remote host ID, URL, Keychain-supplied key, and server instance ID in one immutable recovery record. Each pull attempt temporarily leases that exact route, joins a compatible Catalog POST already in Starting, and releases on success, failure, cancellation, staleness, supersession, or abort so Retry must reacquire it; edits/removals supersede pending replacement ownership. Unique component consumer IDs plus unmount invalidation prevent dead views from queueing or tearing down remounted work. Partial prepared failures must name the one-based variation and reviewed prompt, compose any unconfirmed-cancellation caveat, and preserve successful prints. Every generation-facing label resolves catalog IDs through the current inventory for display while retaining the raw ID for requests, matching, and persistence.

**Conditioning-aware expansion invariant:** `ExpandTask` is the cross-surface semantic contract. Derive it from the concrete generation request with the shared Rust or browser helper; do not infer it independently inside a view. T2V is chronological, I2V/V2V preserve source authority, retake and keyframes preserve their boundaries, and audio-driven video follows the source audio. Prepared and quick expansion snapshots include the task so a conditioning change is named as stale work. `/api/expand` receives the task but never source image, video, keyframe, or audio bytes. Clients that omit the additive field retain family-based image/T2V behavior.

**Identity-photo invariant:** face-identity conditioning (PuLID) is one browser-side policy, `studio/lib/identityConditioning.ts`, and web/desktop render the shared `studio/components/IdentityPhotoWell.vue` — never a per-surface rule. The gate is the server's own authority: the resolved recipe's `capabilities.supports_identity` first, the additive `/api/models[].supports_identity` as the picker fallback, absence reading as NO (the client-side legacy recipe adapter never answers, because its `false` is this client talking). An unqualified checkpoint or an older host renders NOTHING rather than a disabled control, and it also refuses NOTHING: visibility and validation are gated on the SAME positive capability, so a staged photo simply parks — retained in form state, absent from the wire, Generate still enabled, and the well reappears with the photo when a qualified model is selected again. That is the LTX-2 staged-media precedent, and blocking there would refuse a print the server would happily render. On a qualified checkpoint the helper mirrors admission and invents nothing: never with a LoRA or an img2img `source_image`, no knob without a photo, PNG/JPEG within the 16 MiB / 8192 px / 32 MP bounds read by an identity-specific header walk that mirrors `mold_core::identity::header_dimensions` across the WHOLE payload (`imageDimensionsFromBase64`'s 1 MiB prefix is right for a source image and wrong here — a camera JPEG's start-of-frame can sit past it) — and those refusals are INLINE beside the control, never a toast, with Generate blocked. The photo is a face reference, not a composition input: it is never fitted, cropped, or resized to the canvas (that rule is about canvas fitting — the H3 Ref2VA reference CROP below is a user's composition choice and is a different thing). `id_weight` / `id_start_step` stay absent until touched so the server's defaults remain authoritative, and they count toward the Advanced badge while the well — primary form, beside the source wells — does not. Saved metadata carries the name, digest, and effective values only; Reuse settings restores the knobs and re-attaches the photo from the same content-addressed local stash `source_image_sha256` uses, disclosing inline when the device no longer holds it. A request may carry SEVERAL references of one person: `id_images` is the plural shape of `id_image` and supplying both is a hard validation error, never a precedence rule, because with averaging a silently dropped photograph changes the face that renders with nothing visible to the caller. The set is bounded by `ID_IMAGES_MAX` (4 — a latency budget, since extractions serialize), plus whole-set encoded-byte and decoded-pixel caps that sit deliberately BELOW the per-image limits times the count. Averaging is `cubiq/PuLID_ComfyUI`'s, and it is POST-IDFormer: each photograph runs the whole detector → ArcFace → EVA02-CLIP → IDFormer pipeline and the final `[1, 32, 2048]` token sets are meaned (`pulid.py:406,415-419`). Averaging the raw ArcFace vectors or the EVA hidden states first is a different, untrained composition and is never done — `ToTheBeginning/PuLID` handles only one image (`pulid/pipeline_flux.py:120-194`), so ComfyUI is the reference for the multi case. The mean is order-independent but the provenance is not: the frozen fingerprint hashes the source digests in request order. A photograph with no detectable face refuses the whole request and names its one-based position. Saved metadata carries the plural names/digests ONLY for the plural form, so a single-photograph print's metadata stays byte-identical to a pre-`id_images` build's. Both `id_images` and true CFG (below) are CAPABILITY-GATED, because an older server DROPS an unknown field rather than rejecting it: `id_images` alone renders with no face in it and `true_cfg` alone renders the distilled path at a guidance value chosen for a branch that never ran. `GET /api/capabilities` → `identity` (`{ multi_photo, max_photos, true_cfg }`, built by `IdentityCapabilities::advertised()` from `mold_core::identity`'s own constants so it can never advertise a bound the validator does not enforce) is the authority, and ABSENCE READS AS NO — the whole block is `#[serde(default)]` all-false, which is exactly what an older server's response deserializes to. A client that needs either shape probes first and refuses by name; the singular `id_image` predates the block and pays no round trip. Only a genuine transport failure — `MoldClient::is_connection_error`, the same authority the local fallback already uses — falls through unrefused, because the ordinary remote attempt fails the same way and falls back to local inference. A REACHABLE server that answers 404 or garbage is read as all-false and refused, since that is precisely how an older server answers before accepting the request and dropping the fields. Multi-photo and true CFG are core, server, and CLI only so far (#1226) on every surface, web/desktop included; the single-photograph shape above is unaffected.

**Expansion-routing invariant:** prompt expansion follows the GENERATION route, but the generation router is model-aware about the checkpoint and knows nothing about the expansion LLM — so `studio/lib/expansionRouting.ts` is the one policy every surface calls. `resolveExpansionRoute(policy, generationRoute, candidates, rank)` keeps the generation route unless that host's `/api/capabilities.expand.model_present` is positively `false`, and only then re-ranks the eligible machines whose `model_present === true` — every ready machine under Auto/Most capable, ONLY the pinned machine when one is pinned. Unknown is never missing: an unread capability snapshot (absent or `null`) keeps the route it already earned and never qualifies a host as a reroute target. The ranking is handed in (desktop/web `pickAutoHost` / `pickMostCapableHost`) so this never becomes a second router, and Remix follows the same route because `/api/remix` runs on the same expander. The generation route is captured BEFORE the request on every surface — an Auto rerank mid-flight must never move the print's machine out from under the reviewed set. The print never follows the rewrite: desktop's prepared/quick snapshots keep the generation route in `route` and record a diverging expansion host in the additive `expansionRoute`, and the existing route-changed staleness rules are unchanged. When no eligible machine has the expander, the pull offer takes its host from `planModelInstall` — fed from the EXPAND capability, never `/api/models`, because the expander is not a generation model — and DEFAULTS to the generation route's host so prepared work still freezes one route; the machine picker is mounted by Models, so Create names its choice instead of opening it. `/api/capabilities.expand.model` names the manifest model (`qwen3-expand`) so clients stop hard-coding it — `expandModelId` falls back for older servers. iPhone pins exactly one machine, so its decision is always the generation route until mobile Auto/capable routing hands a real candidate list to the same helper. `ExpandTask` derivation is untouched, and `/api/expand` still never receives media bytes.

**Identity-photo staleness invariant:** a changed identity photo is a conditioning-media change. `studio/lib/promptTransform.ts`'s `conditioningFingerprint` reads `id_image` alongside `source_image`, the video/audio sources, keyframes, and H3 references, so reviewed prompt work (remix on iPhone; remix, prepared, and quick expansion on desktop and web) stales on a face swap exactly as on a source-image swap — there is deliberately no second, identity-only staleness rule. `ExpandTask` is untouched (a face reference does not make a text-to-image print an img2img one) and `/api/expand` still never receives media bytes. Mobile's plain (non-remix) prepared batches carry no conditioning fingerprint at all today — identity got exactly the same treatment as source images; close that gap for all conditioning media at once, never for identity alone.

**Command-palette model-search invariant:** the ⌘K palette on web and desktop searches the whole fleet, and every model row's wording and destination derives from `planModelInstall` plus `studio/lib/modelSearch.ts` — never a second policy. Installed rows are the union across ready machines (web's additive `HostRouting.installedModels`, desktop's `models.installed` merged with `hostModels.unionInstalled`), so a model is never hidden because the pinned target lacks it. `resolveModelHost` repins the generation target ONLY for an explicitly pinned target that lacks the model; automatic routing (web `auto`/`capable`, desktop `null`/`capable`) is already model-aware and must stay untouched. Not-installed rows come from a debounced live catalog search restricted to checkpoints, drop unsupported entries and anything the fleet already has (matched on both catalog id and server-reported name), stay appended in the server's relevance order behind the panel's `busy` indicator, and discard responses for abandoned queries via a monotonic epoch. Palette installs deliberately take the plan's first target and name it in the toast instead of opening the machine picker — that dialog is mounted by the Models page and would be invisible from any other route. Load/unload rows stay scoped to the primary; they act on this machine's GPU, not on whichever machine holds the weights.

**Model install-target invariant:** a Models row is merged across machines, so `installed` means "installed somewhere" and never "installed here". Web, desktop, and iPhone derive the row's action from `planModelInstall` in `studio/lib/modelInstallTargets.ts`: every reachable machine that lacks the model stays an install target, owners degrade to repair, and the action collapses to Repair only once every reachable machine has it. Never hide the install because some other machine has the model. A machine whose `/api/models` has not been read is not evidence of absence and is never offered as an install target on desktop or web; the host picker always names the per-machine outcome so a mixed fleet is unambiguous. Both download routes are strict about id shape — `/api/downloads` takes manifest names and `/api/catalog/:id/download` takes `cv:`/`hf:` ids, each rejecting the other — so every install path must route on the id, not on the calling surface.

**Missing-model routing invariant:** Auto / Most capable must never dead-end on a model nobody has. `classifyMissingModel` in `studio/api/generationPlacement.ts` is the one classifier that tells an authoritative `infeasible` caused by the model's own absence (the server's "no concrete local artifacts" reason, or a missing component the requested model itself repairs) apart from a capacity refusal, a policy block, or a missing companion — only the first may be answered with a download, and every surface reads that classification rather than matching the reason string itself. Desktop's `resolveFeasible` and web's `useHostRouting` surface it per host as `missingModel`; Create then offers the pull instead of a toast, choosing the machine through `planModelInstall` (one candidate skips the picker, several open the existing `DownloadTargetDialog` / `ModelInstallTargetDialog`, which Create now mounts too), and arms the exact-host pull-and-resume — desktop's `pullResume` store, web's `usePullResume`, sharing the which-job rule in `studio/lib/pullResume.ts`. Only the machines that reported the model absent are pull targets — one that refused for capacity or policy would refuse again after the download. A resume is only ever promised for a concrete host AND a request that is already final: a source still to be fitted against the chosen machine, or a quick expansion whose provenance is stamped after routing, gets the download and an explicit "press Generate again" instead of a promise that would render different conditioning. The watch takes the server's job id whenever it reports one (`primary_job_id`, desktop's `startCatalogDownload`); otherwise it matches by model against a terminal snapshot captured BEFORE the POST, since a pull that finishes inside that window would otherwise be excluded forever. Auto's #1107 deadline must not manufacture that dead end: while no candidate has answered `planned` and a machine is still checking, it extends once (`AUTO_PLACEMENT_EXTENSION_MS`) instead of synthesising "did not answer" and collapsing a homogeneous infeasible answer into `mixed`. A restored print whose model no machine has keeps the raw id in the form and the request — desktop's `ModelPicker` renders it as the selected entry with a **Not installed** tag, web's `CreateModelPicker` as a disabled `… · not installed` option, iPhone keeps its own indicator — with a one-line disclosure on drop/Reuse; web must never silently substitute `installedModels[0]` (and that model's size/steps/guidance/LoRAs) for a model the user restored, though a genuinely unset model is still re-homed so the `<select>` is never blank.

The frontend is one private repo-root Bun workspace with exact dependencies and one `bun.lock` / generated `bun.nix`. `ui/` owns visual tokens and low-level Vue primitives; browser-safe `studio/` owns explicit-target HTTP contracts, platform adapters, Pinia state, and shared domain logic; `web/` and `desktop/` are surface shells. Install at the repo root and use `bun run build:web`, `bun run build:desktop`, or `bun run build:mobile`; `frontend-bun-lock` refreshes both root dependency artifacts. `studio/` must never import Tauri or either application shell, and native compatibility normalization remains in `desktop/`.

The SPA in `web/` uses Vue 3, Pinia, Vite 7, and Tailwind v4. It is embedded into the `mold` binary at compile time via `rust-embed`. `crates/mold-server/build.rs` resolves the bundle from `$MOLD_WEB_DIST` → `web/dist` → a placeholder stub (detected at runtime and swapped for an inline page). The devshell `build`/`serve`/`generate` commands run `./scripts/ensure-web-dist.sh` first, so dev builds ship the real SPA. `MOLD_WEB_DIR` still overrides the embedded bundle at runtime for hot iteration.

The web IA uses Create (`/create`, also the `/` default), Library (`/library`), Models (`/models`), Machines (`/machines` + `/machines/:id`), and Settings (`/settings`). Library's grid toolbar carries the shared persisted Lightroom-style thumbnail-size slider at tablet width and above. **Web Library organization (V3 "Shelf"):** the Library header is a **Prints | Collections | Trash** scope `SegmentedControl` synced to `?scope=` (+ `?c=<slug>`, `?tag=a,b`, `?fav=1`); Prints keeps the grid plus a filter-chip row (♥ Favorites · tag chips · host chips), Collections is a shelf of cover-mosaic cards merged across hosts by slug with a breadcrumb drill-in and an Edit menu, Trash is the same grid with the `trashRetentionSummary` banner, per-tile purge countdown, Restore / Delete forever, and header Empty trash. Every edit lives in the Lightbox aside (`PrintOrganizer`: editable title → PATCH, ♥, tag editor, In-collections checklist) and the bulk bar (Add to collection · Tag · ♥ Favorite · Trash); mutations fan out to every physical copy through `web/src/lib/libraryOrganization.ts` over the studio explicit-target helpers, and the representative logical print carries the union (`mergeLogicalEntries`). Capability-gated per host: a host without `capabilities.gallery.organize` / `gallery.trash` contributes no organization, hides the scope control when none does, and keeps the hard-delete wording. Destructive copy is plain everywhere — `requestConfirm` with `danger`, NEVER `typedPhrase` (the delete-all-filtered flow dropped its typed phrase too); single and selected Trash stay optimistic with the 6 s `undoableAction` undo. Create's title field (`GenerateFormState.title`) rides every one-shot / batch / prepared request as `title`, and a sequence sends it on the chain body for the stitched print. The capability-gated **File under** group sits in the Create controls region (the controls sheet on phones) and binds the shared `@studio/lib/fileUnder` contract through `useFileUnder`: the removable `{slug} · from title` ghost chip, tag suggestions with fleet-wide counts, and a collection row that pre-selects — never creates — the slug-matched collection plus an inline **New collection…**. It files one-shots, batch siblings, prepared variations, and the stitched sequence print, is restored by Reuse settings, and hides on a host without `capabilities.gallery.organize`; **Tag new prints with their title** persists per browser at `mold.create.autoTagTitle.v1`, and Save / Download suggest `{title-slug}__{model}__s{seed}.{ext}` while the gallery file is never renamed. Trash retention is `gallery.trash_retention_days` edited in Settings ▸ Library (origin) and the Machines host-detail Library card (per host, with Empty trash). Retired `/generate` and `/catalog` paths and all unmatched URLs render Page Not Found. Web accepts only the current storage and server wire shapes; an incompatible remote surfaces an actionable upgrade error. Create model selectors render catalog-provided descriptions for `cv:` / `hf:` entries but preserve those stable ids as form and request values; desktop follows the same rule. Sub-640px swaps the nav pills for a hamburger + bottom nav sheet. The shell owns a ⌘K palette, a downloads center, app-frame toasts/dialogs (never `window.alert/confirm/prompt`), and a notifications bell (web nav + desktop title bar) whose session history of every toast — full untruncated error bodies included — derives from the shared `studio/stores/notifications.ts` store; toasts stay transient, the bell is the durable record, and iPhone deliberately keeps persistent inline banners instead. Severity is one policy: `ui/lib/notificationSeverity.ts` owns the single glyph/label/color table (`@ui` is the lowest layer, so the bell and both toast shelves can read it) and `studio/lib/notificationTone.ts` adds the bell's badge fills. Green covers everything that is not a warning or an error — an ordinary notice and a success both read `--success`, separated by glyph, never by hue — while warnings take `--warning` and errors `--stop`. Every surface also names the severity in assistive text and gives it a distinct glyph rather than relying on color alone, warnings share the error's assertive live region (`severityIsUrgent`) because the only one that exists is the sticky host-drop, and the bell badge takes the worst unread entry's tone (an opaque `badge` fill plus the per-theme `--on-status` ink, never a translucent hint ink). Each bell row carries a Copy control backed by `studio/lib/notificationClipboard.ts` — the shells disable chrome text selection, so that button is the only way a long error body leaves the app; it degrades from `navigator.clipboard` (absent on plain-http LAN origins) to the textarea path and reports failure instead of claiming success. Host reachability derives from `reconcileHostConnectivity` in `studio/lib/hostConnectivity.ts` on both web and desktop: every listed host keeps being polled, so a drop is a WARNING that says it is retrying (sticky, once per edge), a recovery withdraws that toast and confirms in green, `"connecting"` is a probe whose settled predecessor is carried forward rather than counted as evidence, a warned host that is disconnected or forgotten has its notice retired with the entry, and the Machines card marks an unreachable machine `reconnecting…`. A recovery is announced ONLY for a host that was actually warned about — desktop's boot probe is deliberately quiet, so a machine asleep at launch must not produce a green "Reconnected to" for a drop nobody was told about. The one deliberate per-surface difference is `warnOnFirstContact`: web warns when a registered machine fails its very first probe, desktop stays quiet because its Machines workspace already shows that row as errored. Per-surface Advanced policy (spec §06 surface split): web at ≥ tablet width is the power surface — Advanced renders inline in the Create controls region as always-open icon-led groups (count badge + Reset kept); mobile web keeps the same groups in its sheet; desktop keeps the simplified inspector by default and reveals those groups inline only when its Advanced toggle is on. Web Machines is browser-side multi-host: a localStorage host registry (`mold.web.hosts.v1`, origin always primary, instance-UUID dedupe) with per-host `x-api-key` headers — keys never in URLs. Its Local network flow is server-assisted: only when the primary reports `discovery.can_browse` does the browser request `GET /api/discovery/peers`, filter remembered instance UUIDs, then test-connect directly to the peer before saving; older servers are never probed. The results reflect the primary server's LAN and do not proxy traffic. The theme (`{ theme: ThemeId, matchSystem }`; a legacy `{ family, theme }` record migrates through the shared table, and fresh visitors start on Safelight) persists at `mold.web.theme.v1` and applies before first paint via the inline `index.html` script. Web Settings stores Hugging Face and Civitai credentials on the serving host in owner-only `$MOLD_HOME/catalog-credentials.json`; the browser receives masked status only. Saved credentials override `HF_TOKEN` / `CIVITAI_TOKEN` defaults, and clearing a saved value returns to the environment fallback.

Sequence mode on web, desktop, and iPhone filters the picker to chain-capable installed video models and auto-selects one when available; its browse action deep-links into Discover with Video + Models filters. Explicit sequences start as two required clips, use the shared Smooth / Cut / Fade user-facing labels (`ui/lib/seam.ts`) for context-capable LTX-2, and label LTX-Video's zero-motion-tail fallback Join. Clip-duration choices must remain strictly greater than the active motion tail and never exceed `sequenceClipFrameCap` (the model's own clip size — see the LTX-2 frame-ceiling entry). The optional **Opening image** (with its source strength and fit-to-frame controls) is a PRIMARY-form well on all three surfaces — desktop `SequenceOpeningImageWell` in the inspector's source-media slot, web `SequenceOpeningImagePanel` beside `SourceMediaPanel`, iPhone a `mobile-sequence-source-disclosure` in the Create stack — never an Advanced section: the primary ↺ Reset clears it exactly as the one-shot wholesale reset discards source media, the Advanced reset and its active-count badge ignore it, and a checkpoint whose `source_image` contract is `unsupported` hides it. Desktop and web clip rails carry right-click menus built by the one pure builder in `studio/lib/sequenceContextMenu.ts` (`clipContextEntries` / `railContextEntries`; desktop feeds them to `useContextMenuStore`, web renders `SequenceContextMenu.vue`) — text fields keep their native menu, a seam's right-click still opens the seam editor, and `duplicateClip` / `insertClip` on the draft store are the only new mutations (a duplicate never shares its source-image `draftId`). **Validate plan** on all three Studio surfaces calls the selected authenticated host's read-only `POST /api/generate/chain/validate`, renders normalized stages/warnings/optional VRAM, creates no job, and discards a response if the draft changes in flight. Durable sequence creation, authenticated events or polling, previews, and job actions must stay on the selected host; iPhone persistence records host identity and job ID while the API key remains Keychain-only, and a saved instance identity must match exactly before recovery reattaches. Every LTX-2 pipeline renders sequence clips, two-stage included, and `/api/models[].supports_sequence` advertises that per model so pickers stop inferring it from the checkpoint name; `POST /api/generate/chain/validate` returns an advisory `vram_estimate` that is the max over stages, never their sum, and must never gate submission. Chain/job/action plus catalog-download failures remain visible in the interface.

**Activity-is-present-tense invariant (spec G15):** the Create activity strip renders only in-flight prints and sequences, plus at most `MAX_ATTENTION_ROWS` (2) dismissible failed/interrupted rows that expire after `SETTLED_VISIBLE_MS` (5 min) measured against server truth (`updated_at_unix_ms` for sequences, a client settle stamp for prints), plus one digest chip counting the settled sequences it is not listing, deep-linking to `/library?panel=history&tab=sequences`. Never render completed or cancelled rows there, never persist the dismissal set (the age rule already survives restart), and keep dismiss client-side — `Clear inactive` is a server `DELETE` and the two must not converge. `Clear inactive` and `Clean up disk` live only in the History ▸ Sequences footer, host-scoped and behind a confirm that names the host and count. The settled sequence resolves to three homes: the canvas (with **Edit sequence** / **Show in library** — settling must never blank it), the print in the Library, and the job in Library ▸ History ▸ Sequences (`HISTORY_JOBS_RENDER_CAP` 200, fetched on open because chain polling stops when nothing is active). The sidebar's **Now developing** shows running sequences with their clip counter but never settled ones. All of this derives from `partitionActivity` / `activityDigestLabel` in `studio/lib/activity.ts`; `ActivityJobVM.createdAtMs` must stay a real wall clock (it was a `clientId` counter, which sank every print below every sequence). History ▸ Sequences is deliberately out of scope on iPhone.

**Queue-selection reuse invariant:** selecting an in-flight print on web, desktop, or phone must restore its complete saved metadata through the same per-surface mapper used by Library **Reuse settings**, never a queue-only subset. A selected running print also owns the Create canvas: clients poll its authenticated `GET /api/queue/:id/preview` snapshot and show the latest denoise image and step count where that model emits previews, without putting credentials in URLs or adding preview payloads to the queue listing.

**Queue-vocabulary invariant:** every waiting row on web, desktop, and iPhone resolves through `resolveQueueWait` in `studio/lib/queuePosition.ts` — running shows step progress, position 0 is **Next up**, everyone behind counts **#N in line**, and absent evidence degrades to a plain **Queued**. Only an ACTIONABLE `QueueBlockedReason` overrides the position with its own copy; `no_schedulable_device`, `no_idle_device`, `lower_priority_opening`, `warm_wait`, and `dependency_wait` are ordinary serialization on a busy host (`mold-scheduler/src/planner.rs`) and must fall through, which is also the predicate the device panel's Blocked list filters on. A reason this build does not know reads "Waiting on the host" — never a raw underscored identifier, and never nothing. Surfaces choose casing only: `queueWaitLabel` (sentence) or `queueWaitCode` (the iPhone/Machines compact uppercase). Queued work is never counted as active — `activityCountLabel` / `activityAnnouncement` split running from waiting.

**Output-shape invariant:** Create's Shape/Size controls on web, desktop, and iPhone render ONE `resolveOutputShape` result from `studio/lib/outputShape.ts` — chips, size pills, badge, status sentence, and the header chip all read that object, so they cannot disagree. The server `generation_profile` stays the only data authority (alignment, ceilings, authored presets and their `tier`); the resolver owns presentation. Shape chips are the canonical families `{1:1, 5:4, 4:3, 3:2, 16:9, 21:9}` × orientation, assigned by log-ratio distance within `FAMILY_LOG_TOLERANCE` (0.06) — LTX-2's 19:11/30:17/20:11, Wan's 26:15, and H3's 7:4 are all 16:9 — plus **Source** while an image is attached; a preset outside every tolerance keeps its own reduced label so nothing is hidden. A family chip never invents pixels: it picks from that family's authored ladder, whose pills are labelled `1216×704` with megapixels and a data-derived mark (`Default` = the recipe default), never a list position (the old `Small/Standard/Native` and mobile `Recommended/…/Max` vocabularies are gone) — which is how #998's "a 16:9 click must not silently land on 19:11" is satisfied. Requests still carry raw `width`/`height`. The canvas's authority is the explicit `CanvasIntent` (`source` | `source-exact` | `model-default` | `manual`) each surface holds beside the form and passes down, NOT a comparison against the last computed size: selecting a model runs `applyModelDefaults` before any source watcher, so `resolveSourceCanvasTransition` reads only the intent (#1166 bug 1 — a source-following canvas re-resolves on every model/pipeline change; a manual one never moves). The badge is `state`, derived positionally from whether the canvas IS source-derived, so `Source` can never sit beside a canvas the source did not produce (#1166 bug 2); mobile's `Manual` is the shared vocabulary.

**Sequence-reuse invariant (spec §06):** a print stitched from a sequence is identified by saved provenance (`metadata.chain`, plus `metadata.chain_job_id` when a durable job produced it) and everything derives from `studio/lib/sequenceReuse.ts` — never a second clip loader. **Reuse settings** is one sequence-aware button: a legacy/still print keeps today's One shot restore, a sequence print loads `planSequenceReuse`'s clips into the shared draft as a NEW draft (no `editing` session) on `/create?output=sequence`, and it must never surface `metadata.prompt`, which for a sequence is every clip newline-joined. Per-clip seeds are never applied (the wire carries a `seed_offset`; deriving one from an effective u64 is guesswork), the recorded negative lands on clip 1 only, and `chain.motion_tail_frames` is validation-only — clips are always re-clamped with `clampClipsToMotionTail` against the LIVE model's tail, and any raise is disclosed, never silent. **Edit sequence** is the second, distinct action: desktop and web only, gated by `sequenceEditAvailability` on positive knowledge only (hide it when the origin host's loaded listing lacks the id; show it when the listing is unloaded), resolved ONLY from the entry's own origin bucket — never a sibling in `availableOn`, which holds auto-saved copies. It is checked once on click; `404` falls back to reuse with a toast naming the host, an unreachable host errors and changes nothing (a silent downgrade would discard cached clips), and `200` hands into the EXISTING `editSequence` path (`normalizeServerChainScript` → `chainScriptToClips` → `draft.loadFromJob`). iPhone is reuse-only until it has a chain-detail recovery route, and its model substitution must pick a sequence-capable model.

**Gallery delete is always enabled.** `DELETE /api/gallery/image/:filename` is a destructive endpoint — pair with `MOLD_API_KEY` when the server is exposed beyond localhost. `GET /api/capabilities` still returns `{ gallery: { can_delete: true } }` so older clients keep a stable shape.

**Hidden collections invariant:** A collection's additive `hidden` flag fans out to every host copy. Hidden collections stay visible and openable in Collections, but their member prints are excluded from the default Prints grid and every text-search result on web, desktop, iPhone, and Android; collection drill-in always reveals them.

**Reference-images invariant:** the attachment UI is driven by the recipe's `capabilities.reference_images` block and nothing else. `studio/lib/generationCapabilities.ts` derives `referenceImages` from the profile first and falls back to `legacyReferenceImages(family, model)` ONLY when the block is absent (an older server), exactly as `supportsStrength` falls back; `sourceImageMode` reads it — `primary_is_target` → `qwen-edit`, `source_relation: replaces` → `references`, `exclusive` → `single-or-references` — and `sourceMediaPlan` takes `max`, `required`, and `primary` from it. No surface may keep an `isFlux2DevModel` / `FLUX2_DEV_MAX_ATTACHMENTS` style constant. A `single-or-references` plan (FLUX.2 [klein]) renders BOTH the existing Source well and the existing attachments strip; `resolveExclusiveWells` in `studio/lib/sourceMediaPlan.ts` is last-write-wins — the well written last is active, the other is PARKED with its media kept and restorable, an inline note explains why, Generate stays enabled, and strength/mask render only while Source is active. `toRequest` emits `source_image` (+`strength`, +`mask_image`) OR `edit_images`, never both. Reuse settings restores whichever well the print used; `conditioningFingerprint` reads `edit_images`, so a reference swap stales prepared work like a source swap.

**Drop-routing invariant:** `studio/lib/imageDropRouting.ts`'s `resolveDropTarget(plan, hovered, state)` is the ONE policy for where a dropped image lands. Every well and strip renders its `DropTarget` as `data-drop-target` through `ImageDropWell`'s prop; the hovered target wins when the plan renders it, otherwise the plan's default (`single` → source; `attachments` → APPEND to the strip; `single-or-references` → the well that already holds media, else source; H3 → first frame then last; H3 references → the ordered list). A full strip or a model with no image input is refused by name, never silently. Strips are appended to, never replaced. Desktop's Tauri bridge (`GenerateView.vue` `onDragDropEvent`, the only path an OS file drag reaches because HTML5 `drop` never fires under Tauri's default `dragDropEnabled`) resolves the hovered target from the event position and writes through `desktop/src/lib/desktopImageDrop.ts`'s `applyDropToForm`, the same fields the wells' pickers write — including `h3Authoring.*`, identity, opening image, and end frame, which used to be unreachable by drag. Web's window-level listener in `CreatePage.vue` prevents the browser's navigate-away and routes only drops no well already handled (`event.defaultPrevented`), through `web/src/lib/createImageDrop.ts`. iPhone/Android keep the touch picker sheet; no OS drag exists there.
