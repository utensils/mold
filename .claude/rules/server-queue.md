# Scheduler, durable queue, admission, metadata DB (mold-server, mold-scheduler, mold-db)

Moved verbatim from the root CLAUDE.md; loaded only when working under the paths above.

- **Placement preview is an authority boundary** — `POST /api/generate/placement-preview` is read-only and authoritative only for ordinary-generation plans the server can admit. Prepared clients preview the finalized sibling shape after source preprocessing and fence URL, API key, and instance identity. An authoritative `infeasible` response may carry additive `missing_components`; a `planned` response may carry additive `pending_downloads` for known encoder dependencies that admission will materialize. Pending previews use a distinct registry-identity fingerprint domain, never start downloads, report low estimate confidence only when a device selected by that candidate plan has pending artifacts, and are recomputed from landed bytes at admission. Cold installed `cv:`/`hf:` IDs resolve only from contained local sidecars; the synthesized model config travels with prepared work through coordinator planning and pre-CUDA validation so config refreshes cannot erase its authority. Clients still queue nothing on infeasible and must not promise repair/resume without exact-host grouped download ownership. A strictly valid version-1 non-authoritative `unsupported` response or legacy `404`/`405` may retain compatible routing; every other HTTP, malformed response, or exhausted transient retry queues nothing. Chain and local prompt-expansion/post-generation-upscale utility previews remain non-authoritative `unsupported` until their real CPU/GPU paths are modeled. Probes redact prompts/media but retain server-local LoRA paths needed for feasibility.
- **Frozen execution plans remain authoritative at worker dispatch.** Scheduler admission owns the family-specific estimate, placement, load strategy, offload mode, and safety policy. A worker may re-sample physical memory and reject the exact `predicted_vram_peak_bytes` if pressure changed, but it must not replace that demand with the legacy path-based resident-model estimator. Apply the recheck to fresh loads, parked reloads, and reconstructed engines; unchanged CUDA hot-cache hits may recheck only when fresh, nonzero Mold-process VRAM attribution can bound the global, potentially stale cache delta. Ambiguous zero/missing CUDA attribution in containers, MIG, or WSL2 retains the scheduler's validated grant rather than double-counting resident weights. CUDA rechecks again after dropping replaced state. Metal rechecks its shared working-set policy on hot-cache hits and after dropping replaced state and sweeping the allocator pool; it credits only bounded, observed cached allocations before release and no released weights afterward. Missing Metal policy or allocation observations fail closed. The same discipline covers host RAM (#1099): a host reservation stays charged in the `HostMemoryLedger` until its lease settles (an OS sample can never prove a not-yet-made allocation is reflected), the worker rechecks the exact frozen `admission_host_demand_bytes` against headroom from the granting ledger — never an independent floor computation — before any fresh load, and missing ledger evidence (legacy dispatch, chain stages) retains the grant. A host rejection is an ordinary insufficient-memory error and must never route through the fatal-CUDA quarantine. Metal reserves no host RAM at all: its host claim rides the unified device gate, and admission and placement preview must move together on that rule.
- **Metal admission spends one pool on every server path (#1059).** Generation, chain-stage, placement-preview, and read-only observation candidates use `ResolvedExecutionPlan::admission_vram_demand_bytes()` (phase maximum plus concurrent host demand) and the backend-aware host accessor. Raw predictions remain immutable worker inputs, never reservation identity: chain stages and generations recover the exact device/fingerprint contract separately from the scheduling envelope. A chain whose unified demand exceeds its admitted capacity raises the typed device shortfall before candidate publication, so it reaches the same reclaim and bounded-settlement path as a resolver refusal. On macOS, `resources::ram_snapshot_from_system` reads `device::available_system_memory_bytes` (free + inactive); the resource aggregator derives Metal telemetry and its `metal_memory` policy from that same RAM sample. Admission reads the policy's floor-adjusted working-set headroom, never the legacy RAM projection; missing policy or available-host observations make the device temporarily unavailable. Worker preflight takes a fresh observation through the same policy authority. CUDA retains its discrete VRAM and host pools. Generation-free tests cover accounting and transport; pressure-margin render qualification remains separately tracked in #1059.
- **A host-headroom refusal releases mold's own cache before it becomes an answer (#1289).** The LRU model cache is memory mold is holding by choice, so a generation refused for want of HOST memory — never device, which placement and the cache's own evict-to-fit path already own — asks `host_reclaim::reclaim_host_headroom` first: it evicts least-recently-used across the shared cache and every idle worker's, skipping the requested model, any leased engine (`ModelCache::reclaimable` excludes the take window by construction), and any worker the scheduler would not lease a hard-pinned releasing job — busy, quarantined, shutting down, or draining, each of which would leave a request waiting on a oneshot nobody sends (degraded is deliberately admitted, exactly as `DeviceSnapshot::accepts_releasing_work` admits it), with a bounded wait on top for the race that filter cannot close. A placement preview NEVER reclaims: `ExistingOnly` is the read-only probe automatic routing fans across the fleet, so one that evicted would flush every candidate machine's warm cache to answer a question about one print. Each eviction is awaited and handed back through #1273's `release_host_memory_after_unload` BEFORE the sample is re-taken — an OS sample can no more prove an unfinished release than an unsettled allocation — and admission is retried exactly once. A shortfall that survives that is refused with the post-eviction numbers plus what was released ("released 9.8 GB by unloading 2 idle models; still 2.9 GB short"), because the figure a user acts on must already include every byte mold could return. The decision reads a TYPE, never prose: `H3PrivateHostHeadroomShortfall` is what the two H3 gates raise, for the same reason #1272 stopped sniffing a refusal for the substring "host". H3 is the only family whose host ADMISSION refuses; every other family's host shortfall is a planner `InsufficientHostRam` _block_ that resolves when the running work returns the RAM — and when nothing is running, the coordinator asks the same module (`next_memory_reclaim` → `reclaim_host_headroom`, one at a time, oldest blocked job first, never on a busy scheduler) before `settle_unschedulable_generations` bounds the wait as a RETRYABLE hold naming the post-eviction numbers. The block is a typed `MemoryBlock` with a KIND — host, or the VRAM of the device that would run it — recorded with the numbers that were compared, logged once at WARN. The device kind is the same deadlock in the other memory (hal9000, 2026-08-27): an idle device is planned against `free + the cache's recorded footprint`, the driver attributes more to mold than that record, and a PuLID `flux-dev:q8` print (22.2 GB) sat unplanned for five minutes beside an idle `flux2-klein:q8` — no block reason, no bound, nothing running — until an unrelated print evicted it. That refusal comes from the execution-plan RESOLVER (`ExecutionPlanError::InsufficientVram` → `GenerationPlanFailure::Transient`), which drops a device before the planner ever sees it, so `BlockedReason::InsufficientVram` never appears for it; `TransientPlanFailure::vram_shortfall` carries the numbers and `record_resolver_vram_block` records the block from the settle pass. The reclaim re-samples through the device's own driver reading (`device_headroom_from_driver`), and the hold names the device. Two things make host demand honest for a warm hit (hal9000, 2026-08-27): `ResolvedExecutionPlan::predicted_warm_host_increment_bytes` charges a device that already holds the plan's engine (`GpuWorker::holds_execution_fingerprint`) only the per-request transients — a CPU-parked encoder stays resident for the engine's life (FLUX drops T5 only when `on_gpu`) and `MemAvailable` already excludes it, so charging the cold figure parked every queued `flux-dev:q8` print on 9.85 GB of headroom until the model was unloaded by hand — and `candidate_host_demand_bytes` deliberately applies no learned envelope to that warm figure, because the envelope is sampled across a whole lease and a cold load's high-water mark would re-create the double charge. **What that refusal charges is a PEAK, not a sum.** When the conditioner falls back to the host on a CUDA route (`private_h3_qwen_route`'s `HostCpuThenDrop` arm — the placement is a device fit since #1423, see `.claude/rules/minimax-h3.md`), its 15.687 GB of packed parameters are real anonymous host bytes; everything charged beside them is a transient, and two transients belonging to different moments must never be added. `h3_factory::qwen_encode_phase_host_bytes` is that rule, and it is ONE authority on purpose: the loader's staging buffers are freed before the first forward allocates an activation, so the phase peak is `parameters + max(load staging, activation + output state)`, and the opened-evidence builder, `validate_target_budget`'s re-derivation, and the freeze-time projection's staging term all read it. The staging term is ONE largest tensor, not two — while tensor k is staged twice only `params[0..k)` are resident, so the load peak is bounded by `total + size(k)`, and `2 x max` charged the staged tensor twice on top of a total that already contained it once. And FL2VA no longer charges the reviewed grant verbatim for every canvas: `qwen_activation_workspace_demand_bytes` scales the ONE observed per-row cost by the request's own text+vision rows under the same x1.15 + 64 MiB-grid policy Ref2VA uses, clamped by the grant so the reviewed shape stays byte-identical while a smaller canvas stops paying for the largest one's conditioner sequence. Steps still scale nothing — a step is time.
- **Host headroom counts evictable ZFS ARC, once, at the sampler (#1439).** Linux's `MemAvailable` excludes the ZFS ARC even though the kernel shrinker drains it inline under allocation pressure (openzfs/zfs#10255), so verifying a 37 GB H3 set through the page cache on hal9000 removed 16 GB from the sample that admits the render and held a Ref2VA print at 26.20 GB of headroom beside 15.08 GB of evictable ARC. The credit enters at ONE place — `resources::ram_snapshot()` (`zfs_arc::evictable_arc_credit` → `RamSnapshot::with_zfs_arc_credit`, the only writer, clamped so `available + credit <= total`) — and `RamSnapshot::available_with_evictable_arc()` is the one figure the scheduler ledger (`HostMemoryReading::from_ram`), `current_h3_host_memory` (`H3HostMemory::from_ram`), `host_headroom_from_system`, and the forced-local CLI spend; `available` stays `MemAvailable` everywhere (every existing pin, `system_ram.available`, `host_memory.available_bytes`) and the credit is published BESIDE it as additive `reclaimable_zfs_arc(_bytes)`, `None` off ZFS. RSS-only probes read `ram_snapshot_from_system()` and never consult arcstats. The formula is OpenZFS's own `arc_evictable_memory()` — `min(Σ mru/mfu evictable, max(size − c_min, 0))`, never `size` (pinned, dirty, anon), never `Σ evictable` alone (`c_min` is a hard floor), never `size − arc_sys_free` (a free-RAM watermark, the wrong axis) — zero while `memory_available_bytes < 0`, while `zfs_arc_pc_percent != 0`, and unless `zfs_arc_shrinker_limit` reads as exactly `0` (2.2's default of 10000 pages caps each reclaim pass at ~160 MiB, so no haircut can make a rate-limited shrinker honest; 2.3 and TrueNAS default to 0). There is deliberately no haircut beyond that: the `max(15%, 8 GiB)` floor sits on top, and the sysinfo and arcstats reads are two non-atomic samples whose transient double-count on an eviction between them is bounded by that floor. Absent arcstats is `None`, never an error; garbage is `None` plus one DEBUG line per process; `MOLD_HOST_RAM_ZFS_ARC=0` is the kill switch, read via `std::env` and deliberately NOT in `ENGINE_SHAPING_VARIABLES` because it shapes admission, not a plan's frozen identity. Every refusal prints the credit BESIDE the headroom it already contains, only when it is above zero, and always from the SAME sample that produced the headroom (`HostHeadroomReply`, the planner's internal `HostMemorySnapshot.reclaimable_zfs_arc_bytes`, `MemoryBlock`, and the H3 loop's `host_sample`) — so every pre-#1439 message test keeps its `None` twin byte-identical, and a ZFS host with a cold cache reads like any other host. `mold-inference` stays ZFS-blind: `H3PrivateHostHeadroomShortfall` is unchanged and the server appends the clause where it composes the hold.
- **A queued generation is either schedulable, running, or answered — never all three at once and never none of them.** A pending job whose execution plan does not resolve contributes zero candidates, and `classify_no_candidate` (`mold-scheduler/src/planner.rs`) then reports the untyped `NoSchedulableDevice` because it has nothing to compare against a device; `Coordinator::generation_plan_catalog` discards the real reason at `debug`. That is the right _retry_ while mold holds the resource — a lease, a preparation, or a legacy chain claim — because the running work gives it back, and the job dispatches on the first turn after it does. It is not an answer once nothing is running: #1272's H3 print logged `no_schedulable_device` three times and then nothing for the rest of a forty-minute wait. `Coordinator::settle_unschedulable_generations` is the bound: it retains the last non-terminal planning failure, accrues an idle wait ONLY while `leases`, in-flight/legacy worker claims, and non-`Ready` preparations are all empty, and after `UNSCHEDULABLE_IDLE_GRACE_MS` refuses the job with that retained text — which for a memory shortfall is `insufficient_vram_error`'s own required-vs-sampled sentence. Never bound a job waiting behind running work, and never let a non-terminal plan failure become terminal on a busy host. `Preparing` is the fourth state that rule originally failed to name, and it is now both VISIBLE and BOUNDED: a job whose own dependency preparation is in flight reports the wire reason `preparing` with `preparation_elapsed_ms` and, when the preparer publishes one, `preparation_progress` — never the `dependency_wait` every OTHER not-ready job gets — and both edges log at INFO. A memory refusal that the machine could still satisfy is a `CapacityPark` (`execution_plan.rs`) rather than a hold: `variant_dependencies::h3_capacity_park` decides on the RESOURCE — required against the hardware's own ceiling — never on which worker happened to be busy when admission sampled, because that made the outcome a race in both directions (a host shortfall on a momentarily idle fleet became a permanent hold, and a device shortfall never waited at all). The park is RETAINED on `PendingGeneration` across its own re-preparation, which is what lets `settle_unschedulable_generations` accrue against it and answer with the shortfall's own numbers; a parked job's own retry is deliberately not counted as the machine being busy, and repeat retries pay the ordinary refresh backoff so a machine that can never hold the job does not re-run admission at 1 Hz forever. The H3 arm of this is that BOTH shortfalls must be _identified_, not sniffed — `H3PrivateHostHeadroomShortfall` and `H3PrivateDeviceHeadroomShortfall` (whose `resource` names `device` or `unified-memory`, since #1214 requires a refusal to say which pool fell short) are raised by every one of the four H3 memory gates, and a host-headroom shortfall in particular: `resolve_private_h3_execution_plans` asks the host question directly before revalidating the frozen evidence, because `validate_for`'s refusal is one opaque sentence that never contains the word the old substring test looked for, so every H3 job blocked on host RAM was filed as a VRAM shortfall it did not have.
- **Owner work asks the same memory questions a generation does, and a cancellation answers none of them.** Two holes made a chain stage the one kind of work that could vanish. First, `owner_plan_cache_and_settle_errors` matched `ExecutionPlanError::InsufficientVram` and `continue`d — correct as a _retry_, since the running work returns the VRAM, but it was the only thing that happened: owner work carried no `MemoryBlock`, so it never reached `next_memory_reclaim` and mold never released its own idle engines for it, and `settle_unschedulable_generations` iterates `pending` alone, so nothing bounded it either. A blocked stage therefore waited forever with nothing reported, which from outside is a hang with the sequence's earlier stages already on disk. `record_owner_vram_block`, `next_owner_memory_reclaim` (asked only when no queued generation is blocked, so a print and a chain stage never evict against each other in one tick), and `settle_unschedulable_owner_work` (same `UNSCHEDULABLE_IDLE_GRACE_MS`, accruing only while the scheduler is idle and only after reclaim has actually run) close it; a resolution that succeeds clears both the block and the clock so a stale block can never bound work that can now run. Second, the owner-work candidate charged `plan.predicted_host_increment_bytes` — the RAW figure `admission_host_demand_bytes` exists to replace (on Metal the host claim already rides the unified device gate, the #1038 double-count), and the COLD figure, on a stage whose worker is usually still holding the engine the previous stage loaded. A sequence is the case where that is always wrong, and its refusal arrives after the earlier stages have already rendered. It now takes `admission_warm_host_demand_bytes` on a `holds_execution_fingerprint` hit, exactly as every generation path does through `candidate_host_demand_bytes`.
- **A cancellation is not memory evidence.** `WorkerEvent::Completed` carried one bit, and the estimate store read every `successful: false` as `EstimateOutcome::Failure` together with the lease's VRAM high-water. While a bucket has no successful sample, `failure_only_vram_floor` then plans every attempt at that shape against the recorded conservative figure — so one cancel mid-render pins the floor at whatever was resident when the user gave up, which for a video clip is near card size. Cancelling a slow sequence and re-queueing it is precisely how a render the card can hold comes back as "not enough memory". `Completed` now carries `cancelled` beside `successful` and the observation becomes `Invalidated`, which the store counts separately and which does not set `last_outcome`, so the floor never engages. Both owners report it: a chain stage from its own `StageRenderOutcome::Cancelled`, a generation from the job registry checked only on an unsuccessful outcome, so a cancel arriving after a completed render is not attributed to it.
- **Wan CUDA peaks retain their total basis; admission consumes a certified increment.** `predicted_vram_peak_bytes` and learned calibration samples remain whole-process totals. After the owner releases its sole completed Wan engine and synchronizes a retained primary context, `cuda_peak::OwnerContext` can certify the process attribution minus unused pool reserves, only when pool-used bytes are zero. Resolver/scheduler and both worker rechecks subtract that typed, owner-epoch-bound baseline from the selected total; worker rechecks bound it by fresh attribution. This addresses #1481's cold-pass/repeat-refusal without adding idle attribution to generic free capacity. Active-model credit never overlaps the certificate; non-Wan work, legacy execution, and poisoning invalidate it. Candle GGUF scratch is owned by the device (shared by its clones), so tearing down a device releases MMQ/MMVQ buffers instead of retaining them under obsolete global device IDs. Never certify live pool allocations, trim/reset a context to manufacture headroom, or normalize the persisted learned total.

So the real question is upstream of the credit: should `predicted_vram_peak_bytes` be a whole-process TOTAL at all, or an INCREMENT over what the process already holds? An increment needs no credit anywhere and cannot be confused with model residency. That is a design decision across admission, the resolver, and both worker rechecks — not a patch — and it should not be made by loosening the guards that currently keep over-admission out. `nvml` IS available in shipped CUDA builds (`cuda = [..., "nvml"]` in `mold-cli`), and `DeviceSnapshot::sampled_mold_vram_bytes` already carries the attribution, so the evidence side is solved; only the modelling decision is open.

- **Learned scheduling separates setup from execution** — typed cold-load, warm-reload, identity-extract, prompt-encode, denoise, legacy VAE, visual-decode, audio-decode, mux, and upscale phases feed the scheduler's independent runtime evidence (schema v15 separates setup-independent runtime; schema v17 adds synchronized A/V output phases; schema v22 adds face-identity extraction). Planning adds exactly the selected cold or warm setup disposition. All client device panels render every advertised device and expose live mutation only under authoritative V2; read-only modes may expose only the supported restart-enable recovery. Queue plans classify non-device work with `planned_lane_kind`; clients never infer lane semantics from opaque `planned_device_id` strings, and the capacity-one host utility lane keeps `planned_device_id = null`.
- **Durable admission is ONE resolved value, and there is no fallback.** The question "does this host generate right now" has exactly four conjuncts — `queue_journal.is_enabled()`, `!is_output_disabled(config)`, `scheduled_work.v2_authoritative()`, and `queue_journal.queue_media_admission().is_some()` — and `routes::DurableAdmissionReadiness::resolve(state, config)` is the only place they are composed. It is TOTAL over all four at ONE evaluation point and takes `config` as a required parameter it never reads, so a caller without a config cannot call it at all; that is what stops the conjunction being re-derived incompletely at a call site. Every consumer reads it: `capabilities.queue.heterogeneous_batch_max_outputs`, `capabilities.durable_media` (through `advertised_media()`, the only route to that value, so applicability cannot be forgotten), `/api/status`, `/health`, `admit_generation_batch`, and `direct_durable_admission`. **`unready()` is one function with one precedence, and every generation route reads it.** An unmet conjunct is `503 DURABLE_ADMISSION_UNAVAILABLE` on `/api/generate`, `/api/generate/stream`, and `/api/generation-batches` alike; the per-conjunct MESSAGE names the repair, but the CODE is one, because a client cannot act differently on "the journal is off" than on "the scheduler is not authoritative". The old attached, non-durable pipeline behind the two direct routes is GONE, together with the `X-Mold-Operation-Id` header that selected it, the two divergent refusal precedences, and `HETEROGENEOUS_BATCH_UNAVAILABLE`. A host that cannot replay a queued print does not render it — silently running work it could not recover is exactly the ambiguity this rule removes — and that refusal is a product decision, documented in `website/guide/configuration.md` and `website/api/index.md`. The encrypted queue-media store is a SEPARATE axis from the four conjuncts (the admission service can be installed while the store is degraded) and gates MEDIA, not generation: `503 DURABLE_MEDIA_UNAVAILABLE` for a request that carries conditioning media, nothing for a media-free one. A LoRA beside conditioning media is an ordinary durable request — `lora.path` is a request field like `model`, persisted with the rest of it and RE-VALIDATED at dispatch, so an adapter moved or deleted in the meantime holds its row naming the file rather than rendering without it; durable media protocol v1 refused the pair and that took out every img2img, inpaint, control and video-source render using one. Ordered H3 references are durable too (their descriptors are settings and their bytes are sealed media — see the queued-generation bullet below). One trait does refuse, for a reason that is not a protocol version: `hdr_exr_dir` names an output directory on the inference machine that an HTTP client may not choose — `reject_client_supplied_hdr_output` keeps that older, better-reasoned refusal and now asks it BEFORE acceptance so it stays an actionable 422. `DurableAdmissionUnready` keeps WHICH conjunct failed rather than collapsing to a bool, because `durable_media_status().reasons` reports a per-conjunct cause. Note `v2_authoritative()` serves FIVE distinct roles across routes.rs and only the durability role is behind this authority: the can-this-host-execute sites are always `|| gpu_pool.worker_count() > 0` and folding them in takes legacy and observe hosts offline; lifecycle authority, validation shape, and queue-control are likewise separate questions.
- **A durable child's ordering token is its `revision`, never its timestamp.** `generation_batch_children.revision` (schema v29) is incremented by every authoritative state transition and by nothing else — a REFUSED transition must not spend one, or a reconciling client cannot tell it from one that landed. It exists because `updated_at_ms` was carrying two jobs at once: an honest wall clock, and the version every client reducer compares. SQLite commits several transitions inside one millisecond routinely, and `POST /api/queue/{id}/retry` is the ONLY route that moves a child BACKWARD through the browser's `FORWARD_PHASE_RANK` (held ⇒ accepted), so a same-millisecond collision there is not a tie to break arbitrarily: `mergeJob` drops the backward move and the retry becomes invisible in the UI. `studio/lib/generationLifecycle.ts`'s `childRevision` reads it off the child itself rather than from an action parameter nobody ever supplied, and treats BOTH absence and `0` as no authority — rows admitted before the migration sit at `0` until their next transition, so reading `0` as a real revision would let a pre-migration snapshot win ties it should lose. The wire field is additive and `#[serde(default)]`, so an older server deserializes to `0` and every client falls back to the timestamp comparison it always used; the retry path additionally keeps its `updated_at_ms = MAX(?, updated_at_ms + 1)` bump for exactly those clients. The SECOND consumer is `reconcile_ambiguous_retry_observed`: a retry POST whose response was lost is reconciled by comparing the child's revision against the one captured BEFORE the POST, because `held` alone conflates "the retry landed and the job was immediately re-held for a fresh reason" with "the retry never arrived". A child still sitting at the submitted revision when the bounded attempts run out was NOT retried, and the call now errors with the retry fence RETAINED rather than republishing the pre-retry snapshot as fresh authority while the original POST may still commit. `observed_revision == 0` (an older host) keeps the original publish-on-exhaustion behaviour, because with no version to compare there is no evidence either way and hanging forever is the worse failure.
- **A hold is durable, not eternal.** `queue_retention.rs` is the queue's peer of `gallery_trash.rs`'s retention sweeper and is shaped like it deliberately — one `sweep_held_once` pass reading `queue.held_retention_days` fresh from the live config (default 30, `0` keeps forever, env `MOLD_QUEUE_HELD_RETENTION_DAYS`), one hourly background task, one manual `POST /api/queue/held/sweep`. What it does NOT share is the deletion mechanism: a trashed print is a file to unlink, whereas a held row's encrypted media is released by the `generation_queue_media_retire` trigger the moment the queue row is deleted, so the sweeper never writes `generation_queue_media` itself — it resolves the GC candidate BEFORE the delete (the lifecycle resolves by job id, and the row is what carries the association), deletes, then collects what the trigger just marked. A failure there is reported as `media_deferred`, not hidden, because the obligation is already `gc_pending` and startup reconciliation still owns it. Age is measured from `updated_at` — when the row was HELD — not from admission, so work that queued for a week and held yesterday gets its full window. `purge_held` re-checks held-and-owned inside the transaction, so a retry or cancel landing between the listing and the purge WINS: a human's explicit decision outranks retention. The batch child is settled to `failed` rather than deleted, because after the queue row is gone that summary is the only thing a reconnecting client can read, and dropping it would report the print as never admitted. Without this sweep a deterministically-failing request kept a `GET /api/queue` row forever AND pinned its encrypted media set, because `hold_claimed` retains `media_set_id` on purpose so a retry still has its source images. **The same horizon covers settled batch summaries.** A `generation_batches` row whose every child is terminal is a receipt for a reconnecting client and nothing else — its media left with the queue rows — and nothing ever deleted one, so the table grew without bound. `queue.held_retention_days` is deliberately the ONE key for both (no second knob): both answer "how long does the durable queue remember work that can no longer run", and `0 = forever` stays coherent. `mold_db::generation_batches::{expired_settled, purge_settled, settled_count}` are the held trio's peers — age is `MAX(children.updated_at_ms)`, the last child settlement; a batch with a held child is ineligible until the held sweep settles it (worst case 2× retention); a batch with a surviving `generation_queue` row is never eligible, and `purge_settled` re-checks all of that inside its transaction so a retry that re-queued a child between listing and purge wins. `spawn_queue_sweeper` runs the held pass then the settled pass each tick, and `POST /api/generation-batches/sweep` runs the settled pass on demand. A purged batch reads as `404 GENERATION_BATCH_NOT_FOUND` / bulk `missing.batch_ids`, which every Studio surface already reduces through `lookup_missing` without reopening a terminal tracker (pinned in `studio/lib/generationLifecycle.test.ts`).
- **Batch capability is static before engine load** — `mold-inference` owns one registry for every production family and factory alias; tests construct every advertised name and engine construction fails closed if the runtime contract differs. Production generation families currently declare only native size `[1]`. `mold-scheduler` prioritizes real initial-wave cardinality, solves homogeneous singleton fleets exactly at arbitrary size, and solves host-coupled heterogeneous singleton inputs exactly through 8 devices at arbitrary child count. Singleton plans retain one arithmetic lane per selected device with typed random access and bounded 4096-record windows; they do not materialize one record per child. Ordinary native inputs use the deterministic 64-strategy bounded fallback, while huge batches visibly fall back to the mandatory compact singleton plan as `BoundedHeuristic`. `/api/generate[/stream]` is permanently singleton-only; Batch N is 1–64 ordered singleton children admitted atomically through `/api/generation-batches`, advertised by the single `heterogeneous_batch_max_outputs` and gated by the request's exact `durable_media` contract. Larger client batches are chunked. All three routes are ONE admission — the two direct ones are that same `admit_batch` with an attached raw/SSE observer — so there is no second pipeline, no capability negotiation, and no raw batch parent: `batch_runtime`/`batch_parent`/`batch_attempt` and `WorkKind::BatchChild` are deleted, and a parent left on disk by an older server is rolled back by the ordinary gallery transaction sweep rather than resumed. No engine is represented as returning multiple native outputs. A LONE singleton carries no synthesised batch provenance — `batch_id`/`batch_index`/`batch_count` are the prepared-expansion contract and stamping them on every one-shot makes "was this a prepared variation?" unanswerable to gallery and reuse consumers — and `mold run` / the TUI keep singletons on `/api/generate/stream`, which is the one that carries live step progress, the centered fixed-protocol denoise preview, and remote missing-model auto-pull.
- **A queued generation is durable, and the retention fence is what makes that true.** One `generation_queue` row (schema v18) per admitted public singleton, written before `submit()` and owned by an RAII `QueueTicket`. Dropping the ticket deletes the row during normal operation and **retains** it once `QueueJournal::retain_all()` has been called, which is how the ~20 existing discard sites in `scheduler/mod.rs` and `gpu_worker.rs` become a resume list without any of them knowing durability exists. Order is the correctness argument: the fence goes up **before** `scheduler_shutdown.cancel()` in `begin_runtime_shutdown`, and it is raised by **all three** abnormal-exit initiators — SIGTERM, the fatal-CUDA notifier in `run_server`'s select, and `quarantine_poisoned_worker` — because fatal CUDA is the one restart mold performs on its own behalf and a SIGTERM-only fence deletes the whole queue on exactly that path. `complete()` and `discard()` delete unconditionally: a finished print must never be replayed, and an explicit cancel outranks the fence even mid-drain. `mold.db` never holds a secret — batch children, jobs with no `output_dir`, and over-`MOLD_QUEUE_JOURNAL_MAX_BYTES` payloads are excluded **at admission**, not redacted, and each is advertised per-job as `durable: false` rather than silently half-persisted. Ordered H3 references are durable media: the DESCRIPTOR is a request setting (`{authority: "descriptor"}` + sha256, what gallery metadata already records) and the BYTES are sealed into the encrypted media set at admission — upload handles are consumed inside `resolve_request` before anything is serialized, the H3 grant is captured on the descriptor request, and every consumer (feeder, H3 dependency preparation, worker, claimed-H3 owner) mints bindings from its own hydration lease; no job field carries a reference set. The H3 grant's `request_authority_sha256` hashes that same PERSISTED form — `scrub_request_media` applied, descriptors kept — so the claim, the owner, dependency preparation, and replay after a restart all compare like with like whether they hold the scrubbed row or their own hydration; media identity is the sealed set's (AEAD-bound to owner and job id), never the grant's. The two counters are charged at deliberately different moments and swapping them is a data-loss bug in both directions: `dispatch_attempts` (cap 2) by the same statement that claims a row for execution on the GPU owner thread, so a job waiting behind a long render through ten deploys is charged zero; `replay_seen` (cap 10) once per boot, sized for a 5 s `RestartSec` crash loop. Exceeding either **holds** the row — listed, never auto-run, never deleted. `OutputMetadata.job_id` is the replay idempotence key, stamped before the save: output filenames are wall-clock, so without it a replayed job leaves a permanently un-mergeable duplicate print. Replay is the durable queue feeder (`durable_queue_feeder::recover_runtime` + `spawn`, `lib.rs`): up to eight preparation workers each atomically claim the oldest unclaimed row (`claim_next`), so admission order is claim order while dependency preparation overlaps, and each row is resubmitted under its original job id through the ordinary admission path so validation, placement, frozen plans, and auto-pull all still apply — there is no second resubmission path. This deliberately diverges from chain jobs, whose `Interrupted` state never auto-resumes (`chain_job_runner.rs`): a chain owns partial artifacts and a stitched timeline, a queued singleton owns nothing, so re-running it from step 0 is free of consequence. Shutdown is genuinely bounded rather than merely timed: the deadline is armed when shutdown begins and runs _beside_ the drain, ending the process on expiry, because Axum's graceful shutdown waits on in-flight responses and a `spawn_blocking` join ignores a dropped handle — a timeout anywhere inside the sequence stops waiting without stopping anything. Hard exit is opt-in (`allow_hard_shutdown_exit`) so the embedded desktop engine, which runs inside a process it does not own, keeps returning instead. The row is settled on what actually reached the gallery, never on inference returning: a failed publication holds the row, because for a replayed job the gallery file is the only delivery. Queue OWNERSHIP and LIVENESS are separate, and conflating them is what four earlier attempts got wrong. The owner is a minted port-independent UUID recorded under `$MOLD_HOME/queue-owners/`; each record also carries the instance id that last held it; the lock proves only that the owner is running right now and never confers ownership. The requirement cannot be met from intrinsic state alone — two servers sharing a root differ only by port, so port-independence and per-server distinctness are contradictory — so a returning server is recognised by the recorded hint, not derived. Hint match ⇒ mine. No match and exactly one unclaimed queue ⇒ the single-server port change, adopt and log loudly (the retention promise clients render at shutdown depends on this working). That rule is knowingly wrong in one direction: a genuinely NEW second server, started while the first is stopped against a root holding one retained queue, is indistinguishable from a port change and adopts it. Accepted deliberately — an announced adoption beats a silent orphan, because nothing tells the user a stranded job is never coming — and documented for operators in `website/guide/configuration.md`. Do not "fix" it by tightening rule 2 without replacing what it protects. No match and several ⇒ adopt none, mint fresh, report each orphan with queued and held counted separately, and let a human use `MOLD_QUEUE_ADOPT_OWNER`. Never "first unlocked wins". A failed idempotence check is never reported as "nothing completed"; replay skips the whole boot with rows unspent, since re-rendering a published print leaves an unmergeable duplicate. A stable device pin is persisted next to the ordinal and re-resolved at replay, because ordinals renumber. Replay is skipped entirely when the boot has no dispatch owner (maintenance mode drops the queue receiver), and a submission that fails hands the job back so its row is explicitly retained — a dropped `GenerationJob` drops its ticket, which deletes the row for work that never ran. Every publication path settles the row and stamps the key, including the CPU-only one, or replay re-renders its prints as duplicates. A submitted job also always runs once queued — `job_supervisor` owns the result channel so a disconnected client no longer trips the fifteen `is_closed()` gates — and only `DELETE /api/queue/:id` closes it early.
- **A degraded subsystem is a standing state, never one startup line.** The encrypted queue-media store holds `master.key`, so `queue_media_store.rs` refuses a path that is not owned by the current user at `0700` (`0600` for the key and the lock files) — correctly, and never self-healed, because a widened mode is evidence an operator should see. What it must never do is refuse opaquely: `insecure_private_path` names the OBSERVED uid and mode beside the expected ones and prints the exact `chown`/`chmod` for whichever half diverged — shell-quoted, with an option terminator, because `MOLD_HOME` may hold a space and an unquoted `/srv/Mold Data` is two operands — because anything that walks the mold root (an ACL pass, `chmod -R`, a restore that drops modes, `rsync` without `-p`) turns durable request media off and the required state alone sends the reader to the source. The refusal is then published from ONE place — `reconcile_claimed_owner` wraps its several early returns so readiness and its reasons are set together by `set_durable_media_status`, and the journal retains those reasons for the life of the process. Three surfaces read them and their split is deliberate: each reason is logged once at WARN in full (never a bare `issues = N` count); authenticated `/api/status.durable_media` carries `available` plus the reason prose; and auth-exempt `/health` carries a body naming only the degraded subsystem (`HEALTH_SUBSYSTEM_DURABLE_MEDIA`) because the reasons name host filesystem paths. `/health` stays **200 while degraded** — generation is unaffected, so failing it would pull a working server out of a load balancer — and it never awaits the config lock, because a liveness probe that can block behind a `/api/config` write gets a healthy server killed. `available` is true EXACTLY when `capabilities.durable_media` is present, which is why `durable_media_is_applicable` (gallery output on, `v2_authoritative`) is one helper that capability discovery, `/api/status`, and `/health` all read; `durable_media_status()` answers `None` rather than degraded whenever that gate or the durable queue itself is off, or every `MOLD_DB_DISABLE`, output-disabled, and observe-mode host reads as broken. Both halves of the reason list are bounded to a sample plus a count — reconciliation issues (one per inconsistent obligation) and held job ids alike — because the durable queue is deliberately not capped by `queue_capacity`, so enumerating either would put an unbounded string in the log and on every `/api/status` response for the life of the process; the full detail stays in `GET /api/queue`, which pages.

`MOLD_HOME/mold.db` (override: `MOLD_DB_PATH`; disable: `MOLD_DB_DISABLE=1`). Current `SCHEMA_VERSION` lives in `crates/mold-db/src/migrations.rs`. Tables: `generations` (gallery rows), `settings` (KV, profile-scoped), `model_prefs` (per-resolved-model generation params, profile-scoped), `prompt_history`, machine-wide `device_preferences` (absent row = enabled by default; discovery never writes), and the library-organization side tables `tags`, `generation_tags`, `collections`, `collection_items` (schema v20; FK `generations(id) ON DELETE CASCADE`; tag names `COLLATE NOCASE`, collections merge across hosts by `slug`). Schema **v22** adds `scheduler_estimates.ewma_identity_extract_ms`, the learned runtime for `ProgressPhase::IdentityExtract` (#1227 phase 2), appended after every existing column so no `SELECT` index moves. Schema **v30** adds `generation_batch_children.error_code`, the typed cause of a held child (`MODEL_NOT_FOUND`, `UNKNOWN_MODEL`, …) persisted beside its sentence and cleared by the retry route — the field every client's missing-model pull offer classifies on, projected as additive `GenerationBatchChild.error_code`. Schema **v31** adds the expression index `idx_gen_dir_recency` on `(output_dir, COALESCE(file_mtime_ms, created_at_ms) DESC)` — exactly the gallery listing's filter and order — so `GET /api/gallery` walks rows in listing order instead of sorting the whole directory in a temp B-tree on every poll (pinned by an `EXPLAIN QUERY PLAN` test). Migrations are forward-only via `PRAGMA user_version`; add to `MIGRATIONS[]` and bump `SCHEMA_VERSION`.

**Library organization and trash are per-host row state, never request state.** `generations.title` / `favorite` / `trashed_at_ms` are user-owned: `upsert_with_conn` excludes them from `ON CONFLICT DO UPDATE` (title is seeded once from `OutputMetadata.title` via `COALESCE`), so a reconcile/import refresh never resets them; `mold-db/src/organization.rs` and `trash.rs` are the only writers. Creation-time filing is the one thing a request seeds, and it is seed-once by construction: `GenerateRequest` / chain-body `tags` + `collection` ride `OutputMetadata` into `seed_creation_organization`, which runs only on `upsert_with_conn`'s INSERT branch, so a reconcile or re-publication never resurrects a tag the user removed. Embedded tags are re-normalized (bad ones dropped, never fatal) and the collection resolves by SLUG, created when absent, so one name means one collection across a fleet. `mold_core::organization` owns the wire rules (≤20 distinct tags post-normalization, 1..=64 scalars each, whitespace-controls collapsed and other controls refused, a leading `#` literal); clients compose the title auto-tag through `compose_client_tags` — the server never auto-tags — and a filing that cannot be applied (`MOLD_DB_DISABLE=1`, a `{id}` collection deleted between listing and admission) is dropped while the print publishes anyway, reported on `x-mold-request-warning` plus additive `request_warnings` on `GenerateResponse` / `ChainResponse`. Never split that header's value on `;` — advisory prose contains it. Trash = `<output_dir>/.trash/<filename>` + the row flag + a `<filename>.trash.json` tombstone carrying the row and its organization; reconcile validates trashed rows against `.trash/`, imports tombstoned files that lost their row, and never scans `.trash` as live. `DELETE /api/gallery/image/:filename` trashes and `?permanent=true` hard-deletes; the committed archive is NOT retired on trash (only on purge), and a restore un-retires nothing because nothing was retired — a live print already holding the name is a `409 GALLERY_RESTORE_CONFLICT`. `GET /api/gallery` applies organization and the `?view=library|trash` filter POST-overlay by filename, because `overlay_db_gallery` prefers archive records and re-adds archive filenames absent from DB rows. Retention is the one DB key `gallery.trash_retention_days` (`gallery.` ⇒ `Surface::Db`, env `MOLD_GALLERY_TRASH_RETENTION_DAYS`, 0 = forever, max 3650, default 30), read fresh by the hourly/startup sweeper and `POST /api/gallery/trash/sweep`; `capabilities.gallery = { can_delete, trash: { enabled, retention_days }, organize, bulk_mutations, media_version, conditional_get, row_events }` (every field past `can_delete` additive and `#[serde(default)]`, so absence reads as no) is absent/false under `MOLD_DB_DISABLE`. Titles ride `GenerateRequest.title` → `OutputMetadata.title` → the row, validated by `mold_core::validate_print_title` (trim, ≤120 chars, no control chars) and slugged into the default filename as `mold-{model}-{ts}[-{idx}]~{slug}.{ext}` (`title_slug`, `[a-z0-9-]{1,40}`; `strip_title_slug` before the legacy filename parser); renaming never renames the file. Download dialogs suggest `mold_core::download_file_name`'s `{title-slug}__{model}__s{seed}.{ext}` (independent components joined `__`, model slug capped at 80, fallback stem `print`) — a suggestion only, never a rename. `mold run --title/--tag/--collection/--no-auto-tag` (with the `generate.auto_tag_title` DB preference), `mold library list|show|grid|title|favorite|unfavorite|tag|collection|trash`, and `mold trash list|restore|empty|sweep` are the CLI surfaces (HTTP to `$MOLD_HOST`, no local fallback). The TUI Library lists only live rows (`MetadataDb::list_live`), shows titles in the Details panel and full detail view, and its `d` moves to the trash — locally via `mold_db::trash` helpers when the metadata DB answered the scan, remotely via `MoldClient::trash_gallery_image` — degrading to honest hard-delete wording (`RemovalKind`) whenever any owning machine cannot trash; the Settings view edits `gallery.trash_retention_days` through the shared config_sync writer.

Gallery writes happen in the server (`queue.rs` upserts after disk write; background `reconcile(output_dir)` on startup), CLI (`crates/mold-cli/src/metadata_db.rs` via `record_local_save`), and TUI (`gallery_scan.rs`). DB is additive — embedded PNG/JPEG `mold:parameters` still get written, and open/upsert failures log and keep working. Open-time `quick_check` and query-time gallery corruption recovery quarantine `mold.db` plus WAL/SHM as `mold.db.corrupt-<timestamp>*` under a cross-process recovery lock, recreate the schema, and reconcile gallery rows from disk; the retained quarantine is the only source for manually salvaging settings/history.

- **`mold queue` is the CLI surface for the durable queue.** `list` / `show` / `cancel` / `retry` / `move` / `pause` / `resume` / `sweep` talk HTTP to `$MOLD_HOST` with no local fallback, exactly as `mold trash` does. Its waiting vocabulary is NOT a second policy: `mold_core::queue_wait` is the Rust twin of `studio/lib/queuePosition.ts` (running step counter, `Next up`, `#N in line`, an ACTIONABLE blocked reason only, `Waiting on the host` for one this build has never heard of), and every Rust surface resolves through it. Retry needs the whole authority, and only `instance_id` belongs to the server — so `GET /api/queue` and `GET /api/queue/{id}` carry additive `batch_id` / `client_batch_id` / one-based `batch_index` off the `generation_batch_children` join, which is what makes a bare job id retryable from any client.
- **Cancellation capability.** Current servers advertise `queue.cooperative_cancellation`: queued work and running singleton generations cancel through `DELETE /api/queue/:id`, with the worker stopping at the next model safe point. iPhone Host detail keeps its 44pt two-step action and exact Keychain-authenticated route for both states; older hosts keep running rows read-only.
