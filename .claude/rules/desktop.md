# Desktop app (Tauri) invariants

Moved verbatim from the root CLAUDE.md; loaded only when working under the paths above.

Desktop gallery authority is singular: while its local server is running or its lifecycle is unresolved, native list/save/delete/media paths use authenticated HTTP (ticketed for media elements). Direct filesystem access is allowed only while the lifecycle mutex proves `LocalServer::Off`.

**Desktop app** (`desktop/`): Tauri 2 macOS/Linux/Windows app (Vue 3 + TS, **Mold Studio** design system — `docs/design/README.md` (lexicon, shell anatomy, component vocabulary) and the reference implementation `docs/design/mold-studio-desktop.dc.html` are the design source of truth; six named themes — Mocha (default), Safelight, Blueprint, Graphite, Porcelain, Nebula — each a complete `--mold-*` token map in `ui/tokens.css` selected by one `data-theme` attribute, with a **Match system** toggle that swaps to the paired light/dark theme through `THEME_PAIR` in `ui/theme.ts`; the Rust `AppSettings` stores `{ theme: ThemeId, match_system }` and migrates the old `{ theme, theme_family }` pair on the JSON value so a legacy `theme` can never fail the struct and drop saved hosts — and `settings::load` recovers PER KEY, so a value this build cannot read (an update channel or connection mode a newer nightly wrote, then an older build or a dev build sharing the same app data reads it back) falls back alone while every other key stays, a list keeps every element that reads (one malformed saved machine never forgets the others), and `load_reporting` names the keys that fell back so the boot-time remote-primary migration is withheld when `mode` or `remoteUrl` was a fallback rather than the user's value (`migration_premise_intact`); a document that is not a JSON object is kept as owner-only `settings.json.invalid` rather than overwritten. Never let `load` answer a parse failure with whole-struct defaults: the next save persists them, which is exactly how a stale dev build moved a Nightly install back to Stable and forgot every machine on 2026-09-03; shared primitives live in repo-root `ui/`, consumed by web, desktop, and iOS), package `mold-desktop` — its own cargo root, `exclude`d from the workspace. The desktop speaks the binding lexicon (`docs/design/README.md` §2; `desktop/src/lib/lexicon.test.ts` pins the destination words on the router, sidebar, palette, and native menu plus the inspector's seed labels — view copy is reviewed by hand): the sidebar's destinations are **New image** (⌘1, `/create` — the view toolbar's **Still picture | Short clip | 3-D object** control is the ONE output switch, emitting `set-output` into the inspector's `setOutputMode`; the inspector carries no second one. **A clip has two ways of being made, and the plain one is the default.** **Simple | Scenes** (`data-test="clip-mode"`, "How to make the clip") is `ClipModeStrip.vue`, a row of its own UNDER the toolbar in the chip row's chrome, rendered only while the kind is clip, with one sentence beside it saying what the chosen way does ("One prompt, one clip." / "Scene by scene, joined into one clip."). It is deliberately NOT a second control on the toolbar: there it sat between the kind control and the doors, so choosing Short clip pushed the whole right-hand cluster left and the control just clicked jumped away from the pointer; `CreateHeader` holds the same children in every kind (pinned by its test) so nothing on it ever moves. **Simple** is the EXISTING one-shot video path: `draft.output` stays `single`, a clip style is what makes it a clip, the composer invites "Describe the clip" and carries a **Length** chip (an 84px track plus the mono `97f · 4.0s`, snapped by `@studio/lib/videoDuration` to the family's request grid, writing the same `form.frames` the inspector's Clip card slider writes), and Make is the ordinary batch stepper. **Scenes** is `sequence` output and the timeline; Make is HIDDEN there, because a chain has no batch. The sub-mode is `sequenceDraft.clipMode`, persisted beside the draft like `lastSingleModel`; the strip RENDERS what is on screen (`isSequence ? "scenes" : "simple"`) rather than the preference, so the two can never disagree, and the store keeps `output === "sequence" ⟹ clipMode === "scenes"` through one sync watcher — `setOutput`, `loadFromJob`, and the direct `output` assignment in `applySequenceReuse` all pass through it, so a reused or edited chain print lands in Scenes without a second writer. Short clip opens onto the remembered sub-mode: Simple adopts a clip style IN THE HEADER (the way the 3-D door adopts a 3-D style — handing the inspector `single` would restore a PICTURE style), Scenes emits `set-output: "sequence"` as before, and a machine with no clip style falls to Scenes, which owns that empty state. `GenerateView.setClipMode` owns the switch itself because it needs the chain limits: to Scenes it seeds scene 1 from the composer's words and the longest scene that fits its length (`sequenceFrameOptions`, never a length the chain validator refuses) but only when no scene has been written; back to Simple it PARKS the draft untouched — the timeline's own Clear the clip stays the only eraser. The palette's `act-clip-scenes` ("Edit the clip scene by scene") raises the `clipScenes` create intent, not a `?output=` deep link, because `consumeOutputQuery` only runs on mount; the palette's `nav-sequence` ("Make a short clip") and File ▸ New Clip raise `shortClip` for the same reason, and the view answers it with `useOutputKindDoor(...).setOutputKind("clip")` — the SAME door the toolbar's segment opens; raised from another workspace the intent is consumed during setup, before `inspectorRef` exists, so the Scenes swap waits a `nextTick` for the inspector instead of being dropped, and with nothing installed (starter cards, no inspector at all) it switches the draft directly since there is no style to swap. The doors pick only from RUNNABLE rows (`targetModels` minus `isModelRuntimeUnavailable`), never a downloaded style no machine can run (`composables/useOutputKindDoor.ts` is the one decision for all three doors; `CreateHeader` only renders it), so they land on the remembered way and the remembered style instead of always Scenes. `?output=sequence` is kept for Library's sequence reuse, which really does mean Scenes. `useCreateOutputKind.outputKindFor` therefore delegates a one-shot to `outputKindForModel`: a one-shot on a clip style IS `clip`, which is what puts the simple clip under Short clip, gives it the New clip title, and narrows the picker to clip styles. In Scenes the one composer carries the SELECTED SCENE's words (two-way with the draft store's active scene), reads "Scene N — describe what happens next", and ⌘↩ submits the chain; the one-shot prompt's provenance, its quick rewrite, and its ↑/↓ history stand down there because those words belong to a scene, not to the form. `SequenceComposer.vue` is therefore the timeline alone — transport (a 26px accent play/pause driven by the rendered-clip player, mono `0:06 / 0:20`, "Add a scene"), ruler, the scenes lane, the playhead, the selected scene's Length picker, the seam editor, and one mono readout — and it reports its own refusal up through `update:blockedReason` rather than holding a second primary action. The lane is `desktop/src/components/create/SceneLane.vue`, desktop-only: every block is `flex: <seconds> 1 0`, so a block is as wide as the time it plays and the lane always FITS its width — there is nothing to scroll, which is the whole difference from the shared `ui/components/ClipRail.vue` filmstrip web still uses. A block's title is the scene's own words, its poster sits behind at 34%, the seam floats above the join, and only the selected block carries the 9px trim grip, whose drag snaps to the same frame grid (`8k+1`, `4k+1` for wan) the Length picker offers. Space and ⌥↩ are the two chords the focused element can claim before the shell does (`resolveFocusSensitiveShortcut`): Space toggles the display host's queue pause and ⌥↩ makes the canvas print four more times, and both stand down inside a field, on a focused control, and under any `aria-modal` overlay — Option+Return is a newline in a prompt. Space additionally stands down on `/library`, where Space is Quick Look, and on a machine whose queue cannot pause (`ShellKeyContext.canPauseQueue`, the same `commands.canPause` the status bar hides its hint behind) — the shell must never swallow a key it cannot act on. The same handler `preventDefault`s a bare Backspace whose target is not editable (`ownsBareBackspace`), because the webview reads it as history Back and unmounts the whole window; Delete on a two-scene clip is how that surfaced. The pause is READ before it is decided: `togglePause` refreshes the display host's queue snapshot and is gated on `caps.canPause`, because `jobs.pause` writes nothing back onto a snapshot nobody fetched — the first Space paused for real, `paused` stayed false, and the second paused again. The shell owns that poll (`App.vue` starts `jobs.startPolling`, refcounted alongside Machines'), and the status bar advertises the Space hint only where the host reports a pausable queue. Per-row Pause/Resume is gated on `caps.canPauseJob` and offered only for a `queued` or `paused` entry — the running job has no pause API, so the active card's button pauses the QUEUE and says so. **Four invariants the first walk-through taught.** (1) `ui/kit.css` is imported inside `@layer components` (`desktop/src/styles/base.css`, pinned by `desktop/src/styles/kitLayer.test.ts`): every Tailwind utility lives in `@layer utilities`, and under CSS Cascade 5 an UNLAYERED declaration outranks every layered one regardless of specificity, so an unlayered kit made every `text-`/`border-`/`h-` utility written beside `ms-toolbar-button` a silent no-op — the queue rail's pause state was invisible. Never unlayer it and never reach for `!` variants to beat it. (2) A colour utility never shares a static class attribute with another: all colour utilities are specificity 0,1,0, so the winner is emitted-rule order, not attribute order (`.text-fg-dim` is emitted after `.text-accent` and `.text-error`, which is how a "won't fit" VRAM verdict painted dim grey). Colour lives entirely in the bound `:class` map with no static default beside it. (3) A subtree that wears another theme (the Look picker's swatch band is the only one) must read `var(--mold-*)` directly, never a Tailwind alias: `--color-bg: var(--mold-bg)` is substituted where it is DEFINED, on the root, and the substituted value is what inherits, so a nested `data-theme` redefines `--mold-bg` after anyone could read it. (4) The Create workbench's bench clamp is `desktop/src/lib/benchLayout.ts`, the one authority: the ceiling is `available − (canvasFloor + resizer + measured composer)`, the canvas's `min-height` is BOUND from the same `canvasFloor`, and the composer measures itself with a `ResizeObserver` — a hard-coded utility beside the clamp is how the CSS came to say 320 while the clamp reserved 144 and `overflow-hidden` ate the composer, which in clip mode is the only Generate. **Embedded engine stop is bounded, and its boot test reads what it requests.** `start_engine_inner` calls `mold_server::bound_http_drain(server::HTTP_DRAIN_GRACE)` before `run_server` because Axum's graceful shutdown waits for every in-flight request and the webview is a client the app does not control (a paused video stops draining its socket; a request whose body never arrives stays in flight forever); after the grace the engine gives up on them, and the runtime drop in `server.rs` is what closes those connections. `HTTP_DRAIN_GRACE` must leave `ENGINE_STOP_BUDGET` room for the dozen shutdown steps after the drain (a compile-time assert pins the ratio); the stop command and app exit pass `ENGINE_STOP_BUDGET`, and changing Mold home waits twice it. The standalone server keeps its unbounded drain behind `MOLD_SHUTDOWN_ABORT_SECS`, which ends the process. In `desktop/src-tauri/tests/engine_boot.rs` every response is READ before shutdown: `/api/models` is over a megabyte, and a response left unread is a response the engine is still writing once the loopback buffers fill — whether they fill was up to the kernel's window autotuning, which is the coin flip that skipped the desktop nightly for days (#1582). `a_client_that_stalls_cannot_hold_the_engine_open` pins the bound with a request whose body never arrives.

**Desktop updater:** signed release builds support persisted **Stable** and **Nightly** channels. Startup and menu/Settings checks are check-only; an available update is announced in persistent app chrome and by a native notification while backgrounded, and installation requires the user's explicit **Update and restart** action. Stable reads the public `mold-desktop-stable.json` manifest from the latest tagged release; Nightly reads `mold-desktop-nightly.json` from the rolling `latest` prerelease, which `.github/workflows/desktop.yml` rebuilds only after the frontend and Rust gates pass for a desktop-relevant `main` commit. Before touching the installed app, Tauri verifies the Minisign signature and Mold fully extracts the archive to temporary storage, binds its bundle ID/version to the manifest, runs strict Apple code-signature and Gatekeeper checks, validates the current app identity and install location, and proves the app's parent directory is replaceable. Only then does Mold atomically exchange the staged and installed bundles with macOS `RENAME_SWAP` and restart. There is deliberately no post-launch watchdog, probation, or Mold-owned rollback; the update either passes preflight and installs or fails while the running version remains in place. Do not add a silent downgrade comparator: selecting Stable from a newer Nightly waits for a later stable version. Distribution CI requires `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in addition to the Apple signing/notarization secrets, verifies signatures against the checked-in public key, and retains ten Nightly desktop generations. The updater private key must have controlled offline backup and must never enter the repo or logs; losing it strands installed clients, and rotation must first be delivered by an update signed with the existing key.

**Desktop Library performance invariant:** the grid is near-native at 1 000+ prints because nothing per tile walks the gallery. `desktop/src/stores/gallery.ts`'s `organizationIndex` / `bucketIndex` getters compute each logical print's organization union and cross-host copies ONCE per data change (`organizationOf`, `locationsOf`, `existsLocally`, `rowOf` all read them; `locationsIn` is the same filename-or-identity-within-window answer the old full scan gave, off the index), rows are `markRaw` immutable snapshots replaced through `patchRow` — never mutated in place, which would notify nothing — and a 304 poll skips the assignment. `LibraryView` renders ONE flat print-keyed absolutely positioned tile layer from per-tile `TileModel`s so a slider drag or resize moves tiles instead of remounting `AuthedMedia`; `studio/lib/thumbnailScheduler.ts` dispatches from per-(priority, host) FIFOs in O(hosts). Thumbnails persist in `desktop/src-tauri/src/thumbnail_cache.rs` (`<app_data>/thumbnail-cache/v1`, key = origin + filename + `media_version` + tier, NEVER the API key; 512 MB / 20 000 files LRU), prepared through `prepare_gallery_thumbnail` and displayed through the async `mold-thumb://` protocol that only reads the cache, so JS holds no bytes for a tile and a cold launch touches no host; with the engine Off, this device's tiles are rendered in-process through `mold_server::thumbnails` and never the full-size file. Every guard is an OPERATION COUNT against a budget (`studio/lib/galleryPerfBudget.ts`): `gallery.perf.test.ts`, `LibraryView.perf.test.ts` (real virtualizer, 2 000 prints), the scheduler drain test, and `cached_thumbnail_performs_zero_fetches` — add to them, never loosen them. Web and the phone have no native disk: `studio/lib/thumbnailPersistentCache.ts` is the shared Cache API store (secure contexts only — a plain-`http://` LAN origin gets `null` and keeps the memory LRU; keyed host + filename + `media_version` + tier, never without a version), `web/src/lib/galleryMedia.ts` reads it for authenticated hosts, the phone already persists through `storeCachedGalleryMedia`, and `thumbnailRenditionQuery` (`?size=256|512&fmt=jpeg`, 512 at DPR ≥ 1.5) is the one rendition policy every surface appends — an older server ignores it and answers its 256 px PNG, so no client may branch on the reply's format.

**Desktop model-library invariant:** the Ready-to-use shelf and download progress are all-connected-host views, host detail mirrors the selected host's downloads, and built-in manifest variants take precedence over ambiguous multi-checkpoint Hugging Face repositories so Get it targets one runnable model rather than an aggregate repository.
